# Bots and abuse

What keeps bots, scripts and floods off the platform, door by door; the Vercel Firewall settings that the owner applies in the dashboard and how to check them; the one door that Vercel cannot see (the sign-up) and when to put a CAPTCHA on it; and what a move to Cloudflare would need if it ever comes back. Decided with the owner on 2026-11-09. The vendors' facts were read from their own pages that day and the DNS from the public records; they change, so read the sources again before acting on them. The settings live in the vendors' dashboards: nothing in the repo reads or writes them.

## Decision (2026-11-09)
- **The goal**, in the owner's words: keep the bots and scripts that pollute the platform out, real humans only, no heavy checks, and no paid service. Asked what Cloudflare is for, the owner first asked how the others keep bots and DDoS attacks away, then wanted to know why they use Cloudflare and whether it is worth it for this
- **Vercel's own firewall, nothing in front of it.** Vercel gives for free the layers that a Cloudflare front door would, says "we do not recommend" a reverse proxy in front of it, and its Bot Protection does not work behind one. The DNS stays at Spaceship and the site goes straight to Vercel. If images of our own, or an attack that Vercel does not hold, bring Cloudflare back, "If Cloudflare comes back" says what it needs
- **No CAPTCHA on the sign-up for now** (the owner chose the Vercel settings only, 2026-11-09). That door is braked by the e-mail code and by Supabase's limits, and "The sign-up door" says what to watch and what it takes to close it
- No code changes for this: the settings are the dashboard's

## The doors
| Door | Road | In the code | In Vercel, free | Left |
| --- | --- | --- | --- | --- |
| The pages, `/api/<slug>/**` (tables, moves, chat, feedback), `/api/hub/**`, `/auth/*`, `/gamemaster/api/login` | Vercel, then our function | `rateLimit` per player and per IP, in the memory of each function instance (`docs/routing.md`); the honeypot of the feedback form | DDoS mitigation (always on), Bot Protection, a rate-limit rule, Attack Mode | a bot that drives a real browser |
| Sign-up, password sign-in, a new code | the browser to Supabase Auth, straight, with the public key: Vercel never sees it | the e-mail code ("Confirm email"); `signUpWithPassword` and `resendSignupCode` take a `captchaToken` | nothing | Supabase's own limits and the e-mail code |
| Google, Discord, Twitch | the provider's sign-in, then our `/auth/callback` (a Vercel route, like the first row) | the provider's own checks | as the first row, for the callback | the provider's side |

## What Vercel gives for free (read 2026-11-09)
Hobby or Pro unless a line says otherwise; the plan is the Vercel team's.
- **DDoS mitigation**, layers 3, 4 and 7, automatic, every plan. Traffic it blocks is not billed; traffic served before it reacted, and bots it does not take for an attack, are
- **Bot Protection** (Firewall › Rules › Bot Management): off by default. Log records what it would catch and touches nothing. Challenge serves a JavaScript challenge to clients that break browser-like behaviour and to requests that lie about being a browser (a `curl` saying it is Chrome); the verified bots (search engines and a list of link-preview and monitoring bots) are left alone. A challenge that is passed leaves a one-hour session in the browser
- **Rate limiting** (Firewall › Configure › New Rule): counted per IP address or per JA4 TLS fingerprint, in a fixed window of 10 seconds to 10 minutes, per region, and shared by all function instances, which `rateLimit` is not. Hobby has one such rule (inside its 3 custom rules) with 1,000,000 allowed requests included; Pro has 40, billed by use
- **Attack Mode** (Firewall › ⋯ › Enable Attack Mode, for 1, 6 or 24 hours): challenges every browser visitor. Free and unlimited; the verified bots, our own functions and our cron jobs go through
- **Alerts** on a detected attack (125,000 requests in 15 minutes) by webhook or the Vercel app for Slack, every plan. **BotID** Basic (free) and Spend Management (Pro) exist too; the OWASP ruleset is Enterprise
- The AI Bots ruleset (off) is a choice about being found by AI crawlers, not about pollution: left alone

## The settings (the owner, in Vercel › project `pbgo` › Firewall)
A change is saved, then published (Review Changes › Publish); publishing again with the old value is the way back.
1. **Bot Protection in Log.** Watch the Traffic view for a few days (filter by the rule; look at the user agents and the paths). What must not be flagged: the preview bots of the apps where table links are pasted (Discord, WhatsApp, Telegram, Slack: none is on the verified list printed on Vercel's page, and a Vercel community report from the beta says Discord lost its previews behind Bot Protection), search engines, the nightly cron, any uptime monitor. Test by pasting `https://playboardgamesonline.app/game/courtisans` in each app
2. **A bypass for what is flagged and legitimate**: a custom rule, If User Agent contains `Discordbot` (for example), Then Bypass. A user agent can be faked, which only lets a script skip Bot Protection: the rate limits remain
3. **Challenge, once the cookie is in the Cookie Policy** (below). Then: a browser still reaches the site; a plain `curl` of the home page gets the checkpoint or an error and not the page; the previews still show; Settings › Cron Jobs runs `/api/cron/purge` (or `curl` it with `?dry=1`) and succeeds
4. **One rate-limit rule on the admin login**: If Request Path equals `/gamemaster/api/login`, Then Rate Limit, Fixed Window, 10 minutes, 10 requests, per IP. The code allows 5 per 10 minutes per function instance; this one is shared, so a script that spreads its guesses over many instances is still capped. On Pro add the next ones in Log first (`/api/` per IP): a household behind one address polls a table every few seconds, so read the Traffic view before enforcing
5. **Attack Mode is the panic button**, not a setting to leave on: turn it on for an hour when the site is hit, off when it is over
6. **Alerts**: the "Attack Detected Firewall Event" webhook or the Slack app. On Pro, Spend Management to be told, or to pause, at an amount

**The cookie.** Challenge, and Attack Mode, keep a one-hour challenge session in the browser of whoever they challenge, and the Vercel pages read do not name it. A visitor who is wrongly challenged then gets something stored on arrival, which the Cookie Policy says never happens. Before Challenge goes on: open a path that a temporary custom rule challenges (If Request Path equals `/challenge-test`, Then Challenge) or turn Attack Mode on for an hour, pass the checkpoint in a browser, read the name, the lifetime and the attributes in the developer tools (Application › Cookies), delete the temporary rule, and in one pull request add the entry to the Cookie Policy ("What the site needs") and reword its "Nothing is stored when you arrive" and the lines of `docs/legal.md` ("On the device")

## The sign-up door
The sign-up and the password sign-in go from the browser to Supabase Auth, straight, with the public key (`createBrowserClient` in `packages/accounts/src/client.tsx`). Vercel never sees them, and a script can call Supabase without visiting the site. What brakes it is Supabase's: the e-mail code (an account stays unconfirmed without it), its rate limits (`docs/legal.md`, Findings 13) and, behind them, the 100 e-mails a day of Resend's Free plan, which a flood can use up for everybody.
- **What to watch**: many unconfirmed accounts, or addresses nobody would own, in Supabase › Authentication › Users; Resend's daily count near its limit; bursts of sign-ups in the project's auth logs
- **When it shows, a CAPTCHA**: Cloudflare Turnstile (free; it needs a Cloudflare account but not Cloudflare in front of the site; invisible or a checkbox only when the visitor looks suspicious) or hCaptcha, the two that Supabase takes. Supabase checks the token itself (Authentication › Bot and Abuse Protection, the provider's secret in the dashboard) and the client sends it as `options.captchaToken`; `captcha_failed` already has its sentence. Not done: the widget in `SignupCard` and `SignupCode`, and in `/login`, because `signInWithPassword` passes no token and Supabase's CAPTCHA very likely applies to the password grant too (to check on `pbgo-preview` before relying on "needs the widget and nothing else" in `docs/accounts.md`, and only the owner can switch it on there)
- **Legal, with the widget**: it is a script from Cloudflare on those pages, so the Privacy Policy ("Who receives your data", "Outside the European Union"), `docs/legal.md` (Recipients) and, if it stores anything on the device (the pages read do not say), the Cookie Policy. Vercel's BotID does not fit this door: it needs a `checkBotId()` call on a server route of ours, and the sign-up does not go through one

## If Cloudflare comes back
Two reasons it might: images of our own are served (an avatar library, uploads), which is where its CSAM Scanning Tool has something to scan; or an attack that Vercel's layers do not hold. Nothing below is done.
- **The DNS today** (public records, 2026-11-09; the owner's export from Spaceship › Advanced DNS is the source of truth, a public lookup cannot list a zone). Nameservers `launch1.spaceship.net` and `launch2.spaceship.net`; no AAAA, CAA or `_dmarc` record found

| Name | Type | Value |
| --- | --- | --- |
| `@` | A | `216.198.79.1` (Vercel) |
| `www` | CNAME | `93b5a2473bd4d47f.vercel-dns-017.com.` (Vercel; redirects to the apex) |
| `@` | MX | `0 mx1.efwd.spaceship.net.` and `0 mx2.efwd.spaceship.net.` (Spaceship's forwarding of `hey@playboardgamesonline.app`) |
| `@` | TXT | `v=spf1 include:spf.efwd.spaceship.net ~all` |
| `send.mail` | CNAME | `send.forge.rmta.net.` (Resend) |
| `resend._domainkey.mail` | TXT | Resend's DKIM key (copy it from the Resend dashboard) |

  Every record must exist at Cloudflare, "DNS only" (grey), before the nameservers change, or the site, the contact address and the sign-up e-mails break; Cloudflare's own scan "is not guaranteed to find all existing DNS records"
- **DNSSEC is on at Spaceship** (a DS record, `57789 13 2 …`, is published at the `.app` registry and the zone is signed). Cloudflare: "you must turn it off at your registrar before replacing nameservers", or validating resolvers answer SERVFAIL and the domain is unreachable. The order: remove the DS at Spaceship; wait until it is gone and its TTL has passed (the registry served 1800 seconds; Cloudflare says "commonly 24–48 hours for most TLDs"); change the nameservers; wait for "Active"; enable DNSSEC at Cloudflare and give Spaceship the new DS (algorithm 13)
- **A proxy (orange cloud) on the site** costs Vercel's firewall visibility, its Bot Protection and the real client IP. Vercel overwrites `x-forwarded-for` and forwards no external value, `x-vercel-forwarded-for` and `x-real-ip` are the same value, and Verified Proxy Lite (automatic for Cloudflare, every plan) recognises the proxy without restoring the client IP (that is Enterprise). `clientIp` (`packages/core/server/rate-limiter.ts`) would then see Cloudflare's address for every visitor: the per-IP ceiling, the presence beat (429 for nearly everyone), the admin login limit (used up by anyone, locking the owner out) and the feedback fingerprint would all share one bucket. The fix, not written: read `CF-Connecting-IP` only when a secret header added by a Cloudflare Transform Rule is present and equal in constant time (a new variable in `apps/web/.env.example` and `docs/supabase-and-env.md`), with tests. With the apex and `www` "DNS only" none of this applies
- **Cloudflare settings that must stay off or be set**: Bot Fight Mode (it sets `__cf_bm`, switches on JavaScript Detections that add a script to the pages and cannot be bypassed on Free), Rocket Loader, Email Address Obfuscation, anything that sets a cookie on arrival; SSL/TLS Full (strict), never Flexible (redirect loops); no cache of the HTML or of `/.well-known/vercel/*`; no HTTP→HTTPS redirect of `/.well-known/acme-challenge/*`. Vercel Cron calls the deployment's `*.vercel.app` address, so a proxy on the domain is not in its path
- **CSAM Scanning Tool** (zone › Caching › Configuration, free): compares images "served for your website through the Cloudflare cache" with known lists, blocks a match where it can and e-mails the matched paths once a day. It scans nothing while the site serves no image that a visitor uploaded (provider pictures load from Google, Discord and Twitch, not from us). Enabling it accepts Cloudflare's Service-Specific Terms. Cloudflare files the report to NCMEC itself, but that "does not relieve you of any legal requirements": the owner likely has to report to the authorities, may have to keep a copy of the content and likely has to keep records for a year, and Cloudflare may end all its services if matched content is not removed in time. No procedure is written: a lawyer should read the terms and write it first
- **Legal, in the same pull request as the change**: a Cloudflare row in `docs/legal.md` (Recipients and, if it proxies, the inventory: it sees the IP address, URL and headers of every request; processor; its Customer DPA, version 6.4 of 2026-04-03, with the standard contractual clauses and the EU–US Data Privacy Framework; it stores "primarily in the United States and the European Economic Area" and may reach data from anywhere; ⚠ the owner confirms in the dashboard that the DPA is in force), the Privacy Policy ("Who receives your data", "Outside the European Union", "Last updated") and the Cookie Policy if a cookie appears
