# The platform's Sanity project

`playboardgamesonline` (project `mhgqs6fe`, dataset `production`, public): the content of the hub itself, apart from the games' own projects. It holds the **catalog** (every game the hub lists and the expansions played with them, with the people, publishers and categories they point at), the **editorial** documents (articles, changelog, announcements) and, one day, the **shop**. The hub reads the catalog from it (PLT-90), in place of the Notion Games database it read before: this project was first filled by a seed from the Notion rows, and the Studio is where it is edited now. Notion stays the internal tracker (what is being built, in which order). Part of PLT-19 and PLT-90.

It is not a game's Sanity project: a game's project holds what is played (cards, board, sounds) and its texts in four languages, this one holds what the hub says about games, in twelve languages, field by field (PLT-104, below).

## The model

The Studio's sidebar has three blocks: **Catalog**, **Editorial** and **Shop**. The shop block is empty on purpose: there is no document type for it, no skin, until we have looked at how Discord builds its shop.

### Catalog

| Type | Fields |
| --- | --- |
| `game` | **Identity**: `name` (English, plain text), `names` (its name in the other languages, optional), `slug`, `bggId`, `kind` (game · reimplementation), `baseGame` (→ game, for a reimplementation), `order`. **Facts**: `playersMin`, `playersMax` (empty: or more), `duration` (minutes), `minAge`, `complexity` (1 to 5, BoardGameGeek's weight), `releaseDate`, `categories` (→ category). **Credits**: `creators` (a list: one creator with one or several roles per line), `publishers` (→ publisher), `buyUrl` (the page of a shop that sells the game, https: the link under the credits of its page; none, no link). **Texts**: `tagline`, `description`. **Rules**: `rules` (links), `helpers` (the aids a player may have while they play, which the game's lobby offers one by one, `HELPERS_MAX` (8) at most: a list of `gameHelper` objects, each with a `title` (one line: "Show the score calculation") and the `key` that the game calls it by, lowercase letters, digits and dashes, unique in the game and not changed once the game reads it; the same in every language for now). **Visuals**: `cover`, `logo`, `icon`, `background`, `boxFront` (the box, front), `gallery` (what the game's page shows after its cover, `GALLERY_MAX` (5) at most: a list of pictures, each with a caption, and clips, an object `galleryClip` with a `video` file (MP4 or WebM, a few seconds to half a minute, muted and played in a loop by the page), a `poster` picture and a caption). **Related**: `related` (→ game). `names`, `tagline`, `description`, `rules`, `cover`, `logo` and `boxFront` are translated fields (one row per language, below); the `icon`, the `background` and the `gallery` are the same in every language |
| `expansion` | **Identity**: `name`, `slug` (48 characters at most where a game's is 40: it starts with its base game's slug, and names no package, token or Studio host), `baseGame` (→ game, required, a strong reference), `bggId`. **Facts**: `playersMin`, `playersMax` (the players with the expansion), `duration` (minutes), `minAge`, `complexity` (1 to 5): filled only where the expansion changes the base game's figure, and an empty one is the base game's (so `playersMax` has no "or more" here); `releaseDate`, its own; `categories`, the ones it brings that its base game does not have (the lobby shows them as tags on its card; no list of the hub is made of them). **Credits**: `creators`, `publishers`, as a game's and its own, since they can differ from the base game's. **Texts**: `description`. **Rules**: `rules` (links). **Visuals**: `cover`, `boxFront` (the box, front). **Identity** also has `names`. In tabs like a game's, without Related; no kind, order, tagline or related. `names`, `description`, `rules`, `cover` and `boxFront` are translated fields, like a game's. The game it is played with has a read-only **Expansions** tab |
| `creator` | `name`, `photo`, `website`, `bggId`, and a read-only **Games** tab |
| `publisher` | `name`, `website`, `logo`, `bggId`, and a read-only **Games** tab |
| `category` | `name` (English: what the hub's filter and icons go by), `names` (in the other languages, translated), `icon`, `color` (#rrggbb), `description` |

### Editorial

| Type | Fields |
| --- | --- |
| `article` | `title`, `slug`, `excerpt`, `body` (rich text), `cover`, `publishedAt`, `author`, `games` |
| `changelogEntry` | `title`, `date`, `kind` (new game · feature · improvement · fix), `body` (rich text), `image`, `games` |
| `announcement` | `title`, `message`, `tone` (info · success · alert), `startsAt`, `endsAt`, `link` (address and label), `dismissible`, `game` |

The hub reads `announcement` and `changelogEntry` for the signed-in home (`packages/catalog/src/editorial.ts`, `getEditorial`, cached ten minutes like the catalog, nothing when the project does not answer): an announcement is a message bar while now is between `startsAt` and `endsAt` (none set = always), a changelog entry with an `image` is a banner that leads to the first of its `games` that the catalog lists (else to `/about#whats-new`), and the newest entries are the news. Everything is cleaned before it is used (a link must be http(s), a picture must be in the project's image CDN, a `kind` the Studio does not have leaves the entry out). `article` is not read yet: the hub has no page for one. The project holds no announcement and no entry on 2026-11-07, so the home draws none of those zones until the Studio does.

### What was decided, and why

- **Translated field by field, in twelve languages, English the default and the fallback (PLT-104).** English, French, Spanish, German, Simplified Chinese (the variant that reaches the most readers), Japanese, Russian, Arabic, Bengali, Hindi, Portuguese and Korean: `PLATFORM_LANGUAGES` of `@pbgo/studio-kit/constants`, English first. `LANGUAGES` stays the four languages of the games, which their forms map over, until their Studios move to the same system. A game stays **one document**: its slug, figures, credits, categories and references are shared by the languages, and only what is said or shown in a language is translated: for a game its `names`, `tagline`, `description`, link to the rules (`rules`, which replaces `rulesFr`, `rulesEn`, `rulesEs` and `rulesDe`), `logo`, `cover` and `boxFront`; for an expansion its `names`, `description`, `rules`, `cover` and `boxFront`; for a category its `names` (`TRANSLATED_FIELDS` of `schemaTypes/constants.ts` is the list, and `model.test.ts` keeps it the list of the Studio's own fields). The icon and the background are the same in every language. The alternative, one document per language (`@sanity/document-internationalization`), would copy the pictures, credits and references of a game once per language and make a reference like `baseGame` pick a language: it is kept for the editorial types (articles, changelog, announcements), later. The fields are arrays of rows `{ language, value }` made by `sanity-plugin-internationalized-array`, not the fixed keys of the games' `localeString`, which Sanity advises against beyond a few languages (they cost one attribute per language). The reader asks for a language and gets the row of it, else the row of English: nothing filled in a language means English.
- **A description is 240 characters at most, in each language** (`DESCRIPTION_MAX` of `@pbgo/studio-kit/constants`, kept by `checkDescriptions` of `schemaTypes/rules.ts` on the field of the `description` kind, so a game's and an expansion's alike: a `max()` on the type of the value would be handed to the row, an object): it is what the page of a game says under its figures, and its start is what a search result says of it. It names no number of players, which the page shows by itself. The Studio refuses to publish a longer one, once it is deployed with the rule.
- **Nothing is required, English comes first.** A game may have no description yet (its page is then not indexed, `docs/catalog.md`), so a translated field may be empty. What the Studio refuses (`checkTranslations` of `schemaTypes/rules.ts`) is a language that has a text or a picture when English has none: English is what every other language falls back on. It also refuses a language the platform does not have and a language twice. These rules are the field's own validation, which replaces the one the plugin puts on its arrays, so they do what it does.
- **The name stays one plain text.** `name` is English and the reference of the slug, the order, the search and the seed. `names` holds the name in the other languages, and its row of English is read-only and refuses a value (the English name is `name`: a second one would be one more way to disagree); the plugin gives every translated field a row of English, so that one is there but left empty. A category's `name` is what the hub's filter and its icons go by, so it stays English too.
- **English has a row in every translated field, empty if need be.** The plugin of the Studio is set up so that the row of English is always there and cannot be removed (`defaultLanguages: ["en"]`, `allowRemovingDefaultLanguages: false`), the add-a-language buttons are under each field and for the whole document, the language filter shows only some of the languages (English always), and `restoreOrder` is off. What it does on its own, read in its code (version 5.3.9), matters for a published document: it puts a missing row of English back **whenever a document that exists is opened**, which writes a patch, which makes a draft of a published document just by opening it. A row of English that is there, even empty, is not touched. The plugin does it only in the fields the form shows, which for a document in tabs are the fields of the open tab: a document made and published while only its first tab was open would lack the row in the other tabs, and opening it on one of them later would make a draft of it. So whatever writes a translated field gives English its row, and all three writers do: the migration pads every translated field of the published documents and the drafts with an empty one, the seed writes it for the fields Notion has nothing for (`withEnglishRows`), and a new document made in the Studio starts with it (the `initialValue` of each translated field, which `translatedField` of `schemaTypes/translations.ts` sets). The consequence for a developer: **a translated field added to the schema later needs `content:migrate-translations` run again**, or opening any published document would make a draft; the script is idempotent and pads what is missing (the reader is blind to the empty rows). The setting `allowRemovingDefaultLanguages: true` would make the plugin leave existing documents alone, at the price of letting an editor remove the English row (the rule above still stops a translation without English from being published); it is the way out if padding ever becomes a burden.
- **The roles are on the line of the game, not on the person.** A person is a designer of one game, an artist of another, both on a third: `game.creators` holds one line per person with all their roles on that game, and `creator` has no role. The roles are BoardGameGeek's credits, in its words: Designer, Solo designer, Developer, Artist, Graphic designer, Editor, Sculptor, Writer, Insert designer (`CREATOR_ROLES`). Its "Editor" is who edits the text, the rules or the cards, not the publisher, which is a `publisher` apart: that is why the list is `creators` and not `credits`, which would include the publishers. Left out: "Accessory designer" (it credits accessories, not games) and "Honored designs" (awards). A person has one `bggId`, the number in the address of their BoardGameGeek page.
- **The link is stored on the game only.** A creator and a publisher do not list their games: the other side is computed, by the **Games** tab of their form in the Studio (a query on the games, with the roles of a creator on each) and by a reverse query for the hub, `*[_type == "game" && $id in creators[].creator._ref]`. Two stored sides would one day disagree.
- **A document for what is shared.** Creators, publishers and categories are documents of their own, referenced by the games, not names written on each game: a name is written once, a person has a photo and a website, a category an icon and a color.
- **References are strong once published, except `related`.** A strong reference needs the document it points at to be published first, and keeps it from being deleted. The dataset refuses a strong reference to a document that is not published, a draft's included, so the seed writes each reference as the Studio does while the target is a draft: weak (`_weak`) and marked `_strengthenOnPublish`, which makes the Studio turn it strong when the draft is published. That is why the order is: creators, publishers and categories, then the games that have no `baseGame`, then the games that have one, then the expansions, whose `baseGame` is a strong reference too. `related` is the exception: two games are related both ways, so strong references would each wait for the other to be published; it is weak for good (`weak: true` in the schema, and `weak` in the mark the seed writes). The editorial documents point at games strongly.
- **An expansion is a document of its own (PLT-102).** It used to be a `game` with `kind: "expansion"` and a hidden `baseGame`, kept off the hub by a filter on `kind`: one missed filter and it showed up as a game, and its form carried fields it has no use for (categories, complexity, order, related). It is now an `expansion`, which the hub never reads as a game because it reads it in a list of its own (`_type == "expansion"`; the games are another one, `_type == "game"`). Its `baseGame` is required and a strong reference, so a game cannot be deleted from under its expansions. Its pictures are a `cover` and a `boxFront`, and no logo, icon or background (the owner's ruling: those are what the hub draws of a game, and an expansion has no page there). An expansion that plays without its base game is not one: it is a `reimplementation` of it, a game (Flip 7 Vengeance). Hub pages for expansions are out of scope; whoever lists the expansions of a game does it by name or by release date, there is no `order`.
- **No `status` and no `live` flag.** Whether a game is playable and indexable stays in the registry (`packages/games/src/registry.ts`, PLT-83): one switch, in the code that serves the game. `order` is a number that lists the games, lowest first, the live games first and then the games to come, each group by it: the hub's list and its Trending sort follow it, so it is what the owner calls the hotness of the games (a game with none comes after those that have one, then the name); the seed numbers them 10, 20, 30… in the order the hub lists them now, so that one can be slipped between two.
- **`cover` and `boxFront` are two pictures.** The cover is the game's picture on the hub (its card draws it, PLT-114), the box front the front of its box (the games' own Studios call it `boxFront` too). Notion has neither.
- **A rich body, later.** `body` is a list of blocks that holds text only for now; pictures and the like are more kinds of block in that list, added with no migration.

## The seed (`platform/content`)

It imports the Notion Games rows as the hub listed them before PLT-90 (`platform/content/notion/` is its own copy of the reader, `readNotionGames`, then `hubOrder` puts the games in the order the hub used to list them in, the live games of the registry first), so the first numbers of `order` are the hub's old list. Like the games' seeds (`docs/content-pipeline.md`, which holds the guarantees) it writes **drafts only**, in one transaction, fills what is empty and keeps what was edited in the Studio, reads the dataset back to check that running it again does nothing, and never publishes: the owner publishes in the Studio.

| Document | Made from |
| --- | --- |
| `game-<slug>` | each game of the catalog: the name, the slug, the figures, `bggId`, `releaseDate`, the categories, the publishers, the credits, the description and the links to the rules in each language Notion has a column for (rows of `description` and `rules`, English first), `related` (both ways: the row's own links first, then the games that name it). A standalone expansion (Flip 7 Vengeance) is a `reimplementation` of its base game; every other game is a `game` |
| `expansion-<slug>` | each expansion of the source (`NotionExpansion`, `buildExpansions`): the figures, the credits, the description and the links to the rules as a game's (`sharedFields`), and its `baseGame`, written like the other references and left out when the base game is not in the catalog. **None is seeded yet**: the Notion reader only counts the 25 rows that have a `Parent item` (and are not standalone expansions), so `SeedSource.expansions` is empty in a real run; the builder, its ids and its tests are there for the day the reader gives them. An expansion has no art slot (Notion holds no cover or box front); its people and publishers get their documents like a game's |
| `creator-<name>` | each person in a `Designers` or `Artists` cell: the people of `Designers` get the role Designer, those of `Artists` the role Artist, and a person in both cells of one game has both roles on one line. The other seven roles have no source in Notion: they are filled in the Studio |
| `publisher-<name>` | each publisher a game lists, with its website |
| `category-<name>` | each tag a game lists |

- The id of a person, a publisher or a category is made of its name, accents and capitals gone (`creator-emilie-menard`); two names that make one id stop the seed, to be settled in Notion. The expansions of the Notion rows (25 today) are not imported, and neither are `Relation kind`, the fonts, the Creators' `Photo` and `Website` (empty today), the Editors' `Country`, and a game's cover and box, which Notion has not. Notion has columns for French, English, Spanish and German only (`Description FR/EN/ES/DE`, `Rules FR/EN/ES/DE`): the eight other languages are written in the Studio.
- A description and a link to the rules are written as rows of a language (`data/translated.ts`: the key of a row is its language, a row for each language the Notion row fills, in the order of the platform's languages, English first; none for a language it leaves empty, and where a field has no text at all the empty row of English that every translated field has: an empty row is no value, and the merge fills it later). A row is found again by its **language**, not its key, since the Studio makes up the key of a row it adds (`@pbgo/content-kit`, `mergeFill`): the seed fills the empty row of English that a converted published document has, adds a language the document lacks in its place, keeps what was edited and says so, and a second run does nothing. A logo from the art step goes in the row of English of `logo`. When a row has a text in a language and none in English, which the Studio will not let be published, the seed says `no English  <document>: <field> is in <languages> and not in English` and writes it all the same: it guesses nothing. **Run the seed after the migration to translated fields**: before it the dataset holds a plain text where the seed has rows, and every such field is reported as different and kept.
- Only the documents of these types are the seed's (the four above, and `expansion` once the source gives some): a game made by hand in the Studio is reported as "in the dataset but not in the seed" and left alone, and the editorial documents are written in the Studio.
- **Token and run**, from the repo root: `SANITY_API_WRITE_TOKEN_PLATFORM` (an Editor token of the project, in `apps/web/.env.local` only: it is not pushed to Vercel, since the hub reads the public dataset with no token) and `NOTION_API_KEY` (a read-only Notion integration connected to the Games, Editors, Creators and Games Development databases, its secret starts with `ntn_`; `pnpm setup-env` no longer writes it, so it goes in `apps/web/.env.local` by hand, or in the environment). `pnpm --filter @pbgo/platform content:seed --dry-run` says what would change, `--apply` writes the drafts. The options are the ones of the pipeline (`--only`, `--overwrite`, `--verbose`). The project's token is made by hand: `pnpm setup-env` and `pnpm go-live` make the tokens of the games' projects only (see "The write token" below).

### The pictures: a second step

Notion hosts the pictures (the games' logo, icon and background, a publisher's logo) behind links that expire after about an hour, so they are copied in two commands, not one:

1. `pnpm --filter @pbgo/platform content:art --out <folder>` reads the links fresh and downloads the pictures the rows hold into a folder **outside the repo** (say `~/Companies/PBGO/assets/platform`), named after the slot each fills: `game-<slug>-logo.png`, `game-<slug>-icon`, `game-<slug>-background`, `publisher-<name>-logo`. A dry run by default, `--apply` downloads; a file that is already there is left as it is. A picture of a kind the art step does not read (a GIF, an icon file) is reported: convert it and put it in the folder by hand. A cell that holds something that is not a picture (a video, say) is reported as "not a picture" and left out.
2. `pnpm --filter @pbgo/platform content:seed --art-dir <folder>` normalizes the pictures (WebP, an SVG is kept), uploads those the dataset does not hold and places them; `--apply` to write. A picture never carries a credit: the sources are unknown.

## Publishing

The seed never publishes. In the Studio, publish the creators, publishers and categories first, then the games, then the expansions (see the references above): the Studio's Publish makes the references strong. A publication made another way (a script, the Sanity MCP) has to do what the Studio does, or the references stay weak, which the hub reads just as well but which keeps nothing from being deleted: drop `_strengthenOnPublish` from each reference, and `_weak` with it unless the mark says the field is weak for good (`related`), create the published document and delete the draft, all in one transaction. That is how the 170 documents of the first seed were published (2026-10-30, on the owner's word), after a dry run that checks that no strong reference points at a document that would not be published. Once published, a document is public (a public dataset: its published documents can be read with no token). A game that is published shows on the hub within about eleven minutes (Sanity's CDN keeps an answer a minute, the hub's cache ten), and `pnpm catalog:list` says what the project answers right now; a draft is never on the hub, and neither is an expansion: the hub reads `game` documents only.

## Moving the expansions made as games (PLT-102)

Before the `expansion` type an expansion was a `game` of kind `expansion`. The one that was made that way, the draft `drafts.game-courtisans-diplomats-confidants` (2026-11-02), is moved by `pnpm --filter @pbgo/platform content:migrate-expansions` (`platform/content/migrate-expansions.ts`; the plan is `migration/expansions.ts`, the dataset side `migration/http-store.ts`, a plain `fetch` of the project's API with the write token):

- For each draft `game` of kind `expansion` it creates the draft `expansion-<slug>` (for this one `expansion-courtisans-diplomats-confidants`, the id the ticket names) and deletes the game draft, **in one transaction**. The fields the two types share are copied as they stand; the references are written again by the rules above (weak, marked to be made strong on publication); the kind is the only thing left behind. It publishes nothing.
- It is a dry run unless `--apply` is given. The dry run prints exactly what is created, deleted, moved and left behind, with the new document in full; `--apply` writes, then reads the dataset back and says if it is not what the plan said.
- It moves drafts only, and stops without writing anything on what it could not move without losing or guessing: a published game of that kind (or one in a release), a field an expansion has no place for (an `order`, a `logo`… with a value), a draft with no base game, a credit or a publisher that points at nothing, a reference to a document that is not there or of another type, an expansion that exists already, two drafts of one slug. It lists every problem at once.
- Run it when the owner says so, after the Studio with the `expansion` type is deployed (`deploy:studio`, also the owner's word), with the game draft closed in the Studio. Then the owner publishes the expansion in the Studio: its base game, its creators and its publisher are published already. It needs `SANITY_API_WRITE_TOKEN_PLATFORM` like the seed. Neither the merge of PLT-102 nor the seed does any of this.
- Done on 2026-11-02, and nothing is left for it to move (no game has the kind `expansion` any more). What it writes is the shape of its time, a plain text and a link per language: if it ever ran again, `content:migrate-translations` (below) converts its output, and `data/schema.test.ts` runs the two one after the other.

## Translating the fields (PLT-104)

The texts and pictures of the catalog were plain values (a text, a picture, and a link per language for the rules). They are now arrays of rows, one per language (above); `pnpm --filter @pbgo/platform content:migrate-translations` (`platform/content/migrate-translations.ts`; the plan is `migration/translations.ts`, the dataset side `migration/http-store.ts`, a plain `fetch` of the project's API with the write token, and `migration/snapshot-store.ts` reads a file instead) converts what exists:

- A text becomes the row of English of its field, a picture too (kept whole: its asset, its hotspot, its crop), and `rulesFr`, `rulesEn`, `rulesEs` and `rulesDe` become the rows of `rules`, which the four fields leave. Every translated field then gets its row of English, empty if need be (above: why). The `game`, `expansion` and `category` documents are converted **where they stand**, the published ones and the drafts alike, since the hub reads the published ones and an editor works on the drafts: each document is patched in place, no draft is made of a published document and none is published.
- It is a dry run unless `--apply` is given. The dry run says how many documents of each type it looked at, what it does to each field and how many documents get it (`game.description  a text → English  31`), the links to the rules it finds by language, and what it takes away; `--verbose` says it for each document, `--show <id>` prints the patch of one as it would be sent. `--apply` writes, in **one transaction**, then reads the dataset back: every document is as planned and planning again finds nothing.
- It stops without writing anything on what it could not convert without losing or guessing: a field that holds neither rows nor the old value, a row of a language the platform does not have, a language twice, a row with no key, two links for one language (a row of `rules` and the old field of that language that differ), a document in a release (a version), and a document it has no revision of. It lists every problem at once. Each patch names the revision it was planned on (`ifRevisionID`): a document saved in the Studio since it was read makes the whole transaction fail, and nothing is written.
- It is idempotent, and it is what pads the English rows a translated field added later needs (above): run it again and it converts only what is missing.
- `--from <file>` plans against a file of documents instead of the dataset (a JSON array, the answer of the query API, or the `data.ndjson` of an export) with no token, always as a dry run: that is how it is rehearsed on a backup.

The order, for the owner (each step waited for their word, and neither the merge of PLT-104 nor the seed does any of it). Steps 1 to 5 were done on 2026-11-02 and the seed, step 6, on 2026-11-03 (see below):

1. Merge the pull request. The hub reads both shapes, so nothing changes on the site (`pnpm catalog:list` says the same 71 games before and after).
2. Back up the dataset: from `platform/apps/studio`, `pnpm exec sanity dataset export production <folder>/platform-before-plt-104.tar.gz` (needs the owner's login).
3. Close the documents in the Studio, then `pnpm --filter @pbgo/platform deploy:studio`. Until the next step the Studio shows the old values as invalid for the new fields: do not open a game, and never press "Reset value" there.
4. `pnpm --filter @pbgo/platform content:migrate-translations` (dry run), look at it, then `--apply` with `SANITY_API_WRITE_TOKEN_PLATFORM`.
5. Check the hub: `pnpm catalog:list` (the same table), and the site within about eleven minutes. Open a game in the Studio: it must not offer "Publish" (no draft is made by opening it).

**Adding a translated field**: put it in `TRANSLATED_FIELDS` and in the type with `translatedField({ name, title, kind, group })` (the type of its kind, the rules of the translations and the initial value of a new document), give the seed its rows if the source has them (`withEnglishRows` does the empty one), extend `model.test.ts`, then run `content:migrate-translations` (dry run, then apply) so that the published documents get the English row of the new field.

## What reads it

The hub (PLT-90): `readSanityGames` of `@pbgo/catalog` reads the published documents with the public API and one GROQ query that follows the references (`categories[]->name`, `creators[]{ "name": creator->name, roles }`, `publishers[]->{ name, "url": website }`, `related[]->slug.current`), and `docs/catalog.md` says what the hub makes of the answer: the games in `order` (the live games of the registry first), the credits one line per role, pictures from the image CDN, English descriptions. A field of a game maps to the hub's `CatalogGame` one by one: `playersMin` and `playersMax` are `players`, `minAge` is `age`, `description` is `descriptions.en`, `creators` keep their roles. A translated field is read in the language of the query (`$language`, English today: `HUB_LANGUAGE`), else the row of English, else the plain value of the model before PLT-104, so that the same query reads the project before and after the migration to the translated fields (`string(description)` is the old text and nothing for an array, `logo.asset->url` the old picture and nothing for an array); the links to the rules are the rows of `rules` and the four old fields, a row over the field of its language. The hub reads English until the language pass (PLT-32): giving the read a language is the `language` option of `readSanityGames`. The answer has two lists, one per document type, so that an expansion is never read as a game: the `game`s, and the `expansion`s with their `name`, `slug`, `baseGame->slug.current` and their two pictures, `cover` and `boxFront` (translated like a game's; they have no `order`). A `reimplementation` is a game and is listed. The lobby of a game on its page offers the expansions that name it as their base game, by name, each a picture with its name (`docs/catalog.md`): to give a game some, create them in the Studio (an expansion, its base game, a Cover or a Box (front), then publish; the game first, then its expansions, as the seed's order has it). One that lacks a name, a usable slug or a published base game is left out and reported (the logs, `pnpm catalog:list`). A `game` that still has the former kind `expansion` is left out and reported the same way: none is left once the migration above has run. What the hub does not read yet: the tagline, the box front of a game, the names in the other languages, the people's photos, websites and BGG ids, the publishers' logos and BGG ids, the categories' icons, colors and descriptions, and the editorial documents.
