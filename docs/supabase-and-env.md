# Supabase and environment

The environment variables and the secrets file, then the single Supabase project: migrations, realtime, player identity and presence.

## Environment (`apps/web/.env.example`)
- Local values in `apps/web/.env.local`, never committed; on Vercel, on the project `pbgo`. `pnpm setup-env` fills both from `~/.config/pbgo/secrets.env` (outside the repo, `chmod 600`)
- The secrets file holds `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF` (production) and `SUPABASE_PREVIEW_PROJECT_REF` (`pbgo-preview`), all three required: `pnpm setup-env` refuses to run without them. The production project's keys go to the Vercel Production target only; `apps/web/.env.local` and the Vercel Preview and Development targets get the preview project's keys, never production ones. A project that is unreachable, whose keys can't be read, or that still has the one-project-per-game schema (`public.games` without a `game` column) stops the run before anything is written or sent. `--check` only validates the settings (no network). `VERCEL_TOKEN` and `VERCEL_TEAM_ID` go together: without a token Vercel is neither read nor written, with one the team is required (there is no default team, and the Vercel CLI login is never used). `VERCEL_PROJECT_ID` (the project's id, `prj_…`; default `prj_bsk7OjC3wkJrI6ElHFa8bfD71xfs`) is optional: the Vercel project is always found by its id, never by its name, which can change. `ADMIN_SESSION_SECRET` is appended to the file when setup-env generates it (the one of `.env.local` is kept when there is one) and never overwritten there: a new secret signs everyone out
- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` · `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET` (the gamemaster: one account for every game, and the secret, 32 characters at least, that signs its session; all three are needed in every environment, only `next dev` with none of them set is open) · `CRON_SECRET` (32 characters at least: the token Vercel Cron sends to `/api/cron/purge`, the nightly clean-up, as `Authorization: Bearer …`; `pnpm setup-env` generates it like `ADMIN_SESSION_SECRET`, appends it to the secrets file and pushes it to every Vercel target; without a valid one the route answers 401, in development too, and a new value applies from the next deployment) · optional `RESEND_API_KEY` (a Resend API key, `re_…`, apart from the one in the SMTP settings of Supabase Auth: the site's own code sends the link that reopens a deleted account with it, `packages/core/server/mail.ts`; there are two, as for Supabase: `RESEND_API_KEY` is the production one and `RESEND_PREVIEW_API_KEY` the one of previews and local development in the secrets file (one alone serves everywhere); `pnpm setup-env` checks their shape, pushes the first to the Vercel production target and the second to preview and development, and writes the second to `.env.local` as `RESEND_API_KEY`; without any a development server prints the e-mail in its terminal and a deployment cannot send it, `docs/accounts.md`, "Deleting an account") · optional `READY_CHECK_SECONDS` (the time the players have to be ready, their boards loaded, once a table is started, 5 to 600, default 60: a short one is how the deadline is tried by hand) · optional `VERCEL_TOKEN`, `VERCEL_TEAM_ID` (Gamemaster › Audience and Health; `pnpm setup-env` wants both or neither), `NEXT_PUBLIC_SITE_URL`, `DEBUG_GAMES=1` · optional `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST` (PostHog; both or neither, inlined at build, so a change applies from the next deployment; without them analytics, the banner and the "Cookies" links are off) · optional `STEAM_WEB_API_KEY` (the key of Steam's Web API, 32 hexadecimal characters: the switch of the Steam sign-in, `docs/accounts.md`; `pnpm setup-env` reads it from the secrets file or `.env.local`, writes it to `.env.local` and pushes it to every Vercel target; without it the sign-in has no Steam button) · `NOTION_API_KEY` is for the platform's seed alone (`platform/content`: the secret of a read-only Notion integration, read from the environment or from this file, not pushed by `pnpm setup-env`); the site needs no key for its catalog, which it reads from the platform's public Sanity project (`docs/catalog.md`)
- `SANITY_API_WRITE_TOKEN_<SLUG>` per game, slug upper-cased with `-` → `_` (`6-nimmt` → `SANITY_API_WRITE_TOKEN_6_NIMMT`); without it, that game's admin is read-only. `pnpm setup-env` reuses the token it finds (the secrets file, then `.env.local`, then the Vercel project) and creates one, with the `npx sanity login` session, only when none exists; a token still missing is a warning, not a failure

## Supabase
- One project for every game (production), plus `pbgo-preview` for local development and Vercel previews. Schema: `supabase/migrations` (`games`, `tasks`, `feedback`, each with a `game` column = the slug, and the functions `online_player_count()` and `member_count()` of migration `0003_hub_figures.sql`, which count the players connected now and the accounts registered for the figures under the title of the home, then `member_presence`, `games.member_ids`, the functions `touch_member` and `seat_member` and a new `online_player_count()` of migration `0005_online_players.sql`, which makes the players online the members who are connected plus the guests who are at a table, then the results of the games (`0006` to `0009`, below), then the deletion of an account (`0011_account_deletion.sql`: `account_deletions` and the functions that close, reopen and erase an account, below), then the date of birth that a member declared (`member_birthdates` and `set_member_birthdate`, `0012`, below), then the rules of the tables (`0013`) and the settings of a table with the list of the public ones (`games.settings` and `public_tables`, `0014`, below), then the profiles of the members (`profiles` and the functions and triggers that make and keep them, `0015`, below), then the log of a game (`game_log`, `0016`, below); RLS on without policies, only the server reads and writes)
- Migrations: `supabase/migrations/<number>_<name>.sql`, applied by `pnpm setup-env` to `pbgo-preview`, then to production, in file order, each one recorded in `supabase_migrations.schema_migrations` (the Supabase CLI's table: `version` = the number, `name` = the rest). One line per project: up to date, applied …, or failed with the error; a recorded migration never runs again. A migration and its tracking row are one `BEGIN … COMMIT`: a failure leaves neither, stops the run, and production is left alone when preview fails. So a file holds no `BEGIN` / `COMMIT` / `ROLLBACK` and no statement that can't run in a transaction (`CREATE INDEX CONCURRENTLY`, `VACUUM`): apply those by hand and insert their row. `0001` and `0002` are recorded without being run on a project that already holds their effects (baseline; `pbgo-preview` predates the tracking table)
- Setup-env applies the files of the checkout it runs in, production included: run it from an up-to-date `main`, never from a branch with an unmerged migration (`--no-push` stays on preview, which is how to try a migration). A merge and its deployment apply nothing
- Accounts: the same project's Supabase Auth signs the visitors in with Google and Discord, and links Twitch to an account, as a connection that signs nobody in (`docs/accounts.md`: the providers and the redirect URLs to set per project; the hub reads `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`). Steam signs in through the hub's own routes: it needs `SUPABASE_SECRET_KEY` (to make the member) and `STEAM_WEB_API_KEY` (it is the switch: Steam is offered only when it is set, and `pnpm setup-env` pushes it) and the table `external_identities` of migration `0010_external_identities.sql`. Nothing of an account is stored beside Supabase Auth's `auth.users` until the platform schema (PLT-13)
- Realtime is broadcast only: after each write the server sends `update` on `game:<slug>:<code>`, clients refetch their view (`GET /api/<slug>/games/<code>`)
- The player cookie and the player id (a guest, until PLT-13; PLT-112): the cookie `<slug>_player` holds a secret, 32 random bytes in base64url, that no response, row, event or log ever carries. The player id that everything else knows (`games.players[].id`, `host_id`, `seen`, the engine's `PlayerInfo.id`, `meId`, the chat, the statistics, `feedback.player_id`) is the first 128 bits of its SHA-256, in hex (`packages/core/server/player-id.ts`, read through `getPlayerId`): public by design, since a table shows it to whoever reads it, and useless as a credential. A cookie that is not such a secret, a player id or the UUID that the cookie held until PLT-112, reads as no cookie, so a table seated under the old ids cannot be continued by its players. Nothing to configure and no column: `games.players` is jsonb
- Player identity: httpOnly cookie `<slug>_player`
- The ready check (PLT-107, migration `0004_ready_check.sql`): `games.status` is `lobby`, `starting`, `playing` or `over`. A table is `starting` from the host's start (or from the moment it fills) until the last player is ready, that is, has pressed "I'm here" and has a board that is loaded: its `state` is already set up for the seats it has, `ready_at` (jsonb, player id → time, the same shape as `seen`) holds who said it and `ready_deadline` when the check ends. A check that falls through sends the table back to `lobby` with `state` null and the players who were not ready unseated (`docs/routing.md`)
- Personal data in the database: a new column, table, log or bucket that holds some has its row in `docs/legal.md` and its place in the Privacy Policy (`/legal/privacy`), with how long it is kept and how it is deleted: a new table or bucket that holds some joins the nightly clean-up below, with its period next to the other two in `packages/core/lib/retention.ts`. Supabase Auth keeps the IP address of each session and, by default, of each event in `auth.audit_log_entries`, which nothing empties (`docs/legal.md`, Findings)
- Retention (PLT-113): the Privacy Policy promises that tables and feedback do not stay for ever, and a nightly job keeps the promise. A table does not wait for the night when nobody sits at it any more: the last player who leaves it, or a ready check that ends with nobody ready, deletes the row at once (PLT-21, `deleteEmptyTable`, `docs/routing.md`); the job is for the tables that are left sitting, idle, and for the ones where that delete failed. Vercel Cron (`apps/web/vercel.json`, 03:17 UTC) calls `GET /api/cron/purge` with `Authorization: Bearer $CRON_SECRET`, and `purgeExpired` (`packages/core/server/retention.ts`) deletes the tables whose `updated_at` is more than `TABLE_RETENTION_DAYS` (30) days old, in one statement (a move, a join or a change of options writes `updated_at`, presence does not), then the rows of `member_presence` (the last time a member was seen on the site) whose `seen_at` is more than `PRESENCE_RETENTION_DAYS` (1) day old, in one statement, then the friend requests that nobody answered (`friend_requests`, PLT-23, migration 0017) whose `created_at` is more than `FRIEND_REQUEST_RETENTION_DAYS` (30) days old, in one statement (a project where the migration is not applied yet has none, and says nothing), then, for the games that are written down, the state of the tables that are over and were last written more than `FINISHED_STATE_RETENTION_HOURS` (24) hours ago (`drop_finished_states`, 500 tables at a time) and the seats of the unranked games that ended more than `UNRANKED_SEAT_RETENTION_MONTHS` (12) calendar months ago (`fold_old_results`, 1,000 seats at a time, their players' totals having counted them), 20 batches of each at most, then the feedback received more than `FEEDBACK_RETENTION_MONTHS` (12) calendar months ago, 100 at a time and 5,000 a night at most, so that a backlog is finished by the next nights. A closed account whose day has passed (`due_account_deletions`, `ERASE_MAX_ACCOUNTS` = 20 a night, the oldest first) is deleted with what it holds (`eraseAccount`: the feedback sent with its address and their screenshots first, then `erase_account`, whose `p_due_before` makes the database check the day again under a lock, so that a member who reopens their account at that very moment wins). A feedback's screenshot is removed from the `feedback` bucket through the Storage API **before** its row goes: a failure keeps the row and the next night finds it again, and no image is left without a row to find it. The periods are the constants of `packages/core/lib/retention.ts`, which the Privacy Policy page imports, so the text and the job cannot drift. The jobs run on their own: one that fails is in the `errors` of the report, the route answers 500 `PURGE_FAILED` and the run shows as failed in Vercel
  - Why a route and not `pg_cron`: Supabase refuses to delete a Storage object from SQL (the trigger `storage.protect_delete` says "Use the Storage API instead", and a SQL delete would leave the file orphaned in the bucket), so a SQL job would delete the feedback row and keep its screenshot; and the periods and the selection are TypeScript, which the tests cover (`retention.test.ts`: what is old enough, what is kept, a table with a recent move or join is kept, the screenshot goes before its row)
  - Why only production: Vercel Cron runs for the production deployment only, so `pbgo-preview` is not scheduled (its tables and feedback are tests). To purge it, run `pnpm dev` (`.env.local` holds the preview keys and `CRON_SECRET`) and call `curl -H "Authorization: Bearer $(grep '^CRON_SECRET=' apps/web/.env.local | cut -d= -f2-)" http://localhost:3100/api/cron/purge`
  - `?dry=1` deletes nothing and answers what a run would delete. On production: the same call on the site, or Vercel › the project › Settings › Cron Jobs for the log of the last run. The report holds counts and dates, never a name or a code
- Presence: `games.seen` (jsonb, player id → last time the server saw them), written by the RPC `touch_game_player` (migration `0002_presence.sql`) on reads and writes of a table, at most every 15 s per player (`server/presence.ts`, after the response); it touches neither `version` nor `updated_at`. The takeover only counts the members seen in the last 75 s
- Results, ratings and ranks (PLT-13, migrations `0006_game_results.sql` to `0009_ranks.sql`; the personal data they hold is in `docs/legal.md`, "The games played"). When the write of a request turns a table `over` (the action, takeover and debug routes; only that request can, the version check lets one write through, and a debug command that finds the table over again ends nothing), `recordGameResult` (`packages/core/server/results.ts`, from `after()`) reads the public results of the game (`view(state, null).results`), turns them into an outcome for each seat with `outcomesOf`, and calls `record_game_result`, which writes the game (`game_results`) and one row per seat (`game_participants`) in one transaction. A game is told by its table (`game`, the instant the table was created) and the instant it ended: that is unique, so a game written twice is written once, and a rematch on the same table is another game. There is no key to `games`: the table is deleted after 30 days, the result stays. The accounts come from `games.member_ids` (migration `0005`), read inside the function and not sent by the server: an id that is no account is a guest. A game is ranked (`game_results.ranked`) when the table was opened ranked (`createGame(…, { ranked: true })`, `games.ranked`: nothing opens one yet, the matchmaking of PLT-21 will), every seat is a different account and no debug command ended it; a seat counts for a rating (`counted_ranked`) unless the others played for it (`games.taken_over`, written by `markTakenOver` from the takeover route). `games.started_at` (written by `markGameStarted` when the last board is ready, a rematch is agreed or a debug start is made) gives the duration. The speed the table was set to (`games.settings.pace`) is read by `record_game_result` and kept with the game (`game_results.pace`, migration `0022`, `normal` for a table that was given none): the table goes after 30 days and the result stays. The three marks are written by side functions after the response, like `seat_member`, and every function of the recorder never throws: a project where the migrations are not applied yet keeps playing, the games are not written down, and the failure is logged by its code and message (never by its detail, which holds the row).
  - Ratings and rank points (`0007`): `rate_game` runs in the transaction of the recording (`after_game_result`) for a ranked game rated by Elo (`rating_kind`: `coop` when the engine says the table plays together, else `elo`; the registry has no field for it), on the seats that count. The hidden Elo (`ratings.rating`) measures how strong a player is: it starts at 1500, the factor is 32 for the first 20 rated games then 16, each player is compared with each of the others and the mean taken, players who share a place share the points, fewer than two seats that count change nothing, and the ratings are locked in one order. Each game gives or takes the whole number nearest to what it did to the rating, the rank points (`ratings.points`, never below 0; `c_points_per_rating` of `rate_game` is the scale, 1): a win over a stronger player gives more, a win over a weaker one less, a loss to a weaker player takes more. `rating_changes` keeps what each game did to the rating and to the points. A rating is hidden: no function returns it, the pages read places, rank points and what a game gave.
  - Totals and what goes (`0008`): `count_game` adds the game to the `player_stats` of each account at the table (and the games recorded before the migration are counted when it is applied); `fold_old_results` deletes the seats of the unranked games older than a year and `drop_finished_states` the state of a finished table a day after its last write, both run by the nightly job above.
  - Ranks (`0009`, PLT-105): a player reaches a rank by reaching a number of points, earned by playing as above. The steps are the same for every player of every game (`packages/core/lib/ladder.ts`): `DIVISION_POINTS` (100) a division, three divisions a tier, Apprentice, Bronze, Silver, Gold, Platinum, Diamond, Master and Grandmaster, so 2,400 points to Legend, which has no division; the rank does not depend on the number of players nor on their places. `game_standings`, `player_standing` and `player_history` answer places, points and what each game gave; `getStandings`, `getPlayerStats` and `getHistory` of `apps/web/src/lib/game-activity.ts` read them through `core/server/standings.ts`, which reads the points into a rank. The board holds the players who rated at least one game (`board_min_games()`, migration `0019`; it was five games before), the most points first, a tie told apart by the rating (not returned). These are my defaults, not confirmed ones: with 100 points a division and about 16 points for a win over an equal, a community of players of the same strength stays in the low tiers, and the top ones are for those who keep beating stronger players. The two numbers to change are `c_points_per_rating` (migration `0007`) and `DIVISION_POINTS` (`ladder.ts`).
  - Tests of the SQL: `supabase/tests/*.sql` are `DO` blocks to run on `pbgo-preview` with the migrations applied, through the Supabase MCP's `execute_sql` or the SQL editor: each ends with `RAISE EXCEPTION 'RESULT …'`, so that everything it wrote is rolled back and the message is the answer; they never run on production.
- The rules of the tables (PLT-120, migration `0013_table_rules.sql`; its test is `supabase/tests/table_rules.sql`; `docs/routing.md`, "The rules of the tables"): two read functions, no table and no column, both called by the server only (service role). `member_tables(p_user, p_idle)` lists the tables an account sits at that are a lobby, in their ready check or being played and were written within `p_idle` (six hours: `TABLE_IDLE_MS`), the one written last first, each with the seat the account holds there; `busy_seats(p_game, p_code, p_idle)` lists the seats of a table that are in a game somewhere else. Both read `games.member_ids` (migration 0005) and leave out a seat that left (`"left": true` among the `players` of the table). The code does not depend on the migration: a project where it is not applied yet lists no tables, takes nobody to a game and lets every table start. Run the test on `pbgo-preview` as the others (one `DO` block, rolled back).
- The settings of a table and the public tables (PLT-21, migration `0014_table_settings.sql`; its test is `supabase/tests/public_tables.sql`; `docs/routing.md`, "The settings of a table and the public tables"; the personal data it exposes is in `docs/legal.md`): `games.settings`, a `jsonb` object (default `{}`, a check that it is an object), sparse: `visibility` (`public`|`private`), `minRank` (a tier), `language`, `pace` and `seats`, written by the server only (the create route and `POST …/settings`) and read apart from the table (`readTableSettingsOf`, `readTableSettings`), never in `COLUMNS` of `games.ts`; a partial index on the public lobbies; and `public_tables(p_game, p_alive, p_idle, p_limit)`, a read function for the server only (service role) that lists the lobbies with `settings ->> 'visibility' = 'public'` where a seat that did not leave was seen within `p_alive` (three minutes: `PUBLIC_ALIVE_MS`) and that were written within `p_idle` (six hours), the newest first. The code does not depend on the migration: a project where it is not applied yet opens, joins and plays tables as before, lists no public table, opens a table that asks to be public as a private one, and answers 503 `SETTINGS_UNAVAILABLE` to the host's settings route. Run the test on `pbgo-preview` as the others (one `DO` block, rolled back; the migration's statements can be put inside it to try them before applying). **Oré runs `pnpm setup-env` after the merge**, which applies the migration to preview and production.
- The profiles (PLT-39, migration `0015_profiles.sql`, test `supabase/tests/profiles.sql`; `docs/accounts.md`, "Profiles"; the data is in `docs/legal.md`): `profiles` has one row per account (`user_id` → `auth.users`, `on delete cascade`, `nickname`, `tag` 1 to 9999, `avatar_url`, `hide_history`, `created_at`), unique on `(lower(nickname), tag)`. RLS is on with no policy and no right for `anon` or `authenticated`. A trigger on `auth.users` makes the profile with the account (`free_tag`, `make_profile`). A second trigger copies the picture and the choice to hide the games. The migration ends with a backfill. `set_profile(p_user, p_nickname, p_tag)` is the only way to change the nickname and the tag (`'ok'`, `'taken'`, `'invalid'`, `'missing'`). `profile_by_handle(p_nickname, p_tag)` finds a member for the page, and nobody for a closed account or one that never signed in. The migration also makes `scrub_member_from_tables` remove the tag from a deleted account's seats, and `player_history` give each opponent's account (`userId`, never sent to the browser). The code works without the migration: no tags, no links, `/player/…` is a 404, the settings route answers 503. The test is a rolled-back `DO` block. The same block with the migration's statements inside ran on `pbgo-preview` before the migration was applied. Run `pnpm setup-env` after the merge, which applies the migration to preview, then production
- The log of a game (PLT-45, migration `0016_game_log.sql`; the personal data it holds is in `docs/legal.md`, "The table"; its test is `supabase/tests/game_log.sql`): `game_log` has a row for each move that said something (`game`, `code`, `version`: the `games.version` the move produced, and `entries`: the move's `LogEntry`s as `jsonb`), with a key to `games` and `on delete cascade`, RLS on without policy and no right for `anon` or `authenticated`. `updateGame` writes it after the move and before `notify` (best effort: a log that cannot be written leaves the game going, and nothing is logged for a project where the migration is not applied yet), `servedGame` reads the last rows for a player and `viewLog` gives each player their lines. A new game on the table empties it. The migration also replaces `drop_finished_states`, which now drops the log of a table with its state. `docs/engine/01-the-game/12-events-and-the-log.md`
- The date of birth (migration `0012_member_birthdates.sql`, PLT-125; the personal data it holds is in `docs/legal.md`): `member_birthdates` holds one row per member who declared one (`user_id` → `auth.users` with `on delete cascade`, `birthdate`, `set_at`), RLS on without policy and no right for `anon` or `authenticated`: the server (service role) reads it, for the age check of the tables (`core/server/birthdate.ts`, `age-gate.ts`), and writes it only through `set_member_birthdate(p_user, p_birthdate)`, which keeps the date once and answers false for an account that has one (it is never replaced, so a refusal cannot be got round by declaring another date) and refuses a date that makes the member younger than 13 or is in the future (`22023`). `POST /api/hub/birthdate` is the one caller. It is a declaration, never a proof: nothing verifies it. The test is `supabase/tests/member_birthdates.sql` (a `DO` block that rolls back, as above), and the same block with the migration's statements inside it ran on `pbgo-preview` before the migration was applied. A migration that adds a table: Oré runs `pnpm setup-env` after the merge
- Deleting an account (PLT-36, migration `0011_account_deletion.sql`; `docs/accounts.md`, "Deleting an account"; its test is `supabase/tests/account_deletion.sql`): `account_deletions` has a row for each account that is closed (the SHA-256 of the token of the link that reopens it, when it was closed, the day the link stops working and the account is deleted, and the ban it had before). The functions are `close_account` (it inserts the row, bans the account with `auth.users.banned_until` a hundred years ahead and deletes its sessions), `peek_reopen_link`, `reopen_account` (it deletes the row and puts the ban back), `due_account_deletions`, `erase_account` and `scrub_member_from_tables` (a trigger on `auth.users` runs it before any deletion of an account, from the nightly job or the dashboard). All are `security definer`, callable by the service role alone. The migration touches `auth.users` and `auth.sessions` and deletes from `auth.audit_log_entries`, which the migration role (`postgres`) may. It is numbered `0011` because the Steam sign-in's migration, `0010_external_identities.sql` (the table `external_identities`, which goes with the account by its own key), takes `0010` and is applied on `pbgo-preview` already: `setup-env` plans a migration by the version that has no tracking row, so the two may reach `main` in either order, and it stops before anything is applied when two files share a number.
- Online players (migration `0005_online_players.sql`): `member_presence` is the presence of the site, one row per signed-in member, `seen_at` written by the RPC `touch_member` from `POST /api/hub/presence` about every 45 s while a tab is in view (`PresenceBeat`), deleted with the account (`on delete cascade`) and by the nightly clean-up a day after the last beat; `games.member_ids` (jsonb, player id → account id) is written by the RPC `seat_member` (after the response, `server/presence.ts`) when a member opens or joins a table, touches neither `version` nor `updated_at`, and is never read into `PublicGame`. `online_player_count()` counts the members seen on the site or seated in the last two minutes, each once, plus the guests seated at a table in the last two minutes, once per game. The three functions are callable by the service role only, like `touch_game_player`; `member_presence` has RLS on without policy. The code that needs them goes live when the PR merges and the migration when `pnpm setup-env` applies it, so for those few minutes the beat answers 500 and the seat write logs an error, and nothing else breaks: the home keeps the old definition until the migration is there
