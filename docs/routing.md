# Routing of `apps/web`

The rules behind the routes table of the root `CLAUDE.md` (layouts, route wrappers, 404 behaviour, games that are not playable, reserved slugs), then the rate limiting of the mutating routes.

## Routes (`apps/web/src/app`): the rules behind the table

- The hub (`(hub)/layout.tsx`: `/`, `/games`, `/game/<slug>`, `/tables`, `/tournaments`, `/pricing`, `/about`, `/legal` and its pages, `/docs` and its pages), the games (`[game]/layout.tsx`) and the gamemaster (`gamemaster/layout.tsx`: platform look, no game runtime, noindex) have separate root layouts; `global-not-found.tsx` answers any URL that matches no route. Links from the hub to a game are plain `<a>` (full page load).
- A window over a page, the settings (`(hub)/@modal`): the hub's layout draws a parallel slot beside `children` (`default.tsx` draws nothing), and the sections of the settings are intercepted in it, one page for each (`@modal/(.)me/settings/<section>/page.tsx`, which re-exports the page of the address it stands for: Next 16 refuses an interception that has no page at its own address, and the sections are static pages, so a `[section]` would not do). A link of the site to `/me/settings/<section>` draws `SettingsFrame` (`@modal/(.)me/settings/layout.tsx`) over the page the visitor is on, which the `children` slot keeps; the same address typed, followed from an e-mail or reloaded draws it as the page (`me/settings/layout.tsx`), over an empty page. A slot keeps what it showed while the page under it changes, so `SettingsModal` draws nothing once the address is no longer `/me/settings/**`: a catch-all page in the slot, which the docs of Next suggest, makes Next 16 refuse the games' and the gamemaster's pages when it starts (`The following page files do not match any complete route`), since the slot then matches every address of the app. The links of the sidebar replace the history entry, so that closing the window (`router.back()`) returns to the page it opened over. The redirects of `/me/settings` and `/me/settings/profile` are in `next.config.ts` and not in a page that redirects while it is drawn: the window would stay open under the next one. The pages of the profile (`/me`, `/me/games`, `/me/friends`) are in the route group `me/(profile)`, which holds their frame (the header, no tabs), so that the settings are not drawn under it; `me/layout.tsx` keeps the second check of who is signed in and the `noindex` for both.
- Route files are thin wrappers: pages call `@pbgo/core/pages/*` with the game (`gameOf` / `playableGameOf` / `previewableGameOf` from `apps/web/src/lib/game.ts`; the gamemaster pages take any game of the registry through `getGame`), API routes wrap the `@pbgo/core/routes/api/**` handler with `gameRoute()` from `@pbgo/games` and the `@pbgo/core/routes/gamemaster/**` ones with `gamemasterRoute()`. Segment configs (`dynamic`, `revalidate`) stay written out in the app (Next does not read them through a re-export).
- 404: a URL that matches no route (`/x/a/b/c`, `/<slug>/not-a-page`) gets `global-not-found.tsx`, rendered on the server. A page that calls `notFound()` (`gameOf` / `playableGameOf` / `previewableGameOf`: unknown slug, missing table or preview) gets `[game]/not-found.tsx` (`GameNotFound`): the game's own 404 for a slug of the registry, the site's 404 for any other slug. The gamemaster has its own `gamemaster/not-found.tsx` (unknown game or section), and the hub has `(hub)/not-found.tsx` for its own pages (a `/game/<slug>` the catalog does not list): the site's 404 inside the hub layout, whose title template adds the site name. Next 16.4 answers a page's `notFound()` with status 404 and `noindex` but renders the not-found UI on the client (the server HTML has an empty body).
- The `[game]` layout is a root layout, so it must not call `notFound()` itself: nothing sits above it to catch the error and Next answers with its own default 404 page. For an unknown slug it renders a bare `<html>` shell and each page's `gameOf` answers 404. `dynamicParams = false` is not enforced on these dynamic pages.
- A game has no home of its own: the platform is the door of the games (PLT-106). `/<slug>`, for every slug of the registry, shows the page `/game/<slug>` (a `beforeFiles` rewrite in `next.config.ts`, next to the one of the previews), so a link or a bookmark of a game lands on its page on the hub, where a table is opened, joined and started, and the address stays `/<slug>`: there is no redirect. The page is the same at both addresses and says its canonical is `/game/<slug>`; the navbar reads both (`isGamePage` of `site-header.tsx`). A game that is not playable here (no engine, or not live in production) lands there too, and the page says "Coming soon" with a button that does nothing; its table and API answer 404 (`GAME_NOT_FOUND`). The registry's slugs are the only ones redirected: a slug that is not a game is a 404 like any URL that matches no route.
- The front page has two faces. `apps/web/src/proxy.ts` matches `/` and sends a visitor with a session cookie, which the Auth server still knows (`updateSession(request, { confirm: true })`: a dead session has its cookies cleared and sees the public home, or the two pages would send it back and forth until its token expired), to `/home`, the member's home (a 307 with `Cache-Control: private, no-store` that carries the cookies the proxy renewed; not a rewrite, which made the development server's hot reload reload the page for ever); everybody else, a crawler included, gets the static public home with no call to anything. `home` is a reserved slug, `/home` is `noindex` and `Disallow`ed in `robots.txt`, and asked for without a session it redirects to `/` (or, for a member who has not passed the second step of their account, to `/login?next=/home`). See `docs/accounts.md`
- A table that waits for players has no screen in the game: the link of a table, `/<slug>/game/<code>`, is the invitation, and `GamePage` of core reads the table on the server and, when it waits (`status` `lobby`), redirects to the platform's page of that table, `/game/<slug>/<code>` (`tablePath` of `lib/site-url.ts`). A table that was started shows its board (behind the ready screen while it is `starting`, below); a code that does not exist is left to `GameClient`, which says so. A table goes back to the lobby only when its ready check falls through (below), and then `GameClient` sends the board back to the platform's page of the table (a rematch goes from `over` to `playing`, never to the lobby). The gamemaster ignores that rule: it manages every game of the registry, live or not, in production too, and its previews render any game with an engine (`hasEngine`, `getPreviewableGame`), for the signed-in gamemaster only.
- `apps/web/public` holds the platform's own files only: `favicon.ico`, the hub's icon, which the hub layout names in the head of its pages as `/favicon.ico?v=2` (`SITE_ICON`). Google keeps an icon under its address and takes days to weeks to read a replaced file again, so when `favicon.ico` is replaced, bump the `v`, which is a new address for it to read, and ask for the home page to be indexed again in Search Console (URL Inspection); only then, since Google asks for an address that stays. A game's pictures and sounds live in its Sanity project, never in the repo, so a game has no folder there and no `asset()`; `registry.test.ts` fails on any other file in `apps/web/public`, and so does the build (`scripts/check-public.mjs` runs before `next build` in `apps/web`, since a deployment never runs the tests; `pnpm check:public` runs it alone)
- `api`, `legal`, `privacy`, `terms`, `docs`, `games`, `tables`, `tournaments`, `whats-new`, `pricing`, `about`, `ingest`, `gamemaster`, `me`, `signup`, `auth`, `home` and `game` (the hub's page of a game, `/game/<slug>`, which is also the segment of every table's address, `/<slug>/game/<code>`) are routes of `apps/web`, `media`, `catalog`, `cron` and `hub` are the routes under `/api` that sit next to `/api/<slug>`, and `login` / `logout` are routes too (`/login`, `/logout`, and `/gamemaster/login` sits next to `/gamemaster/<slug>`), so none of them can be a game slug. `RESERVED_SLUGS` of `packages/games/src/slug.ts` is the one definition of what a slug and a name can be: the scripts (`pnpm new-game`, `pnpm add-game`), `registry.test.ts` and `slug.test.ts` all read it, and `slug.test.ts` keeps the list equal to the routes of `apps/web`
- `/api/catalog/<slug>/<logo|icon|background>` is not a game's API: it is what is left of the route that served the pictures of every game of the catalog, live or not, when they were files of Notion rows: they are in the image CDN of the platform's Sanity project now, so an old address is sent there (308), and `/api/catalog/<slug>/publisher-<n>` and `/api/catalog/<slug>/bgg` serve the icon of a publisher's website and BoardGameGeek's, through `pictureRoute()` of `@pbgo/catalog/route`, which its route file exports as `GET` the way `/api/media` exports `mediaRoute(...)`. The static segment `catalog` wins over `[game]`, so it never meets `/api/<slug>/games/<code>`. It is a GET that starts nothing a visitor can choose, so it has no `rateLimit` rule: the slot and the slug are checked against the catalog before anything is read, and a `v` that is not the current version of a publisher's website (or of BoardGameGeek's) is redirected before anything is downloaded (`docs/catalog.md`)
- `/api/cron/purge` is not a game's API either: it is the nightly clean-up that Vercel Cron calls (`apps/web/vercel.json`, 03:17 UTC), a GET with `Authorization: Bearer $CRON_SECRET` (`cronAuthorized` of `@pbgo/core/server/cron`, which refuses a secret that is missing or shorter than 32 characters, so a deployment that forgot it answers 401, in development too). Its route file exports the `GET` of `@pbgo/core/routes/api/cron/purge/route` the way `/api/media` does, with the segment configs written out in the app. The static segment `cron` wins over `[game]`. It has no `rateLimit` rule: the secret is long and random, and a run only deletes what is already past its retention, so asking twice does nothing more than asking once. What it deletes and why it is a route and not `pg_cron`: `docs/supabase-and-env.md` (Retention)
- `/api/hub/figures` and `/api/hub/presence` are not a game's API either: global routes of the hub, next to `/api/cron`, and the static segment `hub` wins over `[game]` (so `hub` is a reserved slug). `GET /api/hub/figures` is a route file of `apps/web` alone (`getHubFigures` is the app's) and answers the two figures of the home that come from the database, `{ online, members }`, each a count or `null` for one that could not be counted, with `Cache-Control: public, s-maxage=15, stale-while-revalidate=30`; `LiveStats` asks for it when the home opens and every half minute. `POST /api/hub/presence` exports the `POST` of `@pbgo/core/routes/api/hub/presence/route` and is the beat of a signed-in member who has the site open (`PresenceBeat`, about every 45 s while a tab is in view): 401 `NOT_SIGNED_IN` for a visitor who is not signed in, nothing written for the demo account of development, 500 when the database cannot write it (the browser then waits twice as long, up to five minutes)
- `/api/hub/birthdate` is a global route of the hub too (PLT-125), beside the other two: it exports the `POST` of `@pbgo/core/routes/api/hub/birthdate/route` (`force-dynamic`, it reads the session and writes the database). A signed-in member declares their date of birth (`{ "birthdate": "YYYY-MM-DD" }`) for the games and expansions that ask for an age: 401 `NOT_SIGNED_IN` for a visitor who is not signed in, 400 `BIRTHDATE_INVALID` (not a day that exists, in the future or more than 120 years back) or `BIRTHDATE_UNDER_MINIMUM` (younger than 13), 409 `BIRTHDATE_LOCKED` when the account has a date already (it is declared once and never replaced), 200 `{ "saved": true }`, and nothing written for the demo account of development. The four routes of a game that seat somebody or change what a table plays are the other half of the age check: core exports them as `postGame`, `postJoin`, `postOptions` and `postStart`, which take the age rules (`AgeRulesSource`), and the app's files make them with `ageRulesOf` of `@pbgo/catalog/server` (`gameRoute(core.postGame(ageRulesOf))`). `docs/accounts.md`, "The age check"
- `/api/hub/unlink-external` is a global route of the hub too (PLT-133): a `POST` in `apps/web` itself, like the Steam routes (`force-dynamic`: it reads the session and writes the database). A signed-in member takes the account they linked at an external provider off theirs (`{ "provider": "steam" }`). The request must carry this site's `Origin` (403 `FORBIDDEN`), 401 `NOT_SIGNED_IN` for a visitor who is not signed in, 400 `INVALID_REQUEST` for a body that is not that or a provider that is not an external one, 409 `LAST_WAY_IN` when no other way in is left, 500 `UNLINK_FAILED` (the log says the step it stopped at), 200 `{ "unlinked": true }`, and nothing written for the demo account of development.
- `/game/<slug>` is the hub's page of a game (`(hub)/game/[slug]/page.tsx`), for every game of the catalog, live or to come, and `/game/<slug>/<code>` (`(hub)/game/[slug]/[code]/page.tsx`) the same page for a table that waits for players, with that table picked (both are `GamePageView`, `apps/web/src/components/game-page-view.tsx`). The table of a game has three segments too (`/<slug>/game/<code>`), and the static `game` wins over `[game]` at the first segment, so the two never meet (`game` is a reserved slug). The slug is looked up in the catalog (`getGamePage`, `apps/web/src/lib/game-page.ts`): a slug it does not list answers 404 with the hub's own `not-found.tsx`, and `/game` alone is no page. The page ends with the games the catalog finds similar to it (`related` of its entry, nine at most), under the title "Similar games", drawn as the home's cards in one row that scrolls sideways. `robots.txt` has no rule for `/game/<slug>` (`/*/game/` needs a segment before `game`), so the page says itself whether it may be indexed (its `robots` meta), and the sitemap lists the ones that may (`docs/catalog.md`); the page of a table (`/game/<slug>/<code>`) is private to those who have its link: `noindex` and `Disallow: /game/*/`, with the game's picture and name in its metadata so that the link, pasted in a chat, unfurls (the crawler follows the redirect from `/<slug>/game/<code>`)
- Tables on the hub (PLT-106): the page reads the visitor's table in `public.games` with the per-game player cookie (`<slug>_player`: `httpOnly`, `sameSite=lax`, `path=/`, no domain, so the hub's page and `/api/<slug>/...` both get it; only a route handler can write it, so the create and join routes set it and a page only reads it: `getPlayerId`). `findPlayerGame` returns the table that waits or is played and was written last, within six hours (`TABLE_IDLE_MS`: a table the visitor forgot is not theirs any more). The page creates, joins, leaves, sets the options of and starts a table with the routes that exist (`POST /api/<slug>/games`, `[code]/join|leave|options|start`), which take the name and the picture of a signed-in account on the server and the nickname of a guest from the request (`resolveSeat`, which also says which account it is: `seatMember` records it apart from the seat, for the players online). `TableSync` keeps a table that waits alive (Realtime and a poll) and takes whoever sits at it to the board once it is started; `enterBoard` (`apps/web/src/lib/table-door.ts`) is the one place that does
- The ready check (PLT-107): the host's `POST …/start` sets the game up and puts the table in the status `starting`, for `READY_WINDOW_MS` (a minute; `READY_CHECK_SECONDS` of the environment changes it) with `ready_at` empty; everybody seated comes to the board, `/<slug>/game/<code>`, where `BoardEntry` of core mounts the game's board behind the platform's start screen (`StartScreen`: black and white, built from `@pbgo/ui/platform`, one collective bar and a row for each player; `held`, `onLoaded` and `onProgress` of `BoardProps`: the board loads its pictures, says how far it is and holds its opening). A player is ready when their board is loaded: it sends `POST …/ready` by itself, no click, and the boards tell each other how far they are on a presence channel (`loading:<slug>:<code>`, `openLoading` of `lib/realtime.ts`, nothing stored: it only paints the bar). The last board to be ready makes the table `playing` and `game_started` is sent; the screen goes for each player when the game has begun and their board is loaded, and the boards play their opening from then. A player who comes back to a game under way gets the same screen with their own bar only, no barrier and no request: it goes as soon as their board is loaded. Nothing runs on a timer: a check whose time is up is ended by the first request that looks at the table (`settleReadyCheck`: the read route every board polls, `GamePage`, `ready`, `start`), which unseats whoever was not ready and sends the table back to the lobby for the others (`expirePatch`, `server/ready.ts`); PLT-13's backstop will end the ones nobody looks at. `leave` ends a check for everybody too, and `join` and `options` are refused while it lasts (`GAME_IN_PROGRESS`)
- The tabs of the hub's navbar (`SITE_TABS` in `apps/web/src/components/site-header.tsx`) each lead to a page of the hub. The hub's layout mounts the bar once (`SiteHeader`, a client component), and it reads the address to know what is current (`currentOf`: the logo on `/`, a tab on its page, Games on `/game/<slug>`, the bar and no tab on `/docs` and the pages of an account, and nothing, so no bar, on `/login` and `/signup`, which are a page of their own (`AuthShell`: the logo alone, the brand's lettering behind the card, a quiet foot), on the pages of a doc, the legal pages and the 404); the pages do not draw it. Mounted once, it stays from one page to the next, which is what lets the fill behind the current item glide (`docs/design/02-foundations/07-motion.md`). The logo is the home, `/`, and it is the current button there (the front page is no tab); Games is `/games` (a game's page, `/game/<slug>`, is Games too), the list of every game of the catalog, indexable and in the sitemap; Tables, Tournaments, Pricing and About are `/tables`, `/tournaments`, `/pricing` and `/about`, pages with a title and an empty state for now (About also holds a "What's new" section, `/about#whats-new`; `/whats-new`, the page it used to be, is a permanent redirect to it in `next.config.ts`, and stays a reserved slug) (`ComingSoonPage`: the title, what is to come, the footer), `noindex` and out of the sitemap. The legal pages are a folder of their own: `/legal/cookies` (the Cookie Policy), `/legal/privacy` and `/legal/terms`, which the footer links to (the last two are drafts for the owner, or a lawyer, to validate: `noindex`, with the stub's "being written" line until they say so, `docs/legal.md`), and `/legal`, the notice, which nothing links to for now (the owner is not sure the site needs one); `/privacy` and `/terms`, where the last two used to be, are permanent redirects in `next.config.ts` and stay reserved slugs. The sections of the home end with a "See all" that leads to the page of their tab. A new tab is a route folder in `(hub)`, an entry in `SITE_TABS` and a reserved slug (`slug.test.ts` fails without it)
- The docs (`(hub)/docs/`): `/docs` is the way into them (`page.tsx`: a card for each doc, read from the `docs/` folder by `@pbgo/docs/server`) and a page of a doc is `[section]/[[...page]]/page.tsx` (`/docs/<doc>`, `/docs/<doc>/<page>`, `/docs/<doc>/<group>/<page>`) inside the shell of `[section]/layout.tsx`: the side menu stuck to the left edge of the window (`DocsHeader`, the logo that leads back to `/docs` and the name of the doc; `DocsSidebar`, a search of the titles and the sections that fold, the first level open from the start, a menu that stops at the pages and scrolls to the current one) and, at the foot of a page, the page before and the page after it (`DocsPager`, `neighboursOf` of `@pbgo/docs`). The pages are those of the build: `generateStaticParams` lists every file that `@pbgo/docs` found and `dynamicParams` is off, so any other address is a plain 404, and in development a file that is added needs a restart of `pnpm dev` to have its page (the menu shows it at once). A word of an address is a name from the disk (`isDocName`), never a path. The layout of `docs/` draws nothing and makes every page `noindex`. See `docs/packages.md` (`@pbgo/docs`)
- The accounts: `/login`, `/signup`, `/me/*` (per request: they read the session), `/auth/callback`, `/auth/confirm` (the link of the sign-up's confirmation e-mail: a `GET` that spends `?token_hash=…&type=email` on the server and always answers with a redirect, `Cache-Control: no-store`, to `next` or to `/signup?error=confirm`; it has no `rateLimit` rule: Supabase Auth limits verifications by IP address, and from the server that is the host's, so the limit is shared by every visitor who follows a link; the code typed in the page is verified from the visitor's own browser), `/logout` and the development-only `/auth/demo`. `apps/web/src/proxy.ts` (Next 16's `proxy`) matches `/me/:path*`, `/login` and `/signup` only: it renews the session and sends a visitor who is not signed in to `/login?next=…`, so no public page and no game is touched by it. Their robots rules are in `robots.ts`. See `docs/accounts.md`

## Rate limiting
- Every mutating game route (create, join, leave, options, start, ready, action, replay, takeover) and `POST /api/<slug>/feedback` start with `await rateLimit(game.slug, request, "<rule>")` (`server/rate-limit.ts`). Limits live in `RATE_LIMITS` (`server/rate-limiter.ts`): per player cookie when present, else per IP (create: always per IP), never per table, plus a per-IP ceiling across routes. `POST /api/hub/presence` belongs to no game: it starts with `await rateLimit(null, request, "presence")`, 30 a minute per IP (a tab beats about once every 45 s), and so do `POST /api/hub/birthdate` with `"birthdate"`, 20 in ten minutes per IP, and `POST /api/hub/unlink-external` with `"externalUnlink"`, 10 in ten minutes per IP. Over the limit: 429 `RATE_LIMITED` + `Retry-After`. The chat route has its own per-player token bucket
- `POST /gamemaster/api/login` belongs to no game: it starts with `await rateLimit(null, request, "adminLogin")`, 5 attempts per 10 minutes per IP, counted before the credentials are checked (the right password is refused too once the limit is reached)
- Counters are in memory, per function instance; to share them, implement `RateLimitStore` and call `setRateLimitStore()`, or let the Vercel Firewall count (a rate-limit rule on the paths that matter, the admin login first: `docs/bots-and-abuse.md`). A new mutating route of a game (`ROUTES`) must call `rateLimit` too
