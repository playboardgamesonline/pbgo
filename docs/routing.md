# Routing of `apps/web`

The rules behind the routes table of the root `CLAUDE.md` (layouts, route wrappers, 404 behaviour, games that are not playable, reserved slugs), then the rate limiting of the mutating routes.

## Routes (`apps/web/src/app`): the rules behind the table

- The hub (`(hub)/layout.tsx`: `/`, `/games`, `/game/<slug>`, `/tables`, `/tournaments`, `/pricing` (hidden for now: it answers 404, `PRICING_OPEN`), `/about`, `/legal` and its pages, `/docs` and its pages), the games (`[game]/layout.tsx`) and the gamemaster (`gamemaster/layout.tsx`: platform look, no game runtime, noindex) have separate root layouts; `global-not-found.tsx` answers any URL that matches no route. Links from the hub to a game are plain `<a>` (full page load).
- A window over a page, the settings (`(hub)/@modal`): the hub's layout draws a parallel slot beside `children` (`default.tsx` draws nothing), and the sections of the settings are intercepted in it, one page for each (`@modal/(.)me/settings/<section>/page.tsx`, which re-exports the page of the address it stands for: Next 16 refuses an interception that has no page at its own address, and the sections are static pages, so a `[section]` would not do). A link of the site to `/me/settings/<section>` draws `SettingsFrame` (`@modal/(.)me/settings/layout.tsx`) over the page the visitor is on, which the `children` slot keeps; the same address typed, followed from an e-mail or reloaded draws it as the page (`me/settings/layout.tsx`), over an empty page. A slot keeps what it showed while the page under it changes, so `SettingsModal` draws nothing once the address is no longer `/me/settings/**`: a catch-all page in the slot, which the docs of Next suggest, makes Next 16 refuse the games' and the gamemaster's pages when it starts (`The following page files do not match any complete route`), since the slot then matches every address of the app. The links of the sidebar replace the history entry, so that closing the window (`router.back()`) returns to the page it opened over. The redirects of `/me/settings` and `/me/settings/profile` are in `next.config.ts` and not in a page that redirects while it is drawn: the window would stay open under the next one. The pages of the profile (`/me`, `/me/games`, `/me/friends`) are in the route group `me/(profile)`, which holds their frame (the header, no tabs), so that the settings are not drawn under it; `me/layout.tsx` keeps the second check of who is signed in and the `noindex` for both.
  - Over a game's screen (`[game]/@modal`): a game's pages have a root layout of their own, which a soft navigation cannot cross, so the settings are drawn over the board by that layout, which has its own `@modal` slot (`default.tsx` draws nothing; `@modal/(...)settings/[section]/page.tsx` is one page that picks the section among the same pages as the settings' own, and `@modal/(...)settings/layout.tsx` draws `SettingsFrame`). It is one dynamic page and not a page for each section as the hub's window has: Next 16.4 reads an interception route as dynamic by its intercepted address only, so a static address (`(...)settings/account`) under a dynamic route (`[game]`) is matched as a static path in production, answers 404 there (development does not show it) and is prerendered by the build with a game it does not know (`Could not resolve param value for segment: game`). The address they have there is an alias, `/settings/<section>` (`GAME_SETTINGS_PATH` of `apps/web/src/lib/settings-paths.ts`), and not `/me/settings/<section>`: the hub's interception is made for the intercepting route `/`, so its rule matches the address of every page the link is followed from (`Next-Url`, `/.*`), a board's included, and it is first in the list of rewrites, so a link to `/me/settings/**` from a board is answered by the hub's window and, the root layouts being two, becomes a full navigation that takes the visitor off the board (a games' interception at the same address is never reached); and the games' rule is for the intercepting route `/[game]`, which matches any first segment, so it would answer the hub's pages if it were first. Two addresses make two rules that cannot meet. "Settings" in the account menu of a game's screen (`AccountMenu` with `game`) leads to the alias, and the sidebar of the window keeps to the address it was opened at (`SettingsNav`), so a window opened over a board never leaves it. The alias is typed, followed with no script or reloaded as `(hub)/settings/[section]/page.tsx`, which leads to the settings' own page (the page an interception needs at its address); it is a reserved slug, `Disallow`ed in `robots.txt`, and `proxy.ts` renews the session for it like for `/me`. A new section of the settings is one more entry of `SECTIONS` in that page too.
- Route files are thin wrappers: pages call `@pbgo/core/pages/*` with the game (`gameOf` / `playableGameOf` / `previewableGameOf` from `apps/web/src/lib/game.ts`; the gamemaster pages take any game of the registry through `getGame`), API routes wrap the `@pbgo/core/routes/api/**` handler with `gameRoute()` from `@pbgo/games` and the `@pbgo/core/routes/gamemaster/**` ones with `gamemasterRoute()`. Segment configs (`dynamic`, `revalidate`) stay written out in the app (Next does not read them through a re-export).
- 404: a URL that matches no route (`/x/a/b/c`, `/<slug>/not-a-page`) gets `global-not-found.tsx`, rendered on the server. A page that calls `notFound()` (`gameOf` / `playableGameOf` / `previewableGameOf`: unknown slug, missing table or preview) gets `[game]/not-found.tsx` (`GameNotFound`): the game's own 404 for a slug of the registry, the site's 404 for any other slug. The gamemaster has its own `gamemaster/not-found.tsx` (unknown game or section), and the hub has `(hub)/not-found.tsx` for its own pages (a `/game/<slug>` the catalog does not list): the site's 404 inside the hub layout, whose title template adds the site name. Next 16.4 answers a page's `notFound()` with status 404 and `noindex` but renders the not-found UI on the client (the server HTML has an empty body).
- The `[game]` layout is a root layout, so it must not call `notFound()` itself: nothing sits above it to catch the error and Next answers with its own default 404 page. For an unknown slug it renders a bare `<html>` shell and each page's `gameOf` answers 404. `dynamicParams = false` is not enforced on these dynamic pages.
- A game has no home of its own: the platform is the door of the games (PLT-106). `/<slug>`, for every slug of the registry, shows the page `/game/<slug>` (a `beforeFiles` rewrite in `next.config.ts`, next to the one of the previews), so a link or a bookmark of a game lands on its page on the hub, where a table is opened, joined and started, and the address stays `/<slug>`: there is no redirect. The page is the same at both addresses and says its canonical is `/game/<slug>`; the navbar reads both (`isGamePage` of `site-header.tsx`). A game that is not playable here (no engine, or not live in production) lands there too, and the page says "Coming soon" with a button that does nothing; its table and API answer 404 (`GAME_NOT_FOUND`). The registry's slugs are the only ones redirected: a slug that is not a game is a 404 like any URL that matches no route.
- The front page has two faces. `apps/web/src/proxy.ts` matches `/` and sends a visitor with a session cookie, which the Auth server still knows (`updateSession(request, { confirm: true })`: a dead session has its cookies cleared and sees the public home, or the two pages would send it back and forth until its token expired), to `/home`, the member's home (a 307 with `Cache-Control: private, no-store` that carries the cookies the proxy renewed; not a rewrite, which made the development server's hot reload reload the page for ever); everybody else, a crawler included, gets the static public home with no call to anything. `home` is a reserved slug, `/home` is `noindex` and `Disallow`ed in `robots.txt`, and asked for without a session it redirects to `/` (or, for a member who has not passed the second step of their account, to `/login?next=/home`). See `docs/accounts.md`
- A table that waits for players has no screen in the game: the link of a table, `/<slug>/game/<code>`, is the invitation, and `GamePage` of core reads the table on the server and, when it waits (`status` `lobby`), redirects to the platform's page of that table, `/game/<slug>/<code>` (`tablePath` of `lib/site-url.ts`). A table that was started shows its board (behind the ready screen while it is `starting`, below); a code that does not exist is left to `GameClient`, which says so. A table goes back to the lobby only when its ready check falls through (below), and then `GameClient` sends the board back to the platform's page of the table (a rematch goes from `over` to `playing`, never to the lobby). The gamemaster ignores that rule: it manages every game of the registry, live or not, in production too, and its previews render any game with an engine (`hasEngine`, `getPreviewableGame`), for the signed-in gamemaster only.
- `apps/web/public` holds the platform's own files only: `favicon.ico`, the hub's icon, which the hub layout names in the head of its pages as `/favicon.ico?v=2` (`SITE_ICON`). Google keeps an icon under its address and takes days to weeks to read a replaced file again, so when `favicon.ico` is replaced, bump the `v`, which is a new address for it to read, and ask for the home page to be indexed again in Search Console (URL Inspection); only then, since Google asks for an address that stays. A game's pictures and sounds live in its Sanity project, never in the repo, so a game has no folder there and no `asset()`; `registry.test.ts` fails on any other file in `apps/web/public`, and so does the build (`scripts/check-public.mjs` runs before `next build` in `apps/web`, since a deployment never runs the tests; `pnpm check:public` runs it alone)
- `api`, `legal`, `privacy`, `terms`, `docs`, `games`, `tables`, `tournaments`, `whats-new`, `pricing`, `about`, `ingest`, `gamemaster`, `me`, `signup`, `auth`, `home`, `player` (the public profiles, `/player/<nickname>-<tag>`) and `game` (the hub's page of a game, `/game/<slug>`, which is also the segment of every table's address, `/<slug>/game/<code>`) are routes of `apps/web`, `media`, `catalog`, `cron` and `hub` are the routes under `/api` that sit next to `/api/<slug>`, and `login` / `logout` are routes too (`/login`, `/logout`, and `/gamemaster/login` sits next to `/gamemaster/<slug>`), so none of them can be a game slug. `RESERVED_SLUGS` of `packages/games/src/slug.ts` is the one definition of what a slug and a name can be: the scripts (`pnpm new-game`, `pnpm add-game`), `registry.test.ts` and `slug.test.ts` all read it, and `slug.test.ts` keeps the list equal to the routes of `apps/web`
- `/api/catalog/<slug>/<logo|icon|background>` is not a game's API: it is what is left of the route that served the pictures of every game of the catalog, live or not, when they were files of Notion rows: they are in the image CDN of the platform's Sanity project now, so an old address is sent there (308), and `/api/catalog/<slug>/publisher-<n>` and `/api/catalog/<slug>/bgg` serve the icon of a publisher's website and BoardGameGeek's, through `pictureRoute()` of `@pbgo/catalog/route`, which its route file exports as `GET` the way `/api/media` exports `mediaRoute(...)`. The static segment `catalog` wins over `[game]`, so it never meets `/api/<slug>/games/<code>`. It is a GET that starts nothing a visitor can choose, so it has no `rateLimit` rule: the slot and the slug are checked against the catalog before anything is read, and a `v` that is not the current version of a publisher's website (or of BoardGameGeek's) is redirected before anything is downloaded (`docs/catalog.md`)
- `/api/cron/purge` is not a game's API either: it is the nightly clean-up that Vercel Cron calls (`apps/web/vercel.json`, 03:17 UTC), a GET with `Authorization: Bearer $CRON_SECRET` (`cronAuthorized` of `@pbgo/core/server/cron`, which refuses a secret that is missing or shorter than 32 characters, so a deployment that forgot it answers 401, in development too). Its route file exports the `GET` of `@pbgo/core/routes/api/cron/purge/route` the way `/api/media` does, with the segment configs written out in the app. The static segment `cron` wins over `[game]`. It has no `rateLimit` rule: the secret is long and random, and a run only deletes what is already past its retention, so asking twice does nothing more than asking once. What it deletes and why it is a route and not `pg_cron`: `docs/supabase-and-env.md` (Retention)
- `POST /api/hub/account/deletion` is the deletion of an account (PLT-36, `docs/accounts.md`, "Deleting an account"), a global route of the hub like the two below it. Its route file calls `deletionRoute(deletionMail)` of `@pbgo/core/routes/api/hub/account/deletion/route`, which is given the e-mail's words by the app (`apps/web/src/lib/deletion-mail.ts`: the site's name, contact and sender). The body says what is asked (`intent`): `close` (the signed-in member deletes their account: the e-mail with the link that reopens it goes first, then the account is closed and the cookies of the browser go), `reopen` and `now` (the link's account and token: no session, since a closed account has none, the token is the proof). It starts with `rateLimit(null, request, "accountDeletion")` (ten an hour per IP); `close`, which acts on the strength of the cookie, refuses a request whose `Origin` is another site (403 `CROSS_ORIGIN`). Its codes are told in `DELETION_MESSAGES` of `@pbgo/accounts`. The page the link opens is `/auth/reopen-account` (`(hub)/auth/reopen-account/page.tsx`: a page of the hub's layout under the `auth` segment that holds the route handlers `callback`, `confirm` and `demo`)
- `/api/hub/figures` and `/api/hub/presence` are not a game's API either: global routes of the hub, next to `/api/cron`, and the static segment `hub` wins over `[game]` (so `hub` is a reserved slug). `GET /api/hub/figures` is a route file of `apps/web` alone (`getHubFigures` is the app's) and answers the two figures of the home that come from the database, `{ online, members }`, each a count or `null` for one that could not be counted, with `Cache-Control: public, s-maxage=15, stale-while-revalidate=30`; `LiveStats` asks for it when the home opens and every half minute. `POST /api/hub/presence` exports the `POST` of `@pbgo/core/routes/api/hub/presence/route` and is the beat of a signed-in member who has the site open (`PresenceBeat`, about every 45 s while a tab is in view): 401 `NOT_SIGNED_IN` for a visitor who is not signed in, nothing written for the demo account of development, 500 when the database cannot write it (the browser then waits twice as long, up to five minutes)
- `/api/hub/birthdate` is a global route of the hub too (PLT-125), beside the other two: it exports the `POST` of `@pbgo/core/routes/api/hub/birthdate/route` (`force-dynamic`, it reads the session and writes the database). A signed-in member declares their date of birth (`{ "birthdate": "YYYY-MM-DD" }`) for the games and expansions that ask for an age: 401 `NOT_SIGNED_IN` for a visitor who is not signed in, 400 `BIRTHDATE_INVALID` (not a day that exists, in the future or more than 120 years back) or `BIRTHDATE_UNDER_MINIMUM` (younger than 13), 409 `BIRTHDATE_LOCKED` when the account has a date already (it is declared once and never replaced), 200 `{ "saved": true }`, and nothing written for the demo account of development. The four routes of a game that seat somebody or change what a table plays are the other half of the age check: core exports them as `postGame`, `postJoin`, `postOptions` and `postStart`, which take the age rules (`AgeRulesSource`), and the app's files make them with `ageRulesOf` of `@pbgo/catalog/server` (`gameRoute(core.postGame(ageRulesOf))`). `docs/accounts.md`, "The age check"
- `/api/hub/cities` is a global route of the hub too (PLT-139): the search of a city for a profile, a `GET` that exports `GET` of `@pbgo/core/routes/api/hub/cities/route` (`force-dynamic`), which asks Geoapify through `server/geoapify.ts` with `GEOAPIFY_API_KEY` (the key is the switch: without it the search is unavailable and the Edit profile window has no City field). It has the rate limit `cities` (150 a minute per IP) and a short `Cache-Control` (it needs no session).
- `/api/hub/profile` is a global route of the hub too (PLT-39). It exports the `GET` and the `POST` of `@pbgo/core/routes/api/hub/profile/route` (`force-dynamic`). `GET` gives the signed-in member's own handle, `{ "nickname": "Alex", "tag": 42 }`: 401 `NOT_SIGNED_IN`, `"tag": null` where the database has no profile or cannot be read, `DEMO_TAG` for the demo account, 120 a minute per IP (`profileRead`). `POST` changes the nickname and the tag: 403 `CROSS_ORIGIN` for a request from another site, 401, 400 `PROFILE_INVALID`, 409 `PROFILE_TAKEN` (case of the nickname ignored, a member's own pair is never taken from them), 503 `PROFILE_UNAVAILABLE` where migration 0015 is not applied, 200 `{ "saved": true, "nickname": "Alex", "tag": 42 }`. The demo account writes nothing. `docs/accounts.md`, "Profiles"
- `/player/<nickname>-<tag>` is a member's public profile (PLT-39, `(hub)/player/[handle]/page.tsx`). It is read per request and is for anybody. The session is read only to know whether the visitor is the member. `parseProfileSegment` reads the last segment from its end (four digits, 0001 to 9999). What no profile can be is the hub's 404 with no database call. `profile_by_handle` finds the member (case ignored) and nobody for a closed account or one that never signed in. The proxy does not match it. It is `noindex` and disallowed in robots.txt. `?from=` (`seat`, `leaderboard`, `history`, `account`) is for analytics only. A new nickname or tag, or a deleted account, makes the old address a 404. `docs/accounts.md`, "Profiles"
- `/api/hub/friends` and `/api/hub/friends/<action>` are global routes of the hub too (PLT-23, `docs/accounts.md`, "Friends"). The app's files are one line each (`apps/web/src/app/api/hub/friends/route.ts`, and `<request|accept|decline|cancel|remove|block|unblock>/route.ts`), `force-dynamic`, and export the `GET` of `getFriends(friendsDeps)` and the `POST` of `postFriend("<action>")` of `@pbgo/core/routes/api/hub/friends/route`; `friendsDeps` (`apps/web/src/lib/friends-deps.ts`) gives the names of the games, which core cannot read (the catalog's). **`GET /api/hub/friends`** answers the whole social state of the signed-in member in one call: `{ friends: [{ nickname, tag, avatarUrl, online, game: { slug, name } | null, phase: "lobby" | "playing" | null }], incoming: […], outgoing: […], blocked: […] }`, never an account's id and never a table's code. 401 `NOT_SIGNED_IN`, the demo account is told nobody (its friends are made up by the browser), where migration 0017 is not applied the state is empty, never cached, rule `friendsRead` (120 a minute per IP). **`POST /api/hub/friends/<action>`** takes `{ "nickname": "Alex", "tag": 42 }` (the tag as a number or as typed, `0042`) and, for `request`, `"source": "form" | "profile"` (analytics only), answers `{ "ok": true, "result": "sent" | "accepted" | "friends" | "declined" | "cancelled" | "removed" | "blocked" | "unblocked" }` and starts with `assertSameOrigin` (403 `CROSS_ORIGIN`), then `rateLimit(null, request, "friendRequest" | "friendAction")`, then the session (401 `NOT_SIGNED_IN`; the demo account is told it is done and nothing is written) and the handle (400 `FRIEND_INVALID`, 400 `INVALID_REQUEST` for a body that is not JSON). The refusals: `request` 404 `FRIEND_NOT_FOUND`, 400 `FRIEND_SELF`, 409 `FRIEND_BLOCKED` (the sender blocked them), `FRIEND_LIMIT` (the sender has 200 friends), `FRIEND_REQUESTS_LIMIT` (100 sent that wait), `FRIEND_REQUEST_UNAVAILABLE` (the member has 50 requests waiting or 200 friends); `accept` 404 `FRIEND_REQUEST_GONE`, 409 `FRIEND_LIMIT`, `FRIEND_REQUEST_UNAVAILABLE`; `block` 404 `FRIEND_NOT_FOUND`, 400 `FRIEND_SELF`, 409 `FRIEND_BLOCK_LIMIT` (500); 503 `FRIENDS_UNAVAILABLE` where migration 0017 is not applied. A member who blocked the sender is never told: `request` answers `sent` and nothing is stored. Declining, cancelling, removing and unblocking what is not there are done, as far as the member can tell. The limits are `packages/core/lib/friends.ts`'s (`MAX_FRIENDS`, `MAX_REQUESTS_RECEIVED`, `MAX_REQUESTS_SENT`, `MAX_BLOCKS`)
- `/api/hub/unlink-external` is a global route of the hub too (PLT-133): a `POST` in `apps/web` itself, like the Steam routes (`force-dynamic`: it reads the session and writes the database). A signed-in member takes the account they linked at an external provider off theirs (`{ "provider": "steam" }`). The request must carry this site's `Origin` (403 `FORBIDDEN`), 401 `NOT_SIGNED_IN` for a visitor who is not signed in, 400 `INVALID_REQUEST` for a body that is not that or a provider that is not an external one, 409 `LAST_WAY_IN` when no other way in is left, 500 `UNLINK_FAILED` (the log says the step it stopped at), 200 `{ "unlinked": true }`, and nothing written for the demo account of development.
- `/game/<slug>` is the hub's page of a game (`(hub)/game/[slug]/page.tsx`), for every game of the catalog, live or to come, and `/game/<slug>/<code>` (`(hub)/game/[slug]/[code]/page.tsx`) the same page for a table that waits for players, with that table picked (both are `GamePageView`, `apps/web/src/components/game-page-view.tsx`). The table of a game has three segments too (`/<slug>/game/<code>`), and the static `game` wins over `[game]` at the first segment, so the two never meet (`game` is a reserved slug). The slug is looked up in the catalog (`getGamePage`, `apps/web/src/lib/game-page.ts`): a slug it does not list answers 404 with the hub's own `not-found.tsx`, and `/game` alone is no page. The page ends with the games the catalog finds similar to it (`related` of its entry, nine at most), under the title "Similar games", drawn as the home's cards in one row that scrolls sideways. `robots.txt` has no rule for `/game/<slug>` (`/*/game/` needs a segment before `game`), so the page says itself whether it may be indexed (its `robots` meta), and the sitemap lists the ones that may (`docs/catalog.md`); the page of a table (`/game/<slug>/<code>`) is private to those who have its link: `noindex` and `Disallow: /game/*/`, with the game's picture and name in its metadata so that the link, pasted in a chat, unfurls (the crawler follows the redirect from `/<slug>/game/<code>`)
- Tables on the hub (PLT-106): the page reads the visitor's table in `public.games` with the per-game player cookie (`<slug>_player`: `httpOnly`, `sameSite=lax`, `path=/`, no domain, so the hub's page and `/api/<slug>/...` both get it; only a route handler can write it, so the create and join routes set it and a page only reads it: `getPlayerId`). `findPlayerGame` returns the table that waits or is played and was written last, within six hours (`TABLE_IDLE_MS`: a table the visitor forgot is not theirs any more). The page creates, joins, leaves, sets the options of and starts a table with the routes that exist (`POST /api/<slug>/games`, `[code]/join|leave|options|start`), which take the name and the picture of a signed-in account on the server and the nickname of a guest from the request (`resolveSeat`, which also says which account it is: `seatMember` records it apart from the seat, for the players online). `TableSync` keeps a table that waits alive (Realtime and a poll) and takes whoever sits at it to the board once it is started; `enterBoard` (`apps/web/src/lib/table-door.ts`) is the one place that does
- The settings of a table and the public tables (PLT-21, phase B; `packages/core/lib/table-settings.ts`, `server/table-settings.ts`, `server/tables.ts`, migration 0014 and its test `supabase/tests/public_tables.sql`): the host's choices at the top of the lobby's panel (who may join, the speed, the number of players) are kept with the table in `games.settings`, one sparse object that only the server writes and reads apart from the table (`COLUMNS` of `server/games.ts` does not have it, so a project where the migration is not applied yet keeps opening, joining and playing tables as before: a read finds no settings, which is a private table of the usual speed and the game's seats). **`POST …/settings`** (`routes/api/games/[code]/settings/route.ts`, rule `settings`: 30 in ten seconds) takes `{ settings }` with every setting at once (`TableSettingsInput`: `visibility` `public|private`, `minRank` a tier above the lowest or null, `language` a language people speak or null, `pace` one of the lobby's four speeds, `seats` between the game's least and most players and never under the people who sit), checks it (`checkTableSettings`: 400 `INVALID_REQUEST`, 400 `INVALID_PLAYERS`), and writes it as one version of the table (so the people at it are told by the usual `update` event); only the host (403 `HOST_ONLY`) and only while the table waits (409 `GAME_IN_PROGRESS`); 503 `SETTINGS_UNAVAILABLE` where the column is missing. `POST /api/<slug>/games` takes the same object as `settings` in its body, checked before anything is written, so that a table opened public is listed from its first moment (a project without the column opens it private). **`POST …/join`** reads the table's settings and refuses, for a **public** table only, a player who does not meet what it asks (403 `RANK_TOO_LOW`: the tier of the member in this game, from their rank points, the lowest for a guest and for a member who never played it ranked; 403 `LANGUAGE_MISMATCH`: the platform language of the visitor, their account's, else the cookie's, else the browser's, by its base form, so English (UK) speaks English), and treats a table set for fewer seats than the game takes as full (409 `GAME_FULL`); a player who sits already is never asked again; a private table asks for nothing. **The public tables** are the lobbies whose host made them public, that someone who sits at them was seen at in the last three minutes (`games.seen`: the page of a lobby asks again every few seconds) and that were written within `TABLE_IDLE_MS`, the newest first, 50 at most, read by `public_tables` (`readPublicTables`, which lists none rather than fail); they are listed on the game's page (`getTables`, after the visitor's own table), on the Tables tab (`/tables`, `publicTableRows`) and after the member's own tables on the signed-in home, and the first two are asked for again every 20 s while in view (`LiveRefresh`, `router.refresh()`). A visitor who does not meet what a table asks reads its row, with its rank and language as tags, and its button says what it asks. The form that opens a table starts with the table public (what the button's globe shows). The speed is kept and shown and sets no clock yet.
- The rules of the tables (PLT-120, `packages/core/server/table-rules.ts`, `tables.ts`, migration 0013): a player can sit at several lobbies, but a table **does not start while one of its players is in a game somewhere else**. `POST …/start` and the vote that completes a rematch (`…/replay`) ask the database which seats of the table are busy (`busy_seats`: a seat is busy when its cookie also sits at another table of the same game that is `starting` or `playing`, or, for a seat that belongs to an account, when that account holds a seat at such a table of any game; the account of a seat is `games.member_ids`, which never reaches the browser) and answer 409 `PLAYER_BUSY`; the look is taken before the write with the table as it was read, so a table whose seats changed in between answers 409 `CONFLICT` (the host presses again), and a look that cannot be had (migration 0013 not applied yet, the database down) lets the table start. **`POST …/leave`** does what fits where the table is: in the lobby the player is unseated and the table has another host if they were it; in the ready check they are unseated and the check is over (PLT-107); in a game in progress their seat stays at the table in `players`, marked `"left": true`, and the server plays it from then on with the engine's `autoPlayFor` (`settleLeavers`, in the same write as the leave and after every move or takeover that reaches a step they owe; never when everybody left); the seat counts for no rating (`mark_taken_over`) and the game they leave may end this way and is recorded like any other; a table that is over has nothing to leave. **The last player who leaves a table deletes it** (PLT-21): a lobby, a ready check, or a game in progress that everybody left (`deleteEmptyTable` in `server/games.ts`, called by the leave route and by `settleReadyCheck`, which ends a ready check with nobody ready the same way) leaves a table that holds nobody and that nobody can come back to, so the row is deleted at once instead of waiting for the nightly clean-up; the delete is guarded by the version of the write that emptied the table, so a player who sat down since keeps it, a game that the leave ended is not deleted (its result is written down after the response, from its row, and the nightly job takes it), a leave that changed nothing deletes nothing, and a failure is logged and left to the nightly job. A player who left is not a member of the table for any route (`isSeated`: `meId` is null, they are not present for the takeover, `action` answers 403 `LEFT_GAME`, chat, takeover and debug 403 `UNKNOWN_PLAYER`), `findPlayerGame` and `member_tables` do not return the table as theirs, and a rematch is played by those who stayed (the table keeps only them, and refuses to begin with fewer than the game needs: 400 `NOT_ENOUGH_PLAYERS`). A player whose table has begun is **taken to it**: a member by the beat of their presence (`POST /api/hub/presence` answers `table`, the game, the code and the `status`, `starting` or `playing`, of the table they sit at that has begun, from `member_tables`, and `watching` when they sit at a lobby or a ready check, which makes the tab beat every 15 s instead of 45; `PresenceBeat` takes them to its board in place of the page they were on), a guest, who is known by the game's cookie alone, from the page of that game (`GamePageView` redirects to the board). While the table is `starting` a member is taken from every page of the hub but the legal ones, so that nobody misses the confirmation they owe the others; while it is `playing` they are taken from every page but the legal ones, a player's profile (`/player/<handle>`, which the seats of the table lead to) and their own pages (`/me`, `/me/games`, `/me/friends`, `/me/settings/**`), which they may look at while they play (`takenToGame(pathname, status)` of `@pbgo/accounts/presence`; an answer with no status counts as `starting`, the strict reading, for a server that has not been deployed yet). The search has a door of its own: a table of a visitor's search that has begun, its ready check included, takes them to its board from any page (`SearchSync`). The tables a member sits at are listed on the signed-in home (`HomeOpenTables`, the same rows as a game's page, each leading to its table); the member's own tables count while they were written within `TABLE_IDLE_MS` (six hours), and the nightly clean-up and `findPlayerGame` use the same time. Not yet: the database does not enforce the rule (two tables that start at the same instant with a player in common both start), which PLT-21's atomic commit will, and nothing penalises a player who leaves a ranked game.
- The search (PLT-21, phase C; `lib/quick-play.ts`, `server/quick-play.ts`, `server/table-seat.ts`): Play sits a visitor at one table of each game they picked, ten at the most, normal or ranked. **`POST /api/hub/play`** (rule `play`, 60 a minute per IP; it belongs to no game, so the app hands in the registry, the age rules and the helpers of each game: `PlayDeps`) takes `{ games, mode, nickname?, poll?, waited? }` and answers `{ tables }`. For each game it keeps the lobby the visitor sits at already, else sits them at the fullest public lobby of the mode that has a seat, whose rank and language they meet and that is played at the usual speed, else opens one (public, the usual speed, `defaultSeats` of the game, and opening is limited like `create`). A visitor who is in a game, or in a ready check, is told that table alone. Asking again changes nothing: the browser does it every 3.5 s while the search lasts (`SearchSync`), which keeps the seats alive (`games.seen`) and moves a visitor who sits alone to an older lobby that has someone, so that two searchers who opened a table at the same instant meet. A **ranked** search is for members (403 `RANKED_MEMBERS_ONLY`) and never meets a normal table. A ranked table is opened with no helpers and with the tier of the member who opened it (`settings.ranked`, `settings.anchor`, `games.ranked`); a joiner's tier must be within `rankGap` of it (one tier, and one more for each 30 s the table has waited: 403 `RANK_GAP`, also for the join route), and nothing in it changes (403 `RANKED_TABLE_LOCKED` for options and settings, 409 `RANKED_TABLE_NOT_FULL` for a host's early start). **`POST /api/hub/play/cancel`** takes `{ tables }` and leaves those lobbies. **Every table begins by itself when it is full** (`startWhenFull`: the join that takes the last seat asks `beginTable`, the one function the host's start uses too; the seat is taken whatever happens, so a table that cannot begin, `PLAYER_BUSY` for one, stays a full lobby that its host starts). **When a game begins its players leave their other lobbies** (`leaveOtherLobbies`, after the ready check: a member leaves them in every game, a guest in the same game). The lists of tables say how each counts, Normal or Ranked. Tests: `server/quick-play.test.ts`, `lib/quick-play.test.ts`.
- The ready check (PLT-107): the host's `POST …/start`, or the join that takes the last seat (`startWhenFull`), sets the game up and puts the table in the status `starting`, for `READY_WINDOW_MS` (a minute; `READY_CHECK_SECONDS` of the environment changes it) with `ready_at` empty, so nobody is ready by default, the host included; everybody seated comes to the board, `/<slug>/game/<code>`, where `BoardEntry` of core mounts the game's board behind the platform's start screen (`StartScreen`: black and white, built from `@pbgo/ui/platform`, one collective bar and a row for each player; `held`, `onLoaded` and `onProgress` of `BoardProps`: the board loads its pictures, says how far it is and holds its opening). Every player confirms that they are there with a button, "I'm here" (large and primary, from the first moment even while the board loads; it has the focus, so Enter and Space press it; once pressed it is disabled, with a spinner, and says that the others are awaited, and the title and the line under it follow where the player stands), and nothing is automatic: a player is ready when they have pressed it and their board is loaded, and only then does the board send `POST …/ready` (a press made before the board is loaded is kept and sent when it is; if the table cannot be told, the button comes back), so a table that began because it was full does not draw an absent player into a game. The boards tell each other how far they are on a presence channel (`loading:<slug>:<code>`, `openLoading` of `lib/realtime.ts`, nothing stored: it only paints the bar). The last board to be ready makes the table `playing` and `game_started` is sent; the screen goes for each player when the game has begun and their board is loaded, and the boards play their opening from then. A player who comes back to a game under way gets the same screen with their own bar only, no button, no barrier and no request: it goes as soon as their board is loaded; one who comes back during the check after the table has them down as ready is not asked again. Nothing runs on a timer: a check whose time is up is ended by the first request that looks at the table (`settleReadyCheck`: the read route every board polls, `GamePage`, `ready`, `start`), which unseats whoever did not confirm, or whose board was not loaded, and sends the table back to the lobby for the others (`expirePatch`, `server/ready.ts`); a check that ends with nobody ready deletes the table (PLT-21), and the players, who read it as gone, go to the game's page instead of the table's (`GameClient`); PLT-13's backstop will end the ones nobody looks at. `leave` ends a check for everybody too, and `join` and `options` are refused while it lasts (`GAME_IN_PROGRESS`)
- The tabs of the hub's navbar (`SITE_TABS` in `apps/web/src/components/site-header.tsx`) each lead to a page of the hub. The hub's layout mounts the bar once (`SiteHeader`, a client component), and it reads the address to know what is current (`currentOf`: the logo on `/`, a tab on its page, Games on `/game/<slug>`, the bar and no tab on the pages of an account and the public profiles (`/player/<nickname>-<tag>`, where a visitor must be able to leave the page), and nothing, so no bar, on `/login` and `/signup`, which are a page of their own (`AuthShell`: the logo alone, the brand's lettering behind the card, a quiet foot), on `/docs`, the way into the docs, and on the pages of a doc, which are not the platform's (a doc has a side menu of its own), the legal pages and the 404); the pages do not draw it. Mounted once, it stays from one page to the next, which is what lets the fill behind the current item glide (`docs/design/02-foundations/07-motion.md`). The logo is the home, `/`, and it is the current button there (the front page is no tab); Games is `/games` (a game's page, `/game/<slug>`, is Games too), the list of every game of the catalog, indexable and in the sitemap; Tables, Tournaments and About are `/tables`, `/tournaments` and `/about`, pages with a title and an empty state for now (About also holds a "What's new" section, `/about#whats-new`; `/whats-new`, the page it used to be, is a permanent redirect to it in `next.config.ts`, and stays a reserved slug) (`ComingSoonPage`: the title, what is to come, the footer), `noindex` and out of the sitemap. Pricing, `/pricing`, has no tab and answers 404 while `PRICING_OPEN` (`apps/web/src/site.ts`) is false, since there is no pricing to show yet: its page and its plans are kept for the day one is on sale, and its message to the publishers is at the foot of About. The legal pages are a folder of their own: `/legal/cookies` (the Cookie Policy), `/legal/privacy` and `/legal/terms`, which the footer links to (the last two are drafts for the owner, or a lawyer, to validate: `noindex`, with the stub's "being written" line until they say so, `docs/legal.md`), and `/legal`, the notice, which nothing links to for now (the owner is not sure the site needs one); `/privacy` and `/terms`, where the last two used to be, are permanent redirects in `next.config.ts` and stay reserved slugs. ## Rate limiting
- Every mutating game route (create, join, leave, options, settings, start, ready, action, replay, takeover, tick) and `POST /api/<slug>/feedback` start with `await rateLimit(game.slug, request, "<rule>")` (`server/rate-limit.ts`). Limits live in `RATE_LIMITS` (`server/rate-limiter.ts`): per player cookie when present, else per IP (create: always per IP), never per table, plus a per-IP ceiling across routes. `POST /api/hub/presence` belongs to no game: it starts with `await rateLimit(null, request, "presence")`, 30 a minute per IP (a tab beats about once every 45 s, and every 15 s while its member sits at a lobby or a ready check), and so do `POST /api/hub/play` and `…/play/cancel` with `"play"`, 60 a minute per IP (a search asks every 3.5 s), `POST /api/hub/birthdate` with `"birthdate"`, 20 in ten minutes per IP, `POST /api/hub/profile` with `"profile"`, 20 in ten minutes per IP, `GET /api/hub/profile` with `"profileRead"`, 120 a minute per IP, and `POST /api/hub/unlink-external` with `"externalUnlink"`, 10 in ten minutes per IP, `GET /api/hub/friends` with `"friendsRead"`, 120 a minute per IP (the panel asks about every 20 s from each tab, and after each change), `POST /api/hub/friends/request` with `"friendRequest"`, 30 in ten minutes per IP, and the other `POST`s of `/api/hub/friends` with `"friendAction"`, 60 in ten minutes per IP. Over the limit: 429 `RATE_LIMITED` + `Retry-After`. The chat route has its own per-player token bucket
- `POST /gamemaster/api/login` belongs to no game: it starts with `await rateLimit(null, request, "adminLogin")`, 5 attempts per 10 minutes per IP, counted before the credentials are checked (the right password is refused too once the limit is reached)
- Counters are in memory, per function instance; to share them, implement `RateLimitStore` and call `setRateLimitStore()`, or let the Vercel Firewall count (a rate-limit rule on the paths that matter, the admin login first: `docs/bots-and-abuse.md`). A new mutating route of a game (`ROUTES`) must call `rateLimit` too
