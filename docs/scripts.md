# Scripts: game-flow, game-rules, setup-env, check-game, check-board, check-scout, check-rules

`pnpm game-flow`, `pnpm game-rules`, `pnpm setup-env`, `pnpm check:game`, `pnpm check:board`, `pnpm check:scout` and `pnpm check:rules` in full; the Commands section of the root `CLAUDE.md` gives one line for each.

## Commands in full

- `pnpm game-flow <verb>` — what the skill `/add-game` keeps the state of a game with (`packages/pipeline`): `status`, `start`, `begin`, `gate`, `check`, `validate`, `fail`, `redo`, `rulebook`, `linear`, `linear-record`. No model, no key, one file of state per game outside the repo, `~/Companies/PBGO/assets/<slug>/pipeline.json`. In full below
- `pnpm game-rules <slug> --rules [<lang>=]<file.pdf> [--rules …] [--dry-run] [--overwrite]` — a game's rulebook PDF per language into the draft of its `settings` (`rulesPdf<Lang>File`, Mechanics tab), whatever its size (the gamemaster's upload stops at 4.4 MB). A field that holds a file keeps it unless `--overwrite`; the same files again change nothing. The tool is `rulebook` of `@pbgo/content-kit` (`packages/content-kit/README.md`)
- `pnpm setup-env [--no-push | --check]` — applies the pending Supabase migrations (see `docs/supabase-and-env.md`), fills `apps/web/.env.local` (generating `ADMIN_SESSION_SECRET` and `CRON_SECRET`, the token of the nightly clean-up, once and appending them to the secrets file) and pushes the variables to the Vercel project `pbgo`, looked up by its id (`VERCEL_PROJECT_ID` of the secrets file, else `prj_bsk7OjC3wkJrI6ElHFa8bfD71xfs`), never by its name, through the API alone (no `.vercel/project.json`, no Vercel CLI, no CLI login: any worktree will do); aborts, touching neither `.env.local` nor Vercel, when a Supabase value is missing, a project can't be used or a migration fails (see `docs/supabase-and-env.md`). `--no-push` writes nothing to Vercel and neither reads nor migrates the production project. `NEXT_PUBLIC_POSTHOG_KEY` and `NEXT_PUBLIC_POSTHOG_HOST` (optional, both or neither) go to `.env.local` and to every Vercel target once `@pbgo/analytics` accepts the pair (a pair it refuses prints ✗ and is neither written nor pushed, the exit code does not change). `GEOAPIFY_API_KEY` (optional: the search of a city in the Edit profile window, to `.env.local` and every Vercel target; without it the window has no City field). `RESEND_API_KEY` and `RESEND_PREVIEW_API_KEY` (optional: the keys the site's own code sends e-mails with, for the link that reopens an account its member deleted; the first is the production key and goes to the Vercel production target, the second serves previews and local development and goes to the preview and development targets and to `.env.local`, as `RESEND_API_KEY`; one alone serves everywhere; a value that is not a Resend key, `re_…`, prints ✗ and is neither written nor pushed). `BGG_API_TOKEN` (optional, from the secrets file or `.env.local`: the token of the application registered at BoardGameGeek, which `content:bgg` reads its API with; it goes to `.env.local` only and is never pushed to Vercel, since the hub does not call BoardGameGeek). `STEAM_WEB_API_KEY` (optional, from the secrets file or `.env.local`: the key of Steam's Web API, 32 hexadecimal characters, which switches the Steam button of the sign-in on) goes to `.env.local` and to every Vercel target the same way (one of the wrong shape prints ✗ and is neither written nor pushed). `NOTION_API_KEY` is not handled any more: the hub reads no Notion since PLT-90, and the platform's seed takes the key from the environment or from `apps/web/.env.local` (`docs/catalog.md`). A Supabase variable already on the Production target (the Supabase ↔ Vercel integration manages them) is skipped, not overwritten, and the run still exits 0; it exits 1 only when the Vercel project can't be reached or a Vercel call really fails
- `pnpm check:game <slug> [--stage scaffold|engine|binding|board|content|live | --only <stage>]` · `pnpm check:game --all` — how far a game has got on its way from a name to live (`scripts/check-game.mjs`). It reads files only: no network, no build, no secret. It reports six stages, each with checks that are `ok`, `warn` (look at it) or `fail`: `scaffold` (registered with a Sanity project, packages and notes there), `engine` (a rules spec, `docs/games/<slug>/rules.md`, as a warning when it is missing; the game's own, exports `GAME`, pure, up to date with the contract: `standings`, `progress`, no words, the contract suite; the layers of tests), `binding` (`GAME` exported, the three binding tests, `vitest.config.ts` running them), `board` (a board, three.js only in its folder, `Game` loaded lazily, hex colours counted, a `check-board.config.mjs` for `pnpm check:board`: a warning when it is missing), `content` (the Studio's guard, the seed, the plan in `CLAUDE.md`) and `live` (`live` and `indexable`). With `--stage` the command is a gate: exit 1 while a check up to that stage fails, exit 2 for a game or a stage that does not exist; with `--only` it is a gate for that stage alone (its own checks, whatever the stages before it say: the gate of a step done out of order, `/add-game` gates the Studio's forms by it), and `--stage` and `--only` exclude each other. `--all` prints each game of the registry with the last stage it passed and what stops it. `--json` prints one line of JSON (`slug`, `missing`, `reached`, `failing`) for the programs that ask (`pnpm game-flow`); for a game with no folder the report says whether the game is in the flow. The skills of `.claude/skills/` say what to do about each failure ([How far a game has got](engine/04-build-a-game/01-steps.md#how-far-a-game-has-got)).
- `pnpm check:board <slug> [--players 3,5,8] [--sizes 1280x800,…] [--checks presses,sizes,scenarios,reload,opening,absent] [--scenarios a,b] [--out <dir>] [--reduced-motion] [--keep-tables] [--port 3100] [--absent-seconds 85]` — checks a game's board in a real browser (`scripts/check-board.mjs`, its parts in `scripts/check-board/`), so that nobody writes the scripts of `engine-board` step 6 again. It is no part of the six gates or of CI: it needs `pnpm dev` running (`http://localhost:3100`) and it opens and plays tables, so it names the Supabase project the dev server's `.env.local` points at before it writes anything and stops when that is the production project (`SUPABASE_PROJECT_REF` of the secrets file); the debug route it plays through answers 403 on a production deployment. It needs a Chromium in Playwright's cache (`npx playwright install chromium`: it fills `~/Library/Caches/ms-playwright`, nothing is added to the repo) and ffmpeg (`brew install ffmpeg`), and says which is missing (exit 2). Details below, in "`pnpm check:board` in full"
- `pnpm check:scout <file> [--online]` · `pnpm check:scout --list` — is a scout file, the JSON of the skill `game-scout` (`.claude/skills/game-scout`), what `/add-game` reads? `packages/games/src/scout.ts` is the one definition (`scoutProblems`: every key there and no other, the name and the slug by the rules of `slug.ts`, a base game for an expansion and a reimplementation and none for a base game, the figures in their ranges, the complexity as BoardGameGeek's weight given by ten people at least, public https addresses, a source for the edition; what is said of a file is printable and short, whatever it holds), `packages/catalog/scripts/check-scout.ts` the command. With `--online` it also reads what exists (`stateProblems`): the registry (the game has no folder yet) and the published games and expansions of the platform's Sanity project through the public API, with no token, so that `existing.catalog`, the entry's own type and base game, the base game and a game that the catalog already has under another slug or as another type are checked (two names are one game only among their peers, the games and the expansions of one base game, unless BoardGameGeek tells the items apart). That is the state at the time of the scout: run it when the file is made, not after the entry exists. `--list` prints what a scouted game is compared with, one line each: slug, type, BoardGameGeek id, base game, folder in the repo and name. Exit 0 when sound, 1 for a problem or when the project cannot be read, 2 for a wrong command line. The command is run by Node itself, so `packages/catalog/src/check-scout-script.test.ts` runs it as `pnpm` does
- `pnpm check:rules <slug> [--name "<Game Name>"] [--stamp [--date YYYY-MM-DD]]` — is the rules spec of a game, the page of the skill `game-rules-spec` (`.claude/skills/game-rules-spec`), what `/add-game` and the engine read? `packages/games/src/rules-spec.ts` is the one definition (`rulesSpecProblems`: the title `<name>: rules spec`, the eleven sections in their order and no other, the five lines of the edition with its status, the players and the goal, the table of the components (a kind, a name, a count, a description, a page), the pages cited in the sections that say the rules, the open points each with its four paragraphs, the glossary, and nothing a page of the docs may not hold: an HTML tag, a placeholder, a picture, an address that is not https, more than a thousand characters quoted from the rulebook; what is said of a page is printable and short, whatever it holds) and `indexProblems` for its landing page `docs/games/<slug>/index.md`, which the docs of the site need for the folder; `packages/games/scripts/check-rules.ts` is the command. `--name` checks the title against the game's name. `--stamp` is the owner's ok: when both pages pass, the status of the spec and every open point that waits for the owner become `validated <day>` (`--date`, default today), the stamped page is checked again before it is written, and a page that is validated already is left as it is. Exit 0 when sound, 1 for a problem or a page that is not there, 2 for a wrong command line. `PBGO_GAMES_DOCS_DIR` moves the folder of the specs (a test's world). The command is run by Node itself, so `packages/games/src/check-rules-script.test.ts` runs it as `pnpm` does

## `pnpm game-flow` in full

**What it is.** The command that the skill `/add-game` (`.claude/skills/add-game`) keeps a game's state with. A game goes from its name to live in ten steps (the table of "A game from A to Z" in `.claude/skills/README.md`: `/game-scout`, `/platform-catalog-entry`, `/game-rules-spec`, `/platform-assets`, `/game-new`, `/game-sanity-create`, `/game-assets`, `/engine-rules`, `/engine-board`, `/game-go-live`). The skill runs in the owner's own Claude session: a sub-agent carries out each step with its skill, the skill runs the step's machine check of what it left, and the owner answers at a gate in the chat (ok, or what to change) before the state and the step's Linear sub-issue are brought up to date and the next step begins. The command holds what must not be improvised: where the game stands, which step is next and whether it may begin, the brief of a sub-agent, the check, what the owner's ok does, the Linear work and the rulebook. It calls no model and holds no key. Exit 0 when it did what it was asked, 1 when it refused or a check failed (the gate is still to be shown), 2 for a wrong command line; every verb prints what to do next.

**The state** of a game is `<assets>/<slug>/pipeline.json` (`~/Companies/PBGO/assets`, `PBGO_ASSETS_DIR` moves it), next to its `scout.json` (and its `rules.pdf`, once there is one): outside the repo, never committed, so that any session picks the game up where it stopped. It keeps what the repo cannot say: for each step its status (`pending`, `running`, `gate`, `validated`, `failed`), the gate it waits at, how many rounds it took, the last report and its links, what the machine said of it, the Linear issues. The stages of `pnpm check:game` are never copied into it: for a game that has a folder `status` prints what `check:game` computes (`--json`). The skill is its only writer, one verb at a time, and every write is a whole file renamed into place; since each verb reads the state, changes it and writes it whole, a lock (`<assets>/.game-flow.lock`, taken by every verb but `status`) makes two that run together wait for each other. Each step also keeps when its round was opened, where its sub-agent writes its report (one file for each round) and when its gate was reached. The file that the terminal command wrote (GAM-35 removed that command) is read as it is: what only it used is left out.

**The verbs.**
- `status [<game>] [--step <id>] [--json]`: a game is a name as typed or a slug. The steps with their state, the Linear parent, whether `games/<slug>` is in this checkout and the stage it has reached, then `Next:`, the action (`begin`, wait for the owner at a gate, begin again after an interruption, the folder is there already, the folder is not in this checkout, done). With no game, the games in the flow; with `--step`, one step's report, check and links.
- `start "<Game Name>" [--family <folder>] [--adopt-through <step>]`: the game enters the flow. `--family` puts its folder in the folder of its line, `<assets>/<folder>/<slug>/`: the base game and the reimplementations of one line sit together (`the-crew/` holds `the-crew-the-quest-for-planet-nine/` and `the-crew-mission-deep-sea/`). The flow looks for a game in `<assets>/<slug>/` and in the folders of the families, one level down, and the scout's change of slug moves the folder inside the one it is in. A game that has a folder in the repo is refused, since the scout never runs for a game that exists, unless `--adopt-through` says up to which step it has really got: those steps are recorded as done outside `/add-game`, and the stages that `pnpm check:game` judges for them (the folder, the forms…) must pass, or the game is not taken on.
- `begin <game> <step> [--scratch <dir>] [--change | --again]`: the steps go in order, and the ones that work in the game's folder (the forms, the art, the engine, the board, going live) wait for `games/<slug>` in this checkout; the game folder also wants the rules spec to be in this checkout (it is written there, uncommitted) and no tracked change but the game's, since its first commit carries what is there. It opens a round, writes the brief of the step's sub-agent (`brief-<slug>-<step>.md` in the scratch folder) and says where its report goes (`report-<slug>-<step>-r<round>.md`: a report that was written and never read is never overwritten). A step that is open and has no report is not opened again unless `--again` says its sub-agent is gone, since a second one would do the work twice; one that has a report is gated, not reopened. `--change` opens a new round for a change the owner asked for. An expansion has no step after the catalog entry: the command says so.
- `gate <game> <step> [--report <file>] [--link <url>]…`: the sub-agent is done. It records the report (the round's own file when `--report` is left out; `STATUS: questions` and `STATUS: blocked` are refused: a gate is for a finished step; a step that has not begun is refused, but for the game folder when it is there already), runs the check, and prints the gate: report, check, links, what the owner's word does.
- `check <game> <step>`: the check again. `validate <game> <step>`: the owner said ok. At the first gate of a step that has two (the catalog entry) it moves to the second, the word `publish`; at the last gate it runs the check once more (the files may have changed), refuses a step that does not pass, and validates the step after doing what the ok does for it (below).
- `fail <game> <step> --reason "<why>"` (a sub-agent that is blocked), `redo <game> <step>` (that step and the ones after it back to not started; the skills fill and never replace).
- `rulebook <game> [--dry-run]`: the rulebook the scout found (`--dry-run` says from where and to where and fetches nothing: the skill asks the owner first, a download needs their yes), `edition.rules.url`, which the owner validated at the scout's gate, fetched to `rules.pdf` next to the scout file, unless it is there already (the owner's own, or an earlier fetch: never replaced). The fetch (`src/download.ts`) is bounded the way a command given an address must be: https and its own port only, no credentials, a host name and not an IP, a host whose every address is public (each hop of a redirect judged again, and the connection goes to the address that was judged), five redirects at the most, 60 MB, 90 s, and a file kept only if it starts with `%PDF-` and ends with `%%EOF`, written whole under another name and renamed. A sub-agent that fetches a PDF with a web tool gets bytes it cannot read, which is why the command does it.
- `linear <game> [--scratch <dir>]` and `linear-record <game> [--scratch <dir>]`: below.

**A step.** `begin` writes its brief (`src/brief.ts`), which the sub-agent is told to read: the skill to run and its argument, what the machine will check, the paths it knows, and the rules that bind it. A sub-agent cannot talk to the owner: whenever the skill says to ask, and always before something that leaves the machine or is hard to undo (an upload, a publication, a Sanity project or a token, `pnpm go-live`, `pnpm setup-env`, a push, a pull request, a download) it stops with `STATUS: questions` and its recommended default for each, and the skill asks the owner in the chat and sends the answers back. It makes no picture, creates no account, reads no secret, merges nothing, deletes only its own files, and writes neither the state nor Linear. It ends with a report (`STATUS`, `SUMMARY`, `QUESTIONS`, `FILES`, `LINKS`, `NOT VERIFIED`) that it returns as its final message: the app does not let a sub-agent write a file, so the skill writes that message to the round's report file.

**The checks** (`src/checks.ts`) are the commands the skills already name, and `validate` runs them again because the files may have changed since the sub-agent's report. The scout: the file exists and has the shape, and `pnpm check:scout <file> --online` passes. The catalog entry has two gates, the drafts and then the word `publish`: its report must say which documents publish would make public, in the skill's own sentence (`Validate publishes 2 documents (game-x, publisher-y)`: the count and the ids agree, each id is a `game-`, `expansion-`, `creator-`, `publisher-` or `category-` one), the second gate shows them, and the check at the end asks the public API of the platform's Sanity (the published perspective, no token) whether those documents were written since the owner said the drafts were right (a game that was in the catalog before is published by what the skill writes again, not by what was there; a Sanity that cannot be read is no confirmation): the skill's word that it published is not taken as done. The hub has no preview of a draft (it reads `perspective=published` of one dataset): the Studio page is what to look at. The rules spec: `pnpm check:rules <slug> --name <name>`. The pictures: `pnpm catalog:pictures <slug>` (the entry is published, the owner may leave pictures empty). The art: the game's seed in a dry run on the art folder (`pnpm -C games/<slug> content:seed --dry-run --art-dir <folder>`), whose "Art" part is shown and which fails only when the seed cannot run. The game folder, the forms, the engine, the board and going live: `pnpm check:game <slug> --stage scaffold`, `--only content` (the checks of that stage alone: the engine is not written yet, which `--stage content` would count), `--stage engine`, `--stage board` and `--stage live` (the flags of the registry are on in the checkout once the pull request that turns them on is merged and the branch is updated).

**What the owner's ok does.** For the scout, the folder follows the slug it settled (`~/Companies/PBGO/assets/<old>` moves to `<slug>`, the name asked for stays an alias, and a slug that has a folder in the repo is refused). For the rules spec, the page is stamped: `pnpm check:rules <slug> --name <name> --stamp --date <today>` sets `- Status: validated <day>` and every `**Status.** to validate` to `validated <day>`: validating accepts the readings of the open points, which `engine-rules` then does not ask for again. For the catalog entry, the first ok moves to the second gate and the word `publish`, which the skill sends to the sub-agent that made the drafts.

**Linear.** One parent issue per game ("<Name>: add the game") and one sub-issue per step ("<Name>: scout", Game lane; "<Name>: catalog entry", Platform lane; "<Name>: rules spec", Game lane; "<Name>: platform assets", Platform lane; then "<Name>: game folder", "studio forms", "game assets" and "go live", Game lane, and "<Name>: engine" and "board", Engine lane), team Games, project Game factory, the game's label of the group Game (made when it is missing). The first step not validated is In Progress, the next Todo, the validated ones Done with a comment of the links; the parent stays open for the steps to come. The command holds no key: `linear` computes what Linear should say from the state and writes the brief of a small sub-agent (Haiku) that does it through Composio, looking for an issue by its exact title before it makes one, and that writes the ids it got to a file; `linear-record` writes them into the state, and a failure is told and never stops the game (the next point tries again). The ids of the team, the project, the states and the labels are in `src/linear.ts`.

**Tests.** `pnpm --filter @pbgo/pipeline test`: each part on its own, and the verbs in a world of temporary folders (a stand-in for the commands they run, for the rulebook fetch and for the platform's Sanity), `bin/game-flow.ts` as Node runs it, and `src/add-game-skill.test.ts`, which keeps the table and the verbs of the skill to the steps and the command, and checks that no file of the repo names the terminal command that GAM-35 removed. What no test can say, and the first run on a game does: that a sub-agent follows its brief, that `SendMessage` takes an answer back to the agent that asked, and the real Composio calls of the catalog entry and of Linear.

**A next step** is a skill (`.claude/skills/<prefix>-<job>`), a `StepDefinition` in `src/steps.ts` (its argument, its notes for the sub-agent, its check) and its row in the tables of `.claude/skills/README.md` and `.claude/skills/add-game/SKILL.md`.

**Settings.** `PBGO_ASSETS_DIR` (the folder of the games' working files; a path with no space or special character: the skills take it as one word), `PBGO_GAMES_DOCS_DIR` (where the pages of the specs are, `docs/games` of the checkout) and `PBGO_SANITY_API_BASE` (where the publication is read back: a test's server).

## `pnpm check:board` in full

**What it does.** Guests are seated through the game's API, each with a cookie jar of its own (so each is a player). The viewer, seat 0, is a headless Chromium on `http://localhost:3100`, the only origin besides production and the Studio that the game's Sanity CDN lets read its pictures, so the cards show their faces (on another `--port`, because a second dev server runs beside the first, the tool fetches those pictures itself, as that origin, and hands them to the page); the other seats exist only in the script and play through the API, at a table opened for the number of seats that is checked (a table opens for the median of the game's players unless it is told how many). The tool sees a board without any help from the game: three.js tells `globalThis.__THREE_DEVTOOLS__` about every renderer and scene it makes, the tool installs that hook before the page's scripts run, and so it holds the camera that draws the table and the objects that react-three-fiber gave a click handler, which is what the board offers to press. For each of them it works out the pixel where a pointer reaches it (react-three-fiber's own raycaster, and `document.elementFromPoint` for whatever the page puts over the canvas: the cookie banner, a box of the HUD) and says why when there is none. No coordinate of the game is copied into the tool. It leans on two internals of react-three-fiber 9 (`object.__r3f.handlers` and `scene.__r3f.root.getState().raycaster`) and on three.js's devtools hook, so after an upgrade of either package run it once on Flip 7: a scan that finds no control is the sign.

**The checks**, in this order, each with its own table and browser, the tables left at the end (the guests leave, and the last to leave deletes a table; `--keep-tables` keeps them). Before them a `warm-up` opens the board of one table, so that a server that compiles on demand has compiled it; when no board draws the run stops there instead of failing every check in turn. A board is measured and photographed once it is shown (the platform's loading screen has lifted), has stood still (the camera and the canvas) and has had 3.5 s for the announcement of the start of the game, which lies over it in the page, to go.
- `presses` — (in the first window of `--sizes`, like every check that is not about the windows) plays the viewer's side with the mouse, as a person would: the game's config says what is next (`presses.plan`) and where the control is (`presses.find`), the tool waits until the board has been told the table's version, scans the pressables, moves the pointer and presses, then reads the table through the API and expects its version to have changed. Fails when the board offers no control for it, when it cannot be reached (and says what lies over it), or when two presses change nothing. A game with no `presses` in its config skips it.
- `sizes` — the board in each window of `--sizes` (default: 1280x800, 1280x720, 1440x900, 1920x1080, 2560x1080, 1024x640, 1024x768, 900x600, 1024x1366, 900x1200), in each situation of the config's `scenes` (default: the viewer's move), as one sheet per situation (`sizes-<seats>p-<scene>.png`, a window to a tile, in the order of the list). In each window it measures what the platform lays over the board (the `overlays` of the report), whether the page scrolls sideways, where the camera stands, and whether every control can be pressed: in the first window every control must be reachable (a failure), in the others a covered control is a warning (a table may lie under the platform's boxes in a small window).
- `scenarios` — the cases that `GAME.debug` can rig, each recorded as frames (`Page.startScreencast`) and tiled into nine from the first change of the page's text (`scenarios-<seats>p-<case>.png`; the frames are in `frames/`). The config lists the game's own (a special card, a bust, a save); every game gets `turn` (one turn played by the engine's `turn` command) and `over` (the game played to its end, the end screen). One table serves all of them, in order, `over` last.
- `reload` — a few moves are played, the board is opened and left to settle, then reloaded with a screencast running: the sheet starts when the platform's loading screen lifts, and the canvas is sampled while the camera stands still. A warning when it keeps changing (cards that fly in again); a failure when the board does not come back or the table moved.
- `opening` — the normal start, not the debug one: the host starts the table, the board loads behind the start screen, the others say they are ready, the viewer presses "I'm here" and the sheet shows the opening. A failure when the start screen never offers its button or the table does not begin. A table that fills begins by itself (the most seats): the host has nothing to start.
- `absent` (the fewest seats only) — the other seats read nothing for `--absent-seconds` (85 s, the platform counts a seat present for 75 s), then the board must still draw, the page's text and a screenshot are kept, and the platform's "Play for them" is pressed: the table must move.

**What fails the run (exit 1).** A board that does not draw within two minutes (no canvas, or a canvas with no scene, or the platform's screen over it for ninety seconds), an error the page printed (`console.error`, an exception, a resource that failed, an answer of the API that is a 5xx or 429; `ignoreConsole` of the config silences the ones that are known, and the 404 of a lazy chunk that Turbopack names with another hash than the one it serves is shown as a warning), a press that changes nothing, a case the game refuses, a table that does not begin. A warning is to look at and never fails: a board that never stood still, a page that scrolls sideways, a covered control in a small window, a table that kept moving after a reload, a case whose page text never changed. Exit 2: it could not run (no server, no Chromium, no ffmpeg, a seat count the game does not take, a wrong config, the production project).

**What it writes** to `--out` (default a folder of the system's temporary files, `<tmp>/check-board/<slug>-<time>`; keep it out of the repo, a pull request holds no screenshot): `report.json` (rewritten after every check: the project, the browser, one entry per check with its `status`, `problems`, `warnings`, `files`, the data it measured and its duration), the sheets (`*.png`, a sheet is 3 columns of cells, the frames in the order the report lists) and `frames/` (every frame a sheet is made of, full size, to look at one). Long: a run of every check at three counts of seats takes about twenty minutes (17 for Flip 7), so run it in the background and read `report.json`; `--players`, `--checks`, `--sizes` and `--scenarios` cut it to what changed.

**What it does not check.** The board on a phone (below 900 px the platform covers every game page with its desktop-only screen unless the game turned it off: `--sizes 390x844` photographs whatever the page shows, with a finger emulated), a drag, a sound, and whether a sheet looks right: a person or an agent reads the sheets, and the pull request says what was seen.

### The game's config: `games/<slug>/check-board.config.mjs`

Optional, plain JavaScript run by Node (it imports nothing of the game, whose board files are TypeScript for the bundler), its default export an object whose every key is optional, so a game with no file is still checked as far as the platform's own parts allow (a board that draws, the windows, the engine's `turn` and `over`, a reload, the start, a player who is away). `games/flip-7/check-board.config.mjs` is the model. A key that is not in the list below is refused, so a typo is told.
- `players: [3, 5, 8]` — the counts of seats (default: the fewest, a middle count and the most of the registry's `players`, at most 12); `--players` wins.
- `sizes: ["1280x800", …]` — the windows; the first is the one every control must be reachable in.
- `options: { targetScore: 500 }` — the game's options for the tables of the checks, set before the others sit down (a table that fills begins by itself and its options can no longer change): a long game so that no case ends it, or a short one.
- `bot({ state, me, seat, table })` — what a seat does when the game waits for it: the action to post (`{ type: "hit" }`), or `null` for the engine's `turn` debug command. `state` is the table as that seat reads it (`GET …/games/<code>`: `view`, `waitingFor`, `status`, `version`, `log`…), `me` its id.
- `warm: 6` — how many moves are played before a reload or an absence, so that there is something on the table.
- `scenes: { turn: async (table) => {}, … }` — the situations the windows are photographed in, in this order. The first is reached before the board opens, the others through the API while it stays open. Each brings the table to the situation: `await table.advance({ until: (state, who) => who === 0 && state.view.phase.kind === "turn", bot })`.
- `presses: { plan, find, expect, max, budgetSeconds, bot }` — `plan({ state, me, table, exercised })` is called when the game waits for the viewer and answers `{ label, prepare? }` (what to press, and an optional `async (table) => {}` that rigs the table first, for a situation that would otherwise be luck) or `null` (nothing to press: the move is played through the API); `find({ label, pressables, state, me })` answers the pressable to press from the list the board offers (`{ path, world: [x, y, z], size, pixel, reachable, why }`, `world` being the middle of the control on the table, x to the right and z toward the viewer: "the draw pile lies left of the middle"), or `undefined` while the board does not show it. `expect` lists the labels that should have been pressed by the end (a warning for the others, once `budgetSeconds` have gone, 150 s by default: a situation that takes many rounds is given that long), `max` caps the presses (60), `bot` is what the seats do between presses (default: the config's `bot`: a faster one brings the table sooner to a rare situation).
- `scenarios: { name: { run, record } }` (or just the function) — `run({ table, page, seats, name, settle, record, sleep })` reaches the case and returns `record(action, { seconds, step, lead })`, the frames of the move that `action` makes. `settle()` lets the board learn of the table's version and stand still (use it after a rigged move and before the recorded one); `table.rig(command)` sends a debug command of `GAME.debug`. A case that throws fails the check and the next one goes on.
- `ignoreConsole: [/\[missing/]` — patterns (RegExp, or text) of console messages that are not a failure here.

The `table` the config receives: `ids` and `names` (by seat, the viewer 0), `state(seat)`, `act(seat, action)` (throws when the game refuses), `rig(command, seat)`, `play(seat)` (the bot's move, else `turn`), `waitedFor(state)` (the seat the game waits for, -1 for nobody), `advance({ until(state, who), bot, max, label })` (plays everyone, the viewer included, until `until`) and `request(seat, method, path, body)` for any other route of the game's API.
