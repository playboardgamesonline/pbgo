# Scripts: add-game, game-rules, setup-env, check-game, check-board

`pnpm add-game`, `pnpm game-rules`, `pnpm setup-env`, `pnpm check:game` and `pnpm check:board` in full; the Commands section of the root `CLAUDE.md` gives one line for each.

## Commands in full

- `pnpm add-game` — a new game from nothing to its Studio. On a terminal with no argument it asks the name, the slug and the rules PDFs; otherwise `pnpm add-game [<slug>] [--name "<Game Name>"] [--rules [<lang>=]<file.pdf> …] [--yes] [--dry-run] [--no-open] [--push]` (the slug comes from the name, a rulebook with no language is English). `setup-env --check`, the name, the slug and the PDFs are checked first (nothing is created when one fails); the summary lists what leaves the machine (Sanity project, Supabase migrations, Vercel variables) and asks before creating anything (`--yes` skips the question, `--dry-run` stops after the summary); then new-game + go-live + the rules PDFs in the draft of Settings + setup-env + a check that the Studio is deployed, which opens it on a terminal (`--no-open` does not). A step that fails does not hide the others: the run ends with "Left to fix", a command per problem, and exits 1. `--push` commits and pushes a branch for a pull request. The skill `game-new` (`/game-new <slug>`) runs it for the owner and goes on to the fields of the Studio
- `pnpm game-rules <slug> --rules [<lang>=]<file.pdf> [--rules …] [--dry-run] [--overwrite]` — a game's rulebook PDF per language into the draft of its `settings` (`rulesPdf<Lang>File`, Mechanics tab), whatever its size (the gamemaster's upload stops at 4.4 MB). A field that holds a file keeps it unless `--overwrite`; the same files again change nothing. The tool is `rulebook` of `@pbgo/content-kit` (`packages/content-kit/README.md`)
- `pnpm setup-env [--no-push | --check]` — applies the pending Supabase migrations (see `docs/supabase-and-env.md`), fills `apps/web/.env.local` (generating `ADMIN_SESSION_SECRET` and `CRON_SECRET`, the token of the nightly clean-up, once and appending them to the secrets file) and pushes the variables to the Vercel project `pbgo`, looked up by its id (`VERCEL_PROJECT_ID` of the secrets file, else `prj_bsk7OjC3wkJrI6ElHFa8bfD71xfs`), never by its name, through the API alone (no `.vercel/project.json`, no Vercel CLI, no CLI login: any worktree will do); aborts, touching neither `.env.local` nor Vercel, when a Supabase value is missing, a project can't be used or a migration fails (see `docs/supabase-and-env.md`). `--no-push` writes nothing to Vercel and neither reads nor migrates the production project. `NEXT_PUBLIC_POSTHOG_KEY` and `NEXT_PUBLIC_POSTHOG_HOST` (optional, both or neither) go to `.env.local` and to every Vercel target once `@pbgo/analytics` accepts the pair (a pair it refuses prints ✗ and is neither written nor pushed, the exit code does not change). `GEOAPIFY_API_KEY` (optional: the search of a city in the Edit profile window, to `.env.local` and every Vercel target; without it the window has no City field). `RESEND_API_KEY` and `RESEND_PREVIEW_API_KEY` (optional: the keys the site's own code sends e-mails with, for the link that reopens an account its member deleted; the first is the production key and goes to the Vercel production target, the second serves previews and local development and goes to the preview and development targets and to `.env.local`, as `RESEND_API_KEY`; one alone serves everywhere; a value that is not a Resend key, `re_…`, prints ✗ and is neither written nor pushed). `BGG_API_TOKEN` (optional, from the secrets file or `.env.local`: the token of the application registered at BoardGameGeek, which `content:bgg` reads its API with; it goes to `.env.local` only and is never pushed to Vercel, since the hub does not call BoardGameGeek). `STEAM_WEB_API_KEY` (optional, from the secrets file or `.env.local`: the key of Steam's Web API, 32 hexadecimal characters, which switches the Steam button of the sign-in on) goes to `.env.local` and to every Vercel target the same way (one of the wrong shape prints ✗ and is neither written nor pushed). `NOTION_API_KEY` is not handled any more: the hub reads no Notion since PLT-90, and the platform's seed takes the key from the environment or from `apps/web/.env.local` (`docs/catalog.md`). A Supabase variable already on the Production target (the Supabase ↔ Vercel integration manages them) is skipped, not overwritten, and the run still exits 0; it exits 1 only when the Vercel project can't be reached or a Vercel call really fails
- `pnpm check:game <slug> [--stage scaffold|engine|binding|board|content|live]` · `pnpm check:game --all` — how far a game has got on its way from a name to live (`scripts/check-game.mjs`). It reads files only: no network, no build, no secret. It reports six stages, each with checks that are `ok`, `warn` (look at it) or `fail`: `scaffold` (registered with a Sanity project, packages and notes there), `engine` (the game's own, exports `GAME`, pure, up to date with the contract: `standings`, `progress`, no words, the contract suite; the layers of tests), `binding` (`GAME` exported, the three binding tests, `vitest.config.ts` running them), `board` (a board, three.js only in its folder, `Game` loaded lazily, hex colours counted, a `check-board.config.mjs` for `pnpm check:board`: a warning when it is missing), `content` (the Studio's guard, the seed, the plan in `CLAUDE.md`) and `live` (`live` and `indexable`). With `--stage` the command is a gate: exit 1 while a check up to that stage fails, exit 2 for a game or a stage that does not exist. `--all` prints each game of the registry with the last stage it passed and what stops it. The skills of `.claude/skills/` say what to do about each failure ([How far a game has got](engine/04-build-a-game/01-steps.md#how-far-a-game-has-got)).
- `pnpm check:board <slug> [--players 3,5,8] [--sizes 1280x800,…] [--checks presses,sizes,scenarios,reload,opening,absent] [--scenarios a,b] [--out <dir>] [--reduced-motion] [--keep-tables] [--port 3100] [--absent-seconds 85]` — checks a game's board in a real browser (`scripts/check-board.mjs`, its parts in `scripts/check-board/`), so that nobody writes the scripts of `engine-board` step 6 again. It is no part of the six gates or of CI: it needs `pnpm dev` running (`http://localhost:3100`) and it opens and plays tables, so it names the Supabase project the dev server's `.env.local` points at before it writes anything and stops when that is the production project (`SUPABASE_PROJECT_REF` of the secrets file); the debug route it plays through answers 403 on a production deployment. It needs a Chromium in Playwright's cache (`npx playwright install chromium`: it fills `~/Library/Caches/ms-playwright`, nothing is added to the repo) and ffmpeg (`brew install ffmpeg`), and says which is missing (exit 2). Details below, in "`pnpm check:board` in full"

## `pnpm check:board` in full

**What it does.** Guests are seated through the game's API, each with a cookie jar of its own (so each is a player). The viewer, seat 0, is a headless Chromium on `http://localhost:3100`, the only origin besides production and the Studio that the game's Sanity CDN lets read its pictures, so the cards show their faces; the other seats exist only in the script and play through the API. The tool sees a board without any help from the game: three.js tells `globalThis.__THREE_DEVTOOLS__` about every renderer and scene it makes, the tool installs that hook before the page's scripts run, and so it holds the camera that draws the table and the objects that react-three-fiber gave a click handler, which is what the board offers to press. For each of them it works out the pixel where a pointer reaches it (react-three-fiber's own raycaster, and `document.elementFromPoint` for whatever the page puts over the canvas: the cookie banner, a box of the HUD) and says why when there is none. No coordinate of the game is copied into the tool. It leans on two internals of react-three-fiber 9 (`object.__r3f.handlers` and `scene.__r3f.root.getState().raycaster`) and on three.js's devtools hook, so after an upgrade of either package run it once on Flip 7: a scan that finds no control is the sign.

**The checks**, in this order, each with its own table and browser, the tables left at the end (the guests leave, and the last to leave deletes a table; `--keep-tables` keeps them). Before them a `warm-up` opens the board of one table, so that a server that compiles on demand has compiled it; when no board draws the run stops there instead of failing every check in turn. A board is measured and photographed once it is shown (the platform's loading screen has lifted), has stood still (the camera and the canvas) and has had 3.5 s for the announcement of the start of the game, which lies over it in the page, to go.
- `presses` — (in the first window of `--sizes`, like every check that is not about the windows) plays the viewer's side with the mouse, as a person would: the game's config says what is next (`presses.plan`) and where the control is (`presses.find`), the tool waits until the board has been told the table's version, scans the pressables, moves the pointer and presses, then reads the table through the API and expects its version to have changed. Fails when the board offers no control for it, when it cannot be reached (and says what lies over it), or when two presses change nothing. A game with no `presses` in its config skips it.
- `sizes` — the board in each window of `--sizes` (default: 1280x800, 1280x720, 1440x900, 1920x1080, 2560x1080, 1024x640, 1024x768, 900x600, 1024x1366, 900x1200), in each situation of the config's `scenes` (default: the viewer's move), as one sheet per situation (`sizes-<seats>p-<scene>.png`, a window to a tile, in the order of the list). In each window it measures what the platform lays over the board (the `overlays` of the report), whether the page scrolls sideways, where the camera stands, and whether every control can be pressed: in the first window every control must be reachable (a failure), in the others a covered control is a warning (a table may lie under the platform's boxes in a small window).
- `scenarios` — the cases that `GAME.debug` can rig, each recorded as frames (`Page.startScreencast`) and tiled into nine from the first change of the page's text (`scenarios-<seats>p-<case>.png`; the frames are in `frames/`). The config lists the game's own (a special card, a bust, a save); every game gets `turn` (one turn played by the engine's `turn` command) and `over` (the game played to its end, the end screen). One table serves all of them, in order, `over` last.
- `reload` — a few moves are played, the board is opened and left to settle, then reloaded with a screencast running: the sheet starts when the platform's loading screen lifts, and the canvas is sampled while the camera stands still. A warning when it keeps changing (cards that fly in again); a failure when the board does not come back or the table moved.
- `opening` — the normal start, not the debug one: the host starts the table, the board loads behind the start screen, the others say they are ready, the viewer presses "I'm here" and the sheet shows the opening. A failure when the start screen never offers its button or the table does not begin. A table that fills begins by itself (the most seats): the host has nothing to start.
- `absent` (the fewest seats only) — the other seats read nothing for `--absent-seconds` (85 s, the platform counts a seat present for 75 s), then the board must still draw, the page's text and a screenshot are kept, and the platform's "Play for them" is pressed: the table must move.

**What fails the run (exit 1).** A board that does not draw within two minutes (no canvas, or a canvas with no scene, or the platform's screen over it for ninety seconds), an error the page printed (`console.error`, an exception, a resource that failed, an answer of the API that is a 5xx or 429; `ignoreConsole` of the config silences the ones that are known, and the 404 of a lazy chunk that Turbopack names with another hash than the one it serves is shown as a warning), a press that changes nothing, a case the game refuses, a table that does not begin. A warning is to look at and never fails: a board that never stood still, a page that scrolls sideways, a covered control in a small window, a table that kept moving after a reload, a case whose page text never changed. Exit 2: it could not run (no server, no Chromium, no ffmpeg, a seat count the game does not take, a wrong config, the production project).

**What it writes** to `--out` (default a folder of the system's temporary files, `<tmp>/check-board/<slug>-<time>`; keep it out of the repo, a pull request holds no screenshot): `report.json` (rewritten after every check: the project, the browser, one entry per check with its `status`, `problems`, `warnings`, `files`, the data it measured and its duration), the sheets (`*.png`, a sheet is 3 columns of cells, the frames in the order the report lists) and `frames/` (every frame a sheet is made of, full size, to look at one). Long: a run of every check at three counts of seats takes about twenty minutes (17 for Flip 7), so run it in the background and read `report.json`; `--players`, `--checks`, `--sizes` and `--scenarios` cut it to what changed.

**What it does not check.** The board on a phone (below 900 px the platform covers every game page with its desktop-only screen unless the game turned it off: `--sizes 390x844` photographs whatever the page shows, with a finger emulated), a drag, a sound, and whether a sheet looks right: a person or an agent reads the sheets, and the pull request says what was seen.

### The game's config: `games/<slug>/check-board.config.mjs`

Optional, plain JavaScript run by Node (it imports nothing of the game, whose board files are TypeScript for the bundler), its default export an object whose every key is optional, so a game with no file is still checked as far as the platform's own parts allow (a board that draws, the windows, the engine's `turn` and `over`, a reload, the start, a player who is away). `games/flip-7/check-board.config.mjs` is the model. A key that is not in the list below is refused, so a typo is told.
- `players: [3, 5, 8]` — the counts of seats (default: the fewest, a middle count and the most of the registry's `players`, at most 12); `--players` wins.
- `sizes: ["1280x800", …]` — the windows; the first is the one every control must be reachable in.
- `options: { targetScore: 500 }` — the game's options for the tables of the checks, set before the others sit down (a table that fills begins by itself and its options can no longer change): a long game so that no case ends it, or a short one.
- `bot({ state, me, seat, table })` — what a seat does when the game waits for it: the action to post (`{ type: "hit" }`), or `null` for the engine's `turn` debug command. `state` is the table as that seat reads it (`GET …/games/<code>`: `view`, `waitingFor`, `status`, `version`, `log`…), `me` its id.
- `warm: 6` — how many moves are played before a reload or an absence, so that there is something on the table.
- `scenes: { turn: async (table) => {}, … }` — the situations the windows are photographed in, in this order. The first is reached before the board opens, the others through the API while it stays open. Each brings the table to the situation: `await table.advance({ until: (state, who) => who === 0 && state.view.phase.kind === "turn", bot })`.
- `presses: { plan, find, expect, max, budgetSeconds, bot }` — `plan({ state, me, table, exercised })` is called when the game waits for the viewer and answers `{ label, prepare? }` (what to press, and an optional `async (table) => {}` that rigs the table first, for a situation that would otherwise be luck) or `null` (nothing to press: the move is played through the API); `find({ label, pressables, state, me })` answers the pressable to press from the list the board offers (`{ path, world: [x, y, z], size, pixel, reachable, why }`, `world` being the middle of the control on the table, x to the right and z toward the viewer: "the draw pile lies left of the middle"), or `undefined` while the board does not show it. `expect` lists the labels that should have been pressed by the end (a warning for the others, once `budgetSeconds` have gone, 150 s by default: a situation that takes many rounds is given that long), `max` caps the presses (60), `bot` is what the seats do between presses (default: the config's `bot`: a faster one brings the table sooner to a rare situation).
- `scenarios: { name: { run, record } }` (or just the function) — `run({ table, page, seats, name, settle, record, sleep })` reaches the case and returns `record(action, { seconds, step, lead })`, the frames of the move that `action` makes. `settle()` lets the board learn of the table's version and stand still (use it after a rigged move and before the recorded one); `table.rig(command)` sends a debug command of `GAME.debug`. A case that throws fails the check and the next one goes on.
- `ignoreConsole: [/\[missing/]` — patterns (RegExp, or text) of console messages that are not a failure here.

The `table` the config receives: `ids` and `names` (by seat, the viewer 0), `state(seat)`, `act(seat, action)` (throws when the game refuses), `rig(command, seat)`, `play(seat)` (the bot's move, else `turn`), `waitedFor(state)` (the seat the game waits for, -1 for nobody), `advance({ until(state, who), bot, max, label })` (plays everyone, the viewer included, until `until`) and `request(seat, method, path, body)` for any other route of the game's API.
