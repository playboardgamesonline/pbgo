# Scripts: add-game, game-rules, setup-env, check-game, check-board, check-scout, check-rules

`pnpm add-game "<name>"` (the pipeline), `pnpm add-game <slug>`, `pnpm game-rules`, `pnpm setup-env`, `pnpm check:game`, `pnpm check:board`, `pnpm check:scout` and `pnpm check:rules` in full; the Commands section of the root `CLAUDE.md` gives one line for each.

## Commands in full

- `pnpm add-game "<Game Name>" [--dry-run] [--yes] [--no-linear] [--new-session] [--redo <step>]` · `pnpm add-game --list` · `pnpm add-game --check` — the pipeline (`packages/pipeline`): a game from its name to the platform's catalog, one headless Claude Code step at a time (`/game-scout`, `/platform-catalog-entry`, then `/game-rules-spec`; `claude -p`, the owner's login, never a key) with a gate in the terminal after each (`validate`, or a message that says what to change; `publish` is a word of its own), the state of each game saved so that the command stops and resumes, a Linear parent issue and a sub-issue per step. It touches one place of the repo only, the rules spec (`docs/games/<slug>/`, left uncommitted), and publishes nothing before the word `publish`. In full below
- `pnpm add-game <slug>` — a new game from nothing to its Studio (its folder, its Sanity project, its Studio: the script the pipeline leaves to a slug and to the flags below; a name, with a capital letter or a space, starts the pipeline instead). On a terminal with no argument it asks the name, the slug and the rules PDFs; otherwise `pnpm add-game [<slug>] [--name "<Game Name>"] [--rules [<lang>=]<file.pdf> …] [--yes] [--dry-run] [--no-open] [--push]` (the slug comes from the name, a rulebook with no language is English). `setup-env --check`, the name, the slug and the PDFs are checked first (nothing is created when one fails); the summary lists what leaves the machine (Sanity project, Supabase migrations, Vercel variables) and asks before creating anything (`--yes` skips the question, `--dry-run` stops after the summary); then new-game + go-live + the rules PDFs in the draft of Settings + setup-env + a check that the Studio is deployed, which opens it on a terminal (`--no-open` does not). A step that fails does not hide the others: the run ends with "Left to fix", a command per problem, and exits 1. `--push` commits and pushes a branch for a pull request. The skill `game-new` (`/game-new <slug>`) runs it for the owner and goes on to the fields of the Studio
- `pnpm game-rules <slug> --rules [<lang>=]<file.pdf> [--rules …] [--dry-run] [--overwrite]` — a game's rulebook PDF per language into the draft of its `settings` (`rulesPdf<Lang>File`, Mechanics tab), whatever its size (the gamemaster's upload stops at 4.4 MB). A field that holds a file keeps it unless `--overwrite`; the same files again change nothing. The tool is `rulebook` of `@pbgo/content-kit` (`packages/content-kit/README.md`)
- `pnpm setup-env [--no-push | --check]` — applies the pending Supabase migrations (see `docs/supabase-and-env.md`), fills `apps/web/.env.local` (generating `ADMIN_SESSION_SECRET` and `CRON_SECRET`, the token of the nightly clean-up, once and appending them to the secrets file) and pushes the variables to the Vercel project `pbgo`, looked up by its id (`VERCEL_PROJECT_ID` of the secrets file, else `prj_bsk7OjC3wkJrI6ElHFa8bfD71xfs`), never by its name, through the API alone (no `.vercel/project.json`, no Vercel CLI, no CLI login: any worktree will do); aborts, touching neither `.env.local` nor Vercel, when a Supabase value is missing, a project can't be used or a migration fails (see `docs/supabase-and-env.md`). `--no-push` writes nothing to Vercel and neither reads nor migrates the production project. `NEXT_PUBLIC_POSTHOG_KEY` and `NEXT_PUBLIC_POSTHOG_HOST` (optional, both or neither) go to `.env.local` and to every Vercel target once `@pbgo/analytics` accepts the pair (a pair it refuses prints ✗ and is neither written nor pushed, the exit code does not change). `GEOAPIFY_API_KEY` (optional: the search of a city in the Edit profile window, to `.env.local` and every Vercel target; without it the window has no City field). `RESEND_API_KEY` and `RESEND_PREVIEW_API_KEY` (optional: the keys the site's own code sends e-mails with, for the link that reopens an account its member deleted; the first is the production key and goes to the Vercel production target, the second serves previews and local development and goes to the preview and development targets and to `.env.local`, as `RESEND_API_KEY`; one alone serves everywhere; a value that is not a Resend key, `re_…`, prints ✗ and is neither written nor pushed). `BGG_API_TOKEN` (optional, from the secrets file or `.env.local`: the token of the application registered at BoardGameGeek, which `content:bgg` reads its API with; it goes to `.env.local` only and is never pushed to Vercel, since the hub does not call BoardGameGeek). `STEAM_WEB_API_KEY` (optional, from the secrets file or `.env.local`: the key of Steam's Web API, 32 hexadecimal characters, which switches the Steam button of the sign-in on) goes to `.env.local` and to every Vercel target the same way (one of the wrong shape prints ✗ and is neither written nor pushed). `NOTION_API_KEY` is not handled any more: the hub reads no Notion since PLT-90, and the platform's seed takes the key from the environment or from `apps/web/.env.local` (`docs/catalog.md`). A Supabase variable already on the Production target (the Supabase ↔ Vercel integration manages them) is skipped, not overwritten, and the run still exits 0; it exits 1 only when the Vercel project can't be reached or a Vercel call really fails
- `pnpm check:game <slug> [--stage scaffold|engine|binding|board|content|live]` · `pnpm check:game --all` — how far a game has got on its way from a name to live (`scripts/check-game.mjs`). It reads files only: no network, no build, no secret. It reports six stages, each with checks that are `ok`, `warn` (look at it) or `fail`: `scaffold` (registered with a Sanity project, packages and notes there), `engine` (a rules spec, `docs/games/<slug>/rules.md`, as a warning when it is missing; the game's own, exports `GAME`, pure, up to date with the contract: `standings`, `progress`, no words, the contract suite; the layers of tests), `binding` (`GAME` exported, the three binding tests, `vitest.config.ts` running them), `board` (a board, three.js only in its folder, `Game` loaded lazily, hex colours counted, a `check-board.config.mjs` for `pnpm check:board`: a warning when it is missing), `content` (the Studio's guard, the seed, the plan in `CLAUDE.md`) and `live` (`live` and `indexable`). With `--stage` the command is a gate: exit 1 while a check up to that stage fails, exit 2 for a game or a stage that does not exist. `--all` prints each game of the registry with the last stage it passed and what stops it. `--json` prints one line of JSON (`slug`, `missing`, `reached`, `failing`) for the programs that ask (`pnpm add-game`); for a game with no folder the report says whether the game is in the pipeline. The skills of `.claude/skills/` say what to do about each failure ([How far a game has got](engine/04-build-a-game/01-steps.md#how-far-a-game-has-got)).
- `pnpm check:board <slug> [--players 3,5,8] [--sizes 1280x800,…] [--checks presses,sizes,scenarios,reload,opening,absent] [--scenarios a,b] [--out <dir>] [--reduced-motion] [--keep-tables] [--port 3100] [--absent-seconds 85]` — checks a game's board in a real browser (`scripts/check-board.mjs`, its parts in `scripts/check-board/`), so that nobody writes the scripts of `engine-board` step 6 again. It is no part of the six gates or of CI: it needs `pnpm dev` running (`http://localhost:3100`) and it opens and plays tables, so it names the Supabase project the dev server's `.env.local` points at before it writes anything and stops when that is the production project (`SUPABASE_PROJECT_REF` of the secrets file); the debug route it plays through answers 403 on a production deployment. It needs a Chromium in Playwright's cache (`npx playwright install chromium`: it fills `~/Library/Caches/ms-playwright`, nothing is added to the repo) and ffmpeg (`brew install ffmpeg`), and says which is missing (exit 2). Details below, in "`pnpm check:board` in full"
- `pnpm check:scout <file> [--online]` · `pnpm check:scout --list` — is a scout file, the JSON of the skill `game-scout` (`.claude/skills/game-scout`), what the pipeline reads? `packages/games/src/scout.ts` is the one definition (`scoutProblems`: every key there and no other, the name and the slug by the rules of `slug.ts`, a base game for an expansion and a reimplementation and none for a base game, the figures in their ranges, the complexity as BoardGameGeek's weight given by ten people at least, public https addresses, a source for the edition; what is said of a file is printable and short, whatever it holds), `packages/catalog/scripts/check-scout.ts` the command. With `--online` it also reads what exists (`stateProblems`): the registry (the game has no folder yet) and the published games and expansions of the platform's Sanity project through the public API, with no token, so that `existing.catalog`, the entry's own type and base game, the base game and a game that the catalog already has under another slug or as another type are checked (two names are one game only among their peers, the games and the expansions of one base game, unless BoardGameGeek tells the items apart). That is the state at the time of the scout: run it when the file is made, not after the entry exists. `--list` prints what a scouted game is compared with, one line each: slug, type, BoardGameGeek id, base game, folder in the repo and name. Exit 0 when sound, 1 for a problem or when the project cannot be read, 2 for a wrong command line. The command is run by Node itself, so `packages/catalog/src/check-scout-script.test.ts` runs it as `pnpm` does
- `pnpm check:rules <slug> [--name "<Game Name>"]` — is the rules spec of a game, the page of the skill `game-rules-spec` (`.claude/skills/game-rules-spec`), what the pipeline and the engine read? `packages/games/src/rules-spec.ts` is the one definition (`rulesSpecProblems`: the title `<name>: rules spec`, the eleven sections in their order and no other, the five lines of the edition with its status, the players and the goal, the table of the components (a kind, a name, a count, a description, a page), the pages cited in the sections that say the rules, the open points each with its four paragraphs, the glossary, and nothing a page of the docs may not hold: an HTML tag, a placeholder, a picture, an address that is not https, more than a thousand characters quoted from the rulebook; what is said of a page is printable and short, whatever it holds) and `indexProblems` for its landing page `docs/games/<slug>/index.md`, which the docs of the site need for the folder; `packages/games/scripts/check-rules.ts` is the command. `--name` checks the title against the game's name. Exit 0 when sound, 1 for a problem or a page that is not there, 2 for a wrong command line. `PBGO_GAMES_DOCS_DIR` moves the folder of the specs (a test's world). The command is run by Node itself, so `packages/games/src/check-rules-script.test.ts` runs it as `pnpm` does

## `pnpm add-game "<name>"` in full

**What it does.** A game from its name to the platform's catalog, one step at a time: `/game-scout` (which game, which edition, its figures, a `scout.json`), then `/platform-catalog-entry` (its entry in the platform's Sanity, as a draft, then published), then `/game-rules-spec` (what is in the box and the rules as the engine will follow them, one page of the docs with the cases the rulebook leaves open). Each step is a headless Claude Code call (`claude -p`, the owner's login, never an API key), and after each the command stops at a gate in the terminal: the skill's report and its links, then `validate` or a message that says what to change. It touches one place of the repo, the rules spec (below): what else it writes is the game's folder of working files outside it, the drafts (then the documents, on the word `publish`) of the platform's Sanity, and Linear issues. The steps that come after (the assets, the game's folder and Studio, the engine, the board, the content, go-live: "A game from A to Z" in `.claude/skills/README.md`) are added one by one to `packages/pipeline/src/steps.ts`.

**Which behaviour.** `scripts/add-game.sh` asks `packages/pipeline/bin/route.ts` (`routeArgs`, tested). A game's name (a capital letter or a space: it is not a slug, or two words) or a flag of the pipeline (`--check`, `--list`, `--redo`, `--new-session`, `--no-linear`) starts the pipeline; a slug, no argument, or `--name`, `--rules`, `--push`, `--no-open` run the script that makes the game's folder, as before (the skill `game-new` uses its forms).

**Before it starts.** `claude --version`; `claude auth status` (it must say `claude.ai`: an API key, a cloud provider or no login refuse, with `claude auth login` as the fix: the CLI has its own login, apart from the desktop app's); the three skills, `pnpm check:scout` and `pnpm check:rules` in the checkout; Composio among `claude mcp list` (the claude.ai connector, whose tools are `mcp__claude_ai_Composio__…`). A game that has a folder in the repo is not scouted: the command says so and gives the stage `pnpm check:game` computes. `--check` goes further with one short call (about a cent, Haiku) that tries the guard from a headless run: `apiKeySource` is `none`, a write in the game's folder passes, a write in the repo, a command on no list and a file of the repo that git ignores are refused, a skill's file can be read, Composio's tools are found. `--dry-run` runs the local checks, prints the plan (the steps, the model, the budget, the Linear issues) and calls nothing.

**The state** of a game is `<assets>/<slug>/pipeline.json` (`~/Companies/PBGO/assets`, `PBGO_ASSETS_DIR` moves it), next to its `scout.json` (and its `rules.pdf`, once there is one): outside the repo, never committed, so that the command comes back from any checkout. It keeps what the repo cannot say: for each step its status (`pending`, `running`, `gate`, `validated`, `failed`), the gate it waits at, the last report and its links, the rounds and the cost, the one session of the game, the Linear issues. The stages of `pnpm check:game` are never copied into it: for a game that has a folder the command prints what `check:game` computes (`--json`), and `check:game`'s message for a game with no folder says where the pipeline stands. A lock (`pipeline.lock`) stops two runs of one game. When the scout settles another slug at its gate the command moves the folder (the skill writes the file where `--out` says, whatever the slug it settles on).

**A step** is one call: `claude -p "/game-scout <name> --out <assets>/<slug>/scout.json" --output-format stream-json --verbose --permission-mode dontAsk --setting-sources project --settings <hook> --allowedTools ToolSearch WebSearch WebFetch --model sonnet --max-budget-usd 3 --session-id <uuid> --name "add-game: <name>"`, run from the repo's root, with stdin closed (the CLI waits three seconds for it otherwise) and the shell's environment minus every `ANTHROPIC_*` and `CLAUDE*` variable (a key takes over the login, and switches the claude.ai connectors, Composio among them, off; `USER` stays: the login is found through it) and minus `PBGO_PUBLISH_OK` and `PBGO_GUARD_*` (the command sets those for each call itself, so a shell that has them set gives a call no power). One session for the whole game: its first call makes it, every other call resumes it (`--resume`: also from another folder, and after Ctrl-C); the bookkeeping calls leave none. The owner's own settings (hooks, permission rules) and the checkout's local ones are left out of every call: `--setting-sources project` keeps the project's own, which is where its skills are (the claude.ai connectors load all the same). While it runs, one line per tool call; at its end the skill's report as it is, the cost, the usage of the plan, the calls the policy blocked (`✗ blocked: …`) and `claude --resume <id>` (a talk with the agent, from the terminal). What an agent wrote (a report, a failure, the line of a tool call) is printed and kept with no escape sequence or control character in it: it read web pages, and a terminal obeys what it is sent. The first event of a call says `apiKeySource`: anything but `none` stops the call before it does anything. A call that did not go well (not logged in, budget reached, interrupted…) ends the step as `failed` with the reason, and the command comes back to it by resuming the session. Each round's raw stream is kept in `<assets>/<slug>/.pipeline/logs`, named by the time it ended.

**The gates.** After the scout: the report, then `pnpm check:scout <file> --online` (a file that fails it cannot be validated), then `validate` (or `v`, `yes`, `y`, `ok`, `oui`, `go`; an empty line is not a yes), a message (it goes to the same session, the skill corrects, the check runs again, a new gate), `o` (opens the file, or the first link of the report that is the platform's own, its Studio or its site, never another address), `q` (stops: all is saved). After the catalog entry, two gates: the first, the drafts and their Studio link, `validate` saying they are right; the second, `publish`, the one word that publishes (`validate` there is refused). The report must say which documents `validate` would publish, in the skill's own sentence (`Validate publishes 2 documents (game-x, publisher-y)`: the count and the ids agree, each id is a `game-`, `expansion-`, `creator-`, `publisher-` or `category-` one); the second gate shows them, and without that sentence `publish` is refused (`b` goes back to ask for it). `publish` resumes the session that showed the drafts (never a fresh one, `--new-session` or not) with the skill's own yes, sets `PBGO_PUBLISH_OK=1` for that call alone (every other call gets `0`) and gives the guard those ids as the only documents it may publish. The skill's word that it published is not taken as done: the command asks the public API of the platform's Sanity (the published perspective, no token) for those ids, and a document it does not show keeps the step at the second gate, validated nowhere; an API that cannot be read is told, and the skill's own read-back is what is left. `b` goes back to change something; so does any call that is not the publication (a change, a resume): it brings the step back to its first gate. The hub has no preview of a draft (it reads `perspective=published` of one dataset): the Studio page is what to look at.

**The guard.** The mode `dontAsk` refuses what is not allowed. By name only read-only tools are allowed (`ToolSearch`, `WebSearch`, `WebFetch`, and for the catalog entry Composio's two lookup tools). Everything that writes or runs something is allowed by a PreToolUse hook (`hook/guard.ts`, registered by `--settings`, running `decide` of `src/policy.ts` on a policy file per call), and the hook is an allowlist, not a filter: what no rule allows is refused, not left to the mode (which lets `cat` or `grep` run, and with them any file of the repo). The agent reads web pages, so it is the one thing the policy does not trust. *Writes*: exactly the files of the step (the scout writes `scout.json`, the catalog entry no file), never the state, the lock, the policy, the settings or the log that sit in the same folder, never a file of secrets. *Reads*: the files of the repo that git does not ignore (a skill's file, the code), the step's own file outside it, nothing else; the owner's own configuration of Claude Code (`~/.claude`) is a secret like an `.env`, the project's `.claude/skills` is not. *`Bash`*: only the commands the skills run, by exact shape (`pnpm check:scout <file> --online` on a file of the game's folder, `pnpm catalog:list`, `pnpm check:game <slug>`, `content:bgg-lookup`, `date`, `mkdir -p` of the game's folder) and the `node -e` one-liners that are the skills' own, word for word (`ONE_LINER_BODIES`: only their arguments vary, and none starts with `-`, since Node reads the options that follow the code). *`Grep` and `Glob`* are refused: they read files the policy cannot judge one by one. *Composio*: only the server the command found (`claude_ai_Composio`; another connector with a tool of the same name is refused), its executor only for the slugs of the step. Sanity: the platform's project and dataset; before `publish`, the `create` or `createIfNotExists` of a draft that has its own `_id` (this game's, or a creator's, a publisher's, a category's) of the type its id says, and the `patch` of such a draft by id; at `publish`, a `createOrReplace` of a document the gate showed with the `delete` of its draft in one transaction, nothing else. Linear: an issue made in the Games team and its project; an issue moved (state, title) or commented only when the game already has it; queries; the one mutation that makes a label (a GraphQL with a comment or a block string is refused). A refusal gives the agent its reason, and every decision is added to `<assets>/<slug>/.pipeline/guard.log`. The hook fails closed: when it cannot read its policy, or fails on a call, it denies that call, and a hook that does not load leaves every write and every Composio call refused (nothing but the read-only tools is allowed by name). What the guard bounds is which documents are published and by whom, not what the published document says: the owner validates the drafts in the Studio and the skill publishes them from its own read of them, so a published body that differs from its draft is not caught (a publication through Sanity's own publish action, which copies the draft as it is, would let the policy promise that). `src/policy.test.ts` keeps the commands of the skills (each must still be in the skill's text, and allowed to its step); `src/guard.test.ts` runs the hook as a process.

**The rules spec.** The third step runs `/game-rules-spec <scout file>` after the catalog entry and is the one step that writes in the repo: `docs/games/<slug>/rules.md` (what is in the box, the rules the engine will follow, who sees what, the cases the rulebook leaves open each with a reading proposed, a glossary) and `docs/games/<slug>/index.md` (its landing page: the docs of the site need one for each folder, and `docs/games/` is a doc of the site like `docs/engine/`). The step's policy allows those two files by their exact paths and no other, `pnpm check:rules <slug>` for this game and no other command of the project, and reads the scout file and `rules.pdf`. They stay uncommitted in the checkout the command was run from: the game's first pull request (`game-new`) takes them. **The rulebook** is read from `<assets>/<slug>/rules.pdf`, because a PDF that an agent fetches with a web tool comes back as bytes and a file outside the repo is not readable otherwise: before the first call (and again before a change) the command itself fetches the address the scout found, `edition.rules.url`, which the owner validated at the scout's gate, to that file, unless it is there already (the owner's own, or an earlier fetch: never replaced). The fetch (`src/download.ts`) is bounded the way a command given an address must be: https and its own port only, no credentials, a host name and not an IP, a host whose every address is public (each hop of a redirect judged again, and the connection goes to the address that was judged), five redirects at the most, 60 MB, 90 s, and a file kept only if it starts with `%PDF-` and ends with `%%EOF`, written whole under another name and renamed. A fetch that does not succeed is told and the step goes on: the skill says where the PDF has to be, the owner puts it there and types `retry` at the gate (a rulebook that is a web page is read as it is). The agent downloads nothing. **The gate** shows the skill's report, then `pnpm check:rules <slug> --name <name>`: a page that fails it, or no page, cannot be validated (the check is run again at `validate`, so a page edited by hand is judged as it is). `validate` stamps the page, `- Status: validated <day>` and every `**Status.** to validate` set to `validated <day>`: validating accepts the readings of the open points, which the report says (`Validate also accepts the N readings of the open points`), so that `engine-rules` does not ask the owner for them again. `o` opens the page. When the game is added the command says where the pages are and gives the `--rules <lang>=<file>` of the script that makes the game's folder, with the PDF it fetched.

**Linear.** One parent issue per game ("<Name>: add the game") and one sub-issue per step ("<Name>: scout", Game lane; "<Name>: catalog entry", Platform lane; "<Name>: rules spec", Game lane), team Games, project Game factory, the game's label of the group Game (made when it is missing). The first step not validated is In Progress, the next Todo, the validated ones Done with a comment of the links; the parent stays open for the steps to come. The command holds no key: at the start (after the plan and the owner's ok), when the scout is validated and when the entry is published, one small call (Haiku, 0.30 $ at most) does a work order through Composio and answers with the ids; a failure is told and the game goes on, the next point tries again; `--no-linear` skips it. The call touches the issues the game already has (their ids are in its state) and makes the others in the state they should be in: it neither moves nor comments an issue it makes itself, the next point does. The ids are in `src/linear.ts`.

**Coming back.** The same command resumes: a gate that waits shows its report again and calls nothing; a step that was interrupted offers to resume its session; a failed step resumes it (a publication that failed is taken up as work, with no word, and the step is at its first gate again). `--redo <step>` puts that step and the ones after it back to not started (the skills fill and never replace); `--new-session` starts a fresh session for the next call (the context is cleared, the state stays); `--list` lists the games and where each stands. A closed input at a gate ends the command (exit 3) with the game saved; Ctrl-C ends it (130).

**Settings.** `PBGO_ADD_GAME_MODEL` (the steps' model, `sonnet`), `PBGO_ADD_GAME_BUDGET_USD` (a call, 3), `PBGO_ADD_GAME_LINEAR_MODEL` (`haiku`), `PBGO_ADD_GAME_LINEAR_BUDGET_USD` (0.3), `PBGO_ASSETS_DIR` (a path with no space or special character: the skills take it as one word); `PBGO_ADD_GAME_NO_DOWNLOAD=1` (the command fetches no rulebook: offline); for the tests `PBGO_CLAUDE_BIN`, `PBGO_CHECK_SCOUT_BIN`, `PBGO_CHECK_RULES_BIN`, `PBGO_GAMES_DOCS_DIR` (where the pages of the specs are written, `docs/games` of the checkout) and `PBGO_SANITY_API_BASE` (where the publication is read back).

**Tests.** `pnpm --filter @pbgo/pipeline test`: each part on its own (the events are the real ones of the CLI 2.1.299), the hook as a process, and the whole command as a process against a stand-in `claude` (`test/fake-claude.mjs`), a stand-in for the platform's public API (a local server, a closed port when a test starts none) and a temporary world: nothing reaches the network, the login, Linear or Sanity. What no test can say, and the first run on a game does: that the three skills do their work inside the policy (a command or a path it forgot shows as `✗ blocked` at the gate), and the real Composio calls of the catalog entry and of Linear.

**A next step** is a skill (`.claude/skills/<prefix>-<job>`), a `StepDefinition` in `src/steps.ts` (prompt, gates, what it may do) and its line in the table of `.claude/skills/README.md`.

## `pnpm check:board` in full

**What it does.** Guests are seated through the game's API, each with a cookie jar of its own (so each is a player). The viewer, seat 0, is a headless Chromium on `http://localhost:3100`, the only origin besides production and the Studio that the game's Sanity CDN lets read its pictures, so the cards show their faces (on another `--port`, because a second dev server runs beside the first, the tool fetches those pictures itself, as that origin, and hands them to the page); the other seats exist only in the script and play through the API, at a table opened for the number of seats that is checked (a table opens for the median of the game's players unless it is told how many). The tool sees a board without any help from the game: three.js tells `globalThis.__THREE_DEVTOOLS__` about every renderer and scene it makes, the tool installs that hook before the page's scripts run, and so it holds the camera that draws the table and the objects that react-three-fiber gave a click handler, which is what the board offers to press. For each of them it works out the pixel where a pointer reaches it (react-three-fiber's own raycaster, and `document.elementFromPoint` for whatever the page puts over the canvas: the cookie banner, a box of the HUD) and says why when there is none. No coordinate of the game is copied into the tool. It leans on two internals of react-three-fiber 9 (`object.__r3f.handlers` and `scene.__r3f.root.getState().raycaster`) and on three.js's devtools hook, so after an upgrade of either package run it once on Flip 7: a scan that finds no control is the sign.

**The checks**, in this order, each with its own table and browser, the tables left at the end (the guests leave, and the last to leave deletes a table; `--keep-tables` keeps them). Before them a `warm-up` opens the board of one table, so that a server that compiles on demand has compiled it; when no board draws the run stops there instead of failing every check in turn. A board is measured and photographed once it is shown (the platform's loading screen has lifted), has stood still (the camera and the canvas) and has had 3.5 s for the announcement of the start of the game, which lies over it in the page, to go.
- `presses` — (in the first window of `--sizes`, like every check that is not about the windows) plays the viewer's side with the mouse, as a person would: the game's config says what is next (`presses.plan`) and where the control is (`presses.find`), the tool waits until the board has been told the table's version, scans the pressables, moves the pointer and presses, then reads the table through the API and expects its version to have changed. Fails when the board offers no control for it, when it cannot be reached (and says what lies over it), or when two presses change nothing. A game with no `presses` in its config skips it.
- `sizes` — the board in each window of `--sizes` (default: 1280x800, 1280x720, 1440x900, 1920x1080, 2560x1080, 1024x640, 1024x768, 900x600, 1024x1366, 900x1200), in each situation of the config's `scenes` (default: the viewer's move), as one sheet per situation (`sizes-<seats>p-<scene>.png`, a window to a tile, in the order of the list). In each window it measures what the platform lays over the board (the `overlays` of the report), whether the page scrolls sideways, where the camera stands, and whether every control can be pressed: in the first window every control must be reachable (a failure), in the others a covered control is a warning (a table may lie under the platform's boxes in a small window).
- `scenarios` — the cases that `GAME.debug` can rig, each recorded as frames (`Page.startScreencast`) and tiled into nine from the first change of the page's text (`scenarios-<seats>p-<case>.png`; the frames are in `frames/`). The config lists the game's own (a special card, a bust, a save); every game gets `turn` (one turn played by the engine's `turn` command) and `over` (the game played to its end, the end screen). One table serves all of them, in order, `over` last.
- `reload` — a few moves are played, the board is opened and left to settle, then reloaded with a screencast running: the sheet starts when the platform's loading screen lifts, and the canvas is sampled while the camera stands still. A warning when it keeps changing (cards that fly in again); a failure when the board does not come back or the table moved.
- `opening` — the normal start, not the debug one: the host starts the table, the board loads behind the start screen, the others say they are ready, the viewer presses "I'm here" and the sheet shows the opening. A failure when the start screen never offers its button or the table does not begin. A table that fills begins by itself (the most seats): the host has nothing to start.
- `absent` (the fewest seats only) — the other seats read nothing for `--absent-seconds` (85 s, the platform counts a seat present for 75 s), then the board must still draw, the page's text and a screenshot are kept, and the platform's "Play for them" is pressed: the table must move.

**What fails the run (exit 1).** A board that does not draw within two minutes (no canvas, or a canvas with no scene, or the platform's screen over it for ninety seconds), an error the page printed (`console.error`, an exception, a resource that failed, an answer of the API that is a 5xx or 429; `ignoreConsole` of the config silences the ones that are known, and the 404 of a lazy chunk that Turbopack names with another hash than the one it serves is shown as a warning), a press that changes nothing, a case the game refuses, a table that does not begin. A warning is to look at and never fails: a board that never stood still, a page that scrolls sideways, a covered control in a small window, a table that kept moving after a reload, a case whose page text never changed. Exit 2: it could not run (no server, no Chromium, no ffmpeg, a seat count the game does not take, a wrong config, the production project).

**What it writes** to `--out` (default a folder of the system's temporary files, `<tmp>/check-board/<slug>-<time>`; keep it out of the repo, a pull request holds no screenshot): `report.json` (rewritten after every check: the project, the browser, one entry per check with its `status`, `problems`, `warnings`, `files`, the data it measured and its duration), the sheets (`*.png`, a sheet is 3 columns of cells, the frames in the order the report lists) and `frames/` (every frame a sheet is made of, full size, to look at one). Long: a run of every check at three counts of seats takes about twenty minutes (17 for Flip 7), so run it in the background and read `report.json`; `--players`, `--checks`, `--sizes` and `--scenarios` cut it to what changed.

**What it does not check.** The board on a phone (below 900 px the platform covers every game page with its desktop-only screen unless the game turned it off: `--sizes 390x844` photographs whatever the page shows, with a finger emulated), a drag, a sound, and whether a sheet looks right: a person or an agent reads the sheets, and the pull request says what was seen.

### The game's config: `games/<slug>/check-board.config.mjs`

Optional, plain JavaScript run by Node (it imports nothing of the game, whose board files are TypeScript for the bundler), its default export an object whose every key is optional, so a game with no file is still checked as far as the platform's own parts allow (a board that draws, the windows, the engine's `turn` and `over`, a reload, the start, a player who is away). `games/flip-7/check-board.config.mjs` is the model. A key that is not in the list below is refused, so a typo is told.
- `players: [3, 5, 8]` — the counts of seats (default: the fewest, a middle count and the most of the registry's `players`, at most 12); `--players` wins.
- `sizes: ["1280x800", …]` — the windows; the first is the one every control must be reachable in.
- `options: { targetScore: 500 }` — the game's options for the tables of the checks, set before the others sit down (a table that fills begins by itself and its options can no longer change): a long game so that no case ends it, or a short one.
- `bot({ state, me, seat, table })` — what a seat does when the game waits for it: the action to post (`{ type: "hit" }`), or `null` for the engine's `turn` debug command. `state` is the table as that seat reads it (`GET …/games/<code>`: `view`, `waitingFor`, `status`, `version`, `log`…), `me` its id.
- `warm: 6` — how many moves are played before a reload or an absence, so that there is something on the table.
- `scenes: { turn: async (table) => {}, … }` — the situations the windows are photographed in, in this order. The first is reached before the board opens, the others through the API while it stays open. Each brings the table to the situation: `await table.advance({ until: (state, who) => who === 0 && state.view.phase.kind === "turn", bot })`.
- `presses: { plan, find, expect, max, budgetSeconds, bot }` — `plan({ state, me, table, exercised })` is called when the game waits for the viewer and answers `{ label, prepare? }` (what to press, and an optional `async (table) => {}` that rigs the table first, for a situation that would otherwise be luck) or `null` (nothing to press: the move is played through the API); `find({ label, pressables, state, me })` answers the pressable to press from the list the board offers (`{ path, world: [x, y, z], size, pixel, reachable, why }`, `world` being the middle of the control on the table, x to the right and z toward the viewer: "the draw pile lies left of the middle"), or `undefined` while the board does not show it. `expect` lists the labels that should have been pressed by the end (a warning for the others, once `budgetSeconds` have gone, 150 s by default: a situation that takes many rounds is given that long), `max` caps the presses (60), `bot` is what the seats do between presses (default: the config's `bot`: a faster one brings the table sooner to a rare situation).
- `scenarios: { name: { run, record } }` (or just the function) — `run({ table, page, seats, name, settle, record, sleep })` reaches the case and returns `record(action, { seconds, step, lead })`, the frames of the move that `action` makes. `settle()` lets the board learn of the table's version and stand still (use it after a rigged move and before the recorded one); `table.rig(command)` sends a debug command of `GAME.debug`. A case that throws fails the check and the next one goes on.
- `ignoreConsole: [/\[missing/]` — patterns (RegExp, or text) of console messages that are not a failure here.

The `table` the config receives: `ids` and `names` (by seat, the viewer 0), `state(seat)`, `act(seat, action)` (throws when the game refuses), `rig(command, seat)`, `play(seat)` (the bot's move, else `turn`), `waitedFor(state)` (the seat the game waits for, -1 for nobody), `advance({ until(state, who), bot, max, label })` (plays everyone, the viewer included, until `until`) and `request(seat, method, path, body)` for any other route of the game's API.
