# Catalog

The list of games the hub can show: the live games of the registry and the planned games of the Notion Games database, joined by `@pbgo/catalog`. Part of PLT-56 ("the hub catalog shows every game").

## What exists
- Step 1 (PLT-71): the reader and the join, in this package. Step 2 (PLT-72): the route that serves the pictures of the planned games, `/api/catalog/<slug>/<logo|icon|background>` (below), and the reader brought up to the Notion database as it is since 2026-10-24 (`Authors`, `Illustrators` and `Editors` relations, the Creators database, no more `Status`, `Priority` or `Effort` on the Games rows), with the coming-soon games ordered by the Games Development database (below), then by name. Steps 3 and 4 (PLT-73, PLT-74): the hub reads the catalog and lists every game in one list, and each card opens the game's own page on the hub, `/game/<slug>`, whether the game is live or to come, and the page ends with the games related to it (below). `[game]`, the game's own site, still serves the registry's slugs only
- Next, one pull request, started after the previous one is merged: the SEO pass (PLT-75). This file describes what has landed; each step updates it

## Where a game comes from
- A **live** game (`live: true` in `packages/games/src/registry.ts`): the registry and the game's own Sanity project. Its Notion row, if any, is ignored
- A **planned** game: its row in the Notion Games database, whatever its status. A game of the registry that is not live takes its row too, and Notion's name with it; with no row it is not listed
- `template` is never listed (`UNLISTED_SLUGS`), and neither are the expansions: a row whose `Parent item` is filled is counted and left out, unless its `Type` is `Standalone expansion` (today 20 of the 51 rows are left out; the 2 standalone ones, Flip 7 Vengeance and 6 nimmt! 25 Jahre, are listed)
- No sync to Sanity: Notion is read, never copied. The registry stays the source of the slug, `live` and the Sanity project

## The package (`packages/catalog`, `@pbgo/catalog`)
- `.` (`src/catalog.ts`, pure: no I/O, no framework) — the types (`PlannedGame`, `DevelopmentRank`, `CatalogEntry`, `Catalog`, `Publisher`), `buildCatalog(games, planned)`, `comparePlanned`, `UNLISTED_SLUGS`, `pickLocalized(values, locale)`, `ART_SLOTS`, `pictureUrl(game, slot)`, `cardPictureUrl(game)` (the logo of a card, else its icon), `pictureVersion(editedAt)`
- `./server` (`src/server.ts`, server only) — `getCatalog()`, `CATALOG_TAG`, `CATALOG_REVALIDATE_SECONDS`, `notionToken()`, `reportOnce(message)`. `getCatalog` is the one call a page makes
- `./route` (`src/route.ts`, server only) — `pictureRoute()`, the handler of the picture route; `apps/web/src/app/api/catalog/[slug]/[slot]/route.ts` is `export const GET = pictureRoute()`
- `src/notion.ts` — the reader, `readPlannedGames({ token, fetch?, init?, timeoutMs? })`: a plain `fetch` against Notion's REST API (`Notion-Version: 2022-06-28`), no SDK, no framework. It reads the Games database and, alongside it, the Editors and Creators databases that the relations of a game point to, and the Games Development database that ranks the planned games. The caller hands in the token and the cache options. `readPictureLinks(options)` reads the Games database alone for the links of the pictures. A failure is a `NotionError` (`status`, `code`, and for a 429 the `retryAfter` it asks, in seconds)
- `src/picture.ts` — `fetchPicture(link)`: downloads a picture from a link and checks it (below)
- `scripts/list.ts` — `pnpm catalog:list`; `src/testing.ts` — the fixtures of the tests (a row as Notion writes it, a fake Notion, fake picture hosts), not exported
- Order of the list: the live games (registry order), then the planned ones by their rank in the Games Development database, then by name (`comparePlanned`, below). A live game is never ranked: it is the registry's, wherever its Notion row and its rank say it would be. `Hotness` is not read: nothing says what it would mean for the hub
- `pickLocalized` gives a text for a visitor: their language, else English, else French, else any other; it says which one it took, so a page can mark a text that is not in the visitor's language

## The Notion databases (`notion.ts` holds the ids and the column names)
- **Games** `3ffd1ca3-468f-80e8-a371-ed666deecc9a`, **Editors** `3ffd1ca3-468f-80e0-ba62-fb466ca8a6c8` (publishers: `Name`, `URL`) and **Creators** `5712daa0-497d-4fa7-9634-1c2320f4446d` (the people: `Name`; its `Role` is not read, the column of the game says whether a person is an author or an illustrator)
- **Games Development** `401d1ca3-468f-8159-a5c2-fbf706218640`: the tasks database, one row per game (its title is the game's slug). `Game` is the relation to the Games row; `Priority`, `Status` and `Effort` rank the game (below)
- The integration must be connected to all four databases (Connections of each one): without Editors no game has a publisher, without Creators no game has an author or an illustrator, without Games Development the coming-soon games are listed by name (the Games database alone still works, with a warning for each)
- `Slug` (text) is the slug of the page, written by hand: a row with none is skipped, never guessed. A slug must pass `slugProblem` (`@pbgo/games/slug`: not a reserved slug, lower-case, 40 characters at most); two rows with one slug: the older row wins, the other is reported
- Shown: `Name`, `Description FR|EN|ES|DE`, `Players` (`4`, `2 - 5`, `3+`), `Duration` (minutes), `Age` (`8+`), `Authors` and `Illustrators` (relations to the Creators database), `Editors` (relation to the Editors database), `Rules FR|EN|ES|DE` (links, http(s) only), `Logo`, `Icon`, `Background`. A relation is read in the order Notion keeps it; a row it points to that has no name, or that the integration cannot see, is dropped without a word. A query hands back 25 related rows of a column at most, far more than a game has
- `Parent item` and `Type` tell an expansion from a game. A row whose `Parent item` is filled is an expansion of that game: counted and left out, never reported. Unless its `Type` (a select: `Base game`, `Expansion`, `Standalone expansion`) is `Standalone expansion`: it plays without its base game, so it is a game of its own, read and listed like any other (with no slug it is reported as skipped, not counted as an expansion). A row with no `Parent item` is a game whatever its `Type`. Without a `Type` column the reader says so, like for any column, and every row with a parent is an expansion again
- `Related Games` (a relation to the Games database itself, one way) and `Parent item` are the links between games, and `related` of a catalog entry is built from both: the slugs its own row points to in either column, plus those of the games whose rows point to it, so a link written on one row is enough. A link to an expansion, to a row with no slug or to a game the catalog does not list (`template`) is left out, a game is never related to itself, and the list follows the catalog's order. A live game's Notion row, ignored for everything else, still gives its links. So the base game of a standalone expansion is one of its related games, and the expansion one of the base game's. `Expansions`, the same link seen from the base game, and `Relation kind` (`Spin-off`, `Re-skin`) are not read
- Every other column is ignored: `Hotness`, `Development` (the relation to the database below: the join is read from the other side, the `Game` column of each Development row), `Tags`, `Game family`, `Release date`, the BGG columns, the fonts, `Expansions`, `Relation kind`, `Other contributors` and the dates. The Games database has no `Status`, `Priority` or `Effort` any more (they live in Games Development now), which the first reader used to order the list
- The pictures are only flagged (`art`): a file that Notion hosts has a link that expires after about an hour, so a link is never kept in the cache. `notionPageId` finds the row again and `editedAt` changes when the row does; the picture route serves the picture from a fresh link. A link to somewhere else (`external`) counts only if it is https: a picture with any other link is not flagged
- A row of the Games database that is archived or in the trash is ignored. Text is trimmed and control characters are removed from what a row says about itself, the names of people and publishers included (it goes to a terminal and to the logs)
- A column that is missing from the database (renamed, deleted) is not an error: the field is empty for every game and the reader says so (`The Games database has no "<column>" column`). A database without `Name` or `Slug` is not the Games database: the read fails. So does a database of more than 1 000 rows (ten requests of 100, twenty times today's), which is a runaway cursor more than a catalog

## The order of the coming-soon games (the Games Development database)
- The sort is the one of that database's own "Table" view, copied into `comparePlanned`: Priority ascending (`P1 · Now` first), then Status descending (the last status of the column first, today `Live`, `Paused`, `Playtest`, `Table`, `Content`, `Engine`, `Rules`, `Not started`), then Effort ascending (`S` first), then the name (case-insensitive, accents aside, numbers in order, so `6 nimmt!`, `7 Wonders`, `10 Minutes`, `Bang`). A game with no value in a column comes after those that have one, in either direction. It is a copy of the sort, not a link to it: changing which columns the view sorts on, or the direction of one, changes nothing here until `comparePlanned` changes with it; moving an option inside a column does (next point)
- A game is ranked by the place of its option in the column's own list of options (the order the options have in Notion, not their alphabet), which is how Notion sorts a select or a status. The reader therefore asks for the schema of the database as well as its rows, and renaming, adding or moving an option in Notion moves the games. A value the column does not have any more counts as empty
- The join: the `Game` relation of a row names the row of the Games database it ranks. A row with no `Game`, or whose game is not in the catalog, ranks nothing; a row that ranks several games ranks each of them; a game with two rows takes the older one (the way a slug does); an archived or trashed row is ignored
- `PlannedGame.development` is `{ priority, status, effort }`, each one `{ position, name }` or `null`, so that `pnpm catalog:list` shows what ordered the list. It is part of the cached catalog: a change in Notion shows after ten minutes like any other
- It never fails the catalog. When the database or its schema cannot be read (the integration is not connected to it: Notion answers a 404 `object_not_found`), no game is ranked, the coming-soon games are listed by name and the reader says so once. A column that is missing or of another type is left out of the order, with a warning of its own

## The hub (`apps/web/src/app/(hub)/page.tsx`)
- It reads `getCatalog()` and draws every entry in one grid, in the order the catalog gives (the live games, then the games to come): the page never sorts or splits again, and status and priority only sort, no card shows them. With no planned game (no key, Notion unavailable) the list is the live games alone, what the hub showed before the catalog. The hero button, "Play <name>", is the first live game and goes straight to its own site, `/<slug>`
- Every card is the same tile, `GameCard` (`@pbgo/ui/platform/game-card`, drawn on `/design`): the game's logo, contained and not cropped, over its background picture on a grey 4:3 frame (`bg-muted`, a platform token), the background darkened by a scrim between the two (`bg-scrim/70`, so that the logo stands out; a frame with no background has none), then its name, on one line and cut with an ellipsis when it does not fit, and two facts, its players and its duration (`UserMultipleIcon` and `HourglassIcon`), and nothing else: no tagline, no placeholder. A picture the game does not have leaves the frame plain; with neither, the frame is a plain grey and the name sits under it
- A live game is `variant="play"`: its logo is the `logo` of its Sanity `settings` and its background the `background` of its Sanity `interface`, both read by `gameCardArt` (`packages/core/sanity/cover.ts`, one request, cached 60 s and tagged like the settings and the skin, so that saving either in the Studio refreshes the card), its facts come from the registry. That `background` is also the picture drawn behind the game's own home, so uploading one for the card changes the home too. A game to come is `variant="soon"`: its logo is `cardPictureUrl(game)` (the logo, else the icon) and its background `pictureUrl(game, "background")`, both from the picture route, its facts are `plannedFacts` (worded like a live game's), and a small "Coming soon" badge sits at the top right of the card
- Every card is a plain `<a>` to the game's page on the hub, `/game/<slug>` (below), the games to come as much as the live ones. `GameCard` requires an `href`, so a card that goes nowhere cannot be drawn; `gameCardProps` and `plannedCardProps` (`apps/web/src/lib/game-card-props.ts`) hold that one rule
- Only the card of a live game, and the hero button, carry `data-game`: analytics counts the games opened from the hub (`game_opened_from_hub`), and a game to come is not one. The click on a live card now leads to the game's page on the hub rather than into the game (`docs/analytics.md`)
- The picture of a card is `GameCardVisual` (`@pbgo/ui/platform/game-card`), which the page of a game draws too, larger (below). `livePicture` and `plannedPicture` (`apps/web/src/lib/game-card-props.ts`) choose its two pictures for the card and for the page alike, and `catalogCardProps` (`apps/web/src/lib/catalog-cards.ts`) is the one place that tells a live entry from a planned one, for the cards of the home and for the related cards of a game's page. Those related cards carry no `data-game` either: the listener is mounted on `/` only

## The page of a game (`apps/web/src/app/(hub)/game/[slug]/page.tsx`)
- Every game of the catalog has one, live or to come, at `/game/<slug>`, in the hub layout and the platform look. `getGamePage(slug)` (`apps/web/src/lib/game-page.ts`) finds the entry in `getCatalog()` and builds what the page draws; a slug the catalog does not list answers 404 (`(hub)/not-found.tsx`). So a game of the Notion database has a page only while Notion answers: without a key, or with Notion down, the catalog is the live games alone and every other slug is a 404
- It shows the name, a line of figures under it (the players and the duration, worded like the card, then the age of a game to come: "Ages 8+"), the description, the credits, the rulebooks and a picture. A field with no value is not drawn and no text is written in its place. A live game takes its tagline from the registry, its description, authors, publisher and rulebooks from the `settings` of its own Sanity project (`loadSettings`; they hold no age, so a live game shows none). A game to come takes the description, the age, the authors, the illustrators, the publishers (a link when the Notion row has their URL) and the rulebooks of its Notion row. The picture, next to the text on a wide screen, is the one of the game's card drawn larger (`GameCardVisual`): the logo over the background on the grey frame, with the scrim between the two when there is a background, and a plain frame when the game has neither, no placeholder. A live game's two pictures are read by `gameCardArt` (the `hero` of its skin is not used here any more), a game to come's come from the picture route. The description goes through `pickLocalized` (the visitor's language, else English, French, any other) and is marked with the `lang` it was found in
- Under the text, the credits follow one another, one line each (Author, Illustrator, Publisher; a live game has Credits and Publisher), then the rulebooks have an area of their own: one link per language the game has a rulebook in, the visitor's language first and the others in `LOCALES` order (`rulebooks` in `game-page.ts`). Each one is a bordered, button-like link (`Item`) that opens the PDF in a new tab: the language's code (EN, FR, ES, DE) on a grey chip (`Badge`, hidden from screen readers, the link carries the `lang`), the title in that language with the game's name ("Règles du jeu - Flip 7", "Rulebook - Flip 7"), then an arrow up-right. The words before the name (`RULEBOOK_TITLES`) are a platform text, in code: a game to come has no Sanity project to read them from
- The games related to it end the page, under a "Related games" heading, as cards like the home's (`catalogCardProps`: a live card or a card to come, with no `data-game`) in a grid that follows the width; a game with none has no such section. They are the `related` of its catalog entry, built from the `Related Games` and `Parent item` links of the Notion rows, whichever row holds the link (above): the base game of a standalone expansion and that expansion show on each other's page, and a live game shows the planned games related to it
- The button: a live game has "Create a game", a plain `<a href="/<slug>">` to the game's own site (another root layout, loaded whole): the table is created there, not from the hub. A game to come has the same button, disabled, labelled "Coming soon". "Live" is the registry's flag (`CatalogEntry.live`, pure data), not `isPlayable(game)`, which needs the loaded binding and is also true outside production for every game with an engine: the hub says the same in production and in a preview
- `noindex`: `robots.txt` has no rule for `/game/<slug>` (`/*/game/` needs a segment before `game`: it keeps crawlers off the tables), so the page sets `robots: { index: false }` itself, and the sitemap does not list it. Which of these pages search engines get, with their metadata and share image, is the SEO pass (PLT-75)
- `game` was already a reserved slug, being a segment of the table's address (`/<slug>/game/<code>`). `/game/<slug>` has two segments and a table three, and the static `game` wins over `[game]`, so the two never meet

## Cache and failure
- `getCatalog` is wrapped in React's `cache` (one read per request); the Notion calls themselves are cached by Next for ten minutes (`next: { revalidate: 600, tags: ["catalog"] }` on the `fetch`, which is what makes a POST cacheable; the stale answer is served while a fresh one is fetched). `revalidateTag(CATALOG_TAG, { expire: 0 })` makes the next read ask Notion again. Next does not cache an answer over 2 MB (the Games database is about 370 KB)
- Notion is the one optional part. Without `NOTION_API_KEY`, or when Notion does not answer (a bad key, a database not shared, a timeout of 5 s per request, an outage), the catalog is the live games alone, exactly what the hub showed before, `notion` is `"off"` or `"unavailable"`, and a Notion-only slug has no page (`/game/<slug>` answers 404)
- What is wrong is logged once per distinct line and per server instance, as `[catalog] …` on `console.warn`: Notion unavailable, the Editors, the Creators or the Games Development database not readable, a missing column, a row left out and why. Nothing logged holds the token

## The picture route (`GET /api/catalog/<slug>/<logo|icon|background>`)
- Why it exists: the pictures of a planned game are files of its Notion row, and Notion's links to them expire after about an hour, so the catalog only flags them (`art`) and this route serves them: it asks Notion for a fresh link, downloads the picture and sends it, and the CDN keeps it. A page draws a picture from `pictureUrl(game, slot)`, the route followed by `?v=<pictureVersion(editedAt)>`, the version of the row the catalog read. A live game's pictures are in its Sanity project and never come through here
- No picture is no error page: the answer is a 404 and the page that asked draws a plain grey frame (`bg-muted`, a platform token: no initials, no placeholder art). The cards of the hub and the pages of the games (`/game/<slug>`) draw it (above)
- The order, so that nothing costs more than it has to. 1) The slot is one of the three and the slug is a planned game of the catalog whose row has that picture, else 404 (503 when Notion could not be read at all: the game may well exist). 2) `v` is the current version of the row, else a 307 to the right URL, before anything is read or downloaded, so nobody can make the server fetch a picture under a `v` of their own. 3) A fresh read of the Games database for the links, then the download

| Answer | `Cache-Control` |
| --- | --- |
| 200, the row is still the one `v` names | `public, max-age=3600, s-maxage=86400` |
| 200, the row was edited since the catalog read it | `public, max-age=60, s-maxage=60` |
| 307 to the current `?v=` | `public, max-age=0, s-maxage=10` |
| 404 | `public, max-age=60, s-maxage=60` |
| 503, with `Retry-After` (Notion, the catalog or the picture host cannot answer now) | `no-store` |

- Every 200 carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, like the media route. Its `Content-Type` comes from the file's first bytes (PNG, JPEG, GIF, WebP, AVIF, SVG), never from what the host said
- One read serves a whole page: the links read from Notion are believed for 30 s, one read runs at a time however many pictures ask for it, a failed read is remembered for 5 s (or as long as Notion's `Retry-After`, when longer), and a 429 that asks for 3 s or less is waited for once. A hub of 66 pictures on a cold server is one query, not 66, which Notion's rate limit (about 3 requests a second) would not take. The memo is per server instance
- What the server fetches (`picture.ts`, the one place that does it): the visitor gives a slug and a slot, never a URL. The link comes from Notion and must be https, with no credentials and the default port; an IP address, a name without a dot, `localhost` and the names a network keeps for itself (`.localhost`, `.local`, `.internal`, `.localdomain`, `.home.arpa`) are refused. A redirect is followed by hand, three at most, each one checked again. One 8 s limit covers the download, the size is capped at 4 MiB while the body streams (a function answers 4.5 MB at most), and the file must be a picture by its bytes. Notion's token goes to Notion only: the picture host gets `Accept: image/*` and nothing else. The logs name the host, never a link (a Notion link carries a signature)
- Limits, on purpose:
  - The server does not resolve names, so a public name that points at a private address (`127.0.0.1.nip.io`) passes: the links come from the Notion workspace, trusted as far as whoever can edit it
  - A row's version is its `last_edited_time`, which has a minute's grain: two edits of one row within the same minute keep the old picture until the row is edited again
  - A picture added to a row shows once the catalog has read the row again (10 minutes) and a cached 404 has expired (1 minute)
  - `getCatalog` has no single flight across concurrent requests: a server that has just started and is asked for many pictures at once may answer a few 503s (`no-store`, nothing is kept). A page that draws the pictures has already read the catalog to build their addresses, which warms the cache

## The key (`NOTION_API_KEY`)
- A read-only internal integration (Notion › Settings › Integrations › New integration, capability "Read content" only, no user information), connected to the Games, Editors, Creators and Games Development databases (Connections of each database). Its secret starts with `ntn_`
- The secret goes in `~/.config/pbgo/secrets.env` (outside the repo) as `NOTION_API_KEY=…`, never in a chat, a commit or a pull request. `pnpm setup-env` writes it to `apps/web/.env.local` and pushes it to every Vercel target (encrypted; `--no-push` keeps it local); a deployed value applies from the next deployment. It only checks the shape of the value (`ntn_…` or `secret_…`): a value of another shape is neither written nor pushed and is not repeated in the message. Nothing is sent to Notion
- To try it before `setup-env`, put the same line in the `apps/web/.env.local` of the checkout (the script falls back on it) and run `pnpm catalog:list`
- The key stays server side: it has no `NEXT_PUBLIC_` prefix and no client component imports `@pbgo/catalog/server`

## `pnpm catalog:list`
What the hub would list right now: one line per game (slug, name, kind — `live` or `planned` —, the Priority / Status / Effort that rank a planned game, which of Logo / Icon / Background and which description languages are filled, players, duration, age, authors, illustrators, publishers, the games related to it) and, under it, the rows Notion has that are not in the catalog and why (no slug, a slug that is not valid, a slug already taken), the columns that are missing and the databases that cannot be read. It reads `NOTION_API_KEY` from the environment or `apps/web/.env.local`, queries each of the four databases once, caches nothing and never prints the token. Without a key it lists the live games and says so; if Notion cannot be read it prints why and exits 1. Run it after filling the Slug column of a new row: a row that is not in the list is not on the site

## Working on the package
- `pnpm --filter @pbgo/catalog test` and `pnpm --filter @pbgo/catalog typecheck`. The tests run the reader against a fake Notion built from the shapes Notion really answers (`src/testing.ts`); a new field = the column in `COLUMNS`, the field of `PlannedGame`, its line in `planned()`, the fixture in `gamePage`, a test (a column that is a relation to another database goes through `readRelated`, and `fakeNotion({ games, editors, creators, development })` answers that database; `developmentSchema` replaces the schema it answers for Games Development)
- The picture route is tested against a fake Notion and fake picture hosts (`fakeWeb`), never the network: the answers, the headers, the memo and the refused links. A change to `route.ts` or `picture.ts` is checked by breaking it on purpose and seeing a test fail
- The source is run as it is by Node (`pnpm catalog:list`, type stripping) and bundled by Next (`transpilePackages`): in `src/`, a value import from a sibling file has no extension that both accept, so a file imports only types from its siblings (`import type`) and the pieces that need each other meet in `server.ts`, `route.ts` and `scripts/list.ts`; `scripts/` import with `.ts` extensions. `picture.ts` imports nothing at all. `server-only` throws under plain Node, so only `src/server.ts` imports it (the tests of `server.ts` and `route.ts` mock it). `list-script.test.ts` runs the script under plain Node to keep this true
