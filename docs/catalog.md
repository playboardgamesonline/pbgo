# Catalog

The list of games the hub shows: the live games of the registry, then the games to come of the platform's own Sanity project (`docs/platform-sanity.md`), joined by `@pbgo/catalog`. Every game on the hub, a live one as much as one to come, shows the values of its `game` in that project; the registry only says which of them can be played. Part of PLT-56 ("the hub catalog shows every game"); PLT-83 made one row the hub's source for every game; PLT-90 moved that source from the Notion Games database to the platform's Sanity project.

## Where a game comes from
- Every value the hub shows of a game is a field of its published `game` in the platform's Sanity project (`mhgqs6fe`, dataset `production`, public), a live game's as much as one to come's: the name, the pictures (logo, icon, background), the description (the English row of its translated field), the players, the duration, the age, the complexity, the categories, the people credited with what each of them did, the publishers and the rulebooks. Courtisans' card and page are its game of the Studio: where it and the registry disagree on a figure (the players, the duration) the hub shows the Studio's
- The hub reads nothing from a game's own Sanity project: that project serves once one enters the game (`/<slug>`, its table and its pages, another root layout)
- The registry decides what the Studio does not: `live` (a game to play or a greyed "Coming soon"), `indexable` and the slug. The order of the live games is the Studio's `order` like the others' (they come before all the others), and the registry's order only breaks a tie between two live games that have the same one. A **live** game (`live: true` in `packages/games/src/registry.ts`) takes its game of the Studio; with none, or with the project down, it takes `registryRow(game)`: its name, its players and its duration when the registry has one figure, nothing else (a plain grey frame, a bare page), still listed and still enterable. There is no value-by-value fallback: a field the game leaves empty stays empty, the registry never fills it
- A **planned** game: a published `game` of the Studio. A game of the registry that is not live takes its game too, and the Studio's name with it; with none it is not listed. Only published documents are read (`perspective=published`): a draft is not on the hub until it is published
- `template` is never listed (`UNLISTED_SLUGS`; in development it still has a page, like every game of the registry that the Studio does not announce yet, so that `pnpm dev` opens a game at `/<slug>`: `developmentEntry` of `apps/web/src/lib/game-page.ts`, the registry's row), and neither are the expansions: a game's `kind` is `game` (the default when it has none) or `reimplementation`. An expansion is played with another game, so it has no page, and it is not a `game` but a document of its own, `expansion` (PLT-102). The query of the hub answers two lists, the games (`_type == "game"`) and the expansions (`_type == "expansion"`), so an expansion can never be read as a game. It is read apart (`CatalogExpansion`, `Catalog.expansions`) with its name, its slug, the slug of its base game, its description, two of its figures (the most players and the minimum age, which the Studio fills only where the expansion changes them) and its two pictures, its cover and the front of its box, and the lobby of its base game offers it (`expansionsOf`, `getExpansions` of `apps/web/src/lib/game-activity.ts`): a card with a small checkbox, its picture at the left, in the shape of its source (the cover, else the front of the box, drawn whole: `pictureRatio`; the initials of the name in a 3 × 2 frame when there is neither), and at the right its name, its description (`pickLocalized`) and, as chips, what it changes about the game (the most players it allows when that is more than the base game's, the age it asks: `getExpansions`); by name, since an expansion has no `order`. One that has no name, a name or a slug the Studio would refuse (the rules of a game's), the slug of an older expansion, or no base game (the base game is a reference, empty while that game is not published) or one the hub does not list, is left out and reported in the logs and in `pnpm catalog:list`, which also prints each one it offers. So is a `game` that still has the former kind `expansion`, which the Studio no longer offers: it is no game of the hub and not an expansion either until it is moved to one (`docs/platform-sanity.md`; none is left once the migration of PLT-102 has run). A `reimplementation` (what Notion called a standalone expansion, a new edition: Flip 7 Vengeance and Time Bomb Evolution today) stands on its own and is listed like a game. The seed imports no expansion, so the ones a game offers are created in the Studio (an expansion, its base game, a Cover or a Box (front), published)
- No sync: the hub reads the published content of the Studio, never a copy of it. The registry stays the source of the slug, `live`, `indexable` and a game's own Sanity project

## The package (`packages/catalog`, `@pbgo/catalog`)
- `.` (`src/catalog.ts`, pure: no I/O, no framework) — the types (`CatalogGame`, `Creator`, `Publisher`, `CreditLine`, `CatalogEntry` = `{ slug, live, indexable, game, related }` where `game` is the game of the Studio, `Catalog` = `{ entries, source }`), `buildCatalog(games, rows)`, `registryRow(game)` (the row of a live game that has none), `compareGames`, `UNLISTED_SLUGS`, `pickLocalized(values, locale)`, `ART_SLOTS` (logo, icon, background, cover), `pictureUrl(game, slot)` (the address of a picture in Sanity's image CDN: the file itself when it is small enough, else sized for the page, `sizedPictureUrl`), `cardPicture(game)` (what a card draws: its cover, else its background, else its logo or its icon, below), `cardPictureUrl(game)` (a game's mark, its logo else its icon), `sharePicture(game)` (the picture a page shares, below), `iconVersion(website)`, `publisherIconUrl(game, index)` (the address of the icon of a publisher, below), `bggUrl(game)` and `bggIconUrl(game)` (a game's page on BoardGameGeek and the address of BoardGameGeek's icon, below), `creditLines(game)` (the credits of a game's page: the labels and the lines, and for a publisher its link and its icon)
- `./server` (`src/server.ts`, server only) — `getCatalog()`, `CATALOG_TAG`, `CATALOG_REVALIDATE_SECONDS`, `reportOnce(message)`. `getCatalog` is the one call a page makes
- `./filter` (`src/filter.ts`, pure like `.`, and the one that the browser imports) — the search and the filters of the hub's list: `GameFilter`, `NO_FILTER` and `DEFAULT_FILTER` (no pick at all, where the bar starts), `GameIndex`, `indexEntry(entry)`, `filterGames(games, filter)`, `SORTS` / `GameSort` / `DEFAULT_SORT` (Trending, A–Z, Newest) and `sortGames(games, sort)` (the order of the list, below), `sortFromParams(params)` / `sortToParams(sort, params)` (the `sort` of an address), `categoriesOf(games)`, `isFiltered`, `optionOf`, `stepOption` / `canStep` (what the stepper of the bar does), `complexityLevel` (the level a weight rounds to), `complexityPick` / `agePick` (the last bar and the last age are no pick), `FIRST_PLAYERS`, `ANY_COMPLEXITY`, `ANY_AGE`, `filterFromParams(params, offered)` / `filterToParams`, `normalize`, `words`, and the options it offers (`PLAYER_COUNTS`, `MANY_PLAYERS`, `DURATION_LIMITS`, `COMPLEXITY_LEVELS`, `AGE_LIMITS`, `MAX_QUERY_LENGTH`). See "Search and filters", below
- `./route` (`src/route.ts`, server only) — `pictureRoute()`, the handler of the picture route: it serves the icon of a publisher's website, and sends the old addresses of the games' pictures to Sanity's image CDN; `apps/web/src/app/api/catalog/[slug]/[slot]/route.ts` is `export const GET = pictureRoute()`
- `./seo` (`src/seo.ts`, pure apart from Next's `Metadata` types) — `isIndexable(entry)`, `metaDescription(text)`, `gameSeo(entry, description)` (the `GameSeo` of a page), `gameMetadata`, `gameJsonLd`, `serializeJsonLd`, `sitemapItems` (below)
- `./picture` (`src/picture.ts`) — `fetchPicture(link)`: downloads a picture from a link and checks it (below); `download(link, kind)` is the download itself, which the page of a publisher's website is read with too. The platform's seed (`platform/content`) downloads the pictures of its Notion rows with it
- `src/sanity.ts` — the reader, `readSanityGames({ fetch?, init?, timeoutMs?, projectId?, dataset? })` (below), `CATALOG_QUERY`, `PLATFORM_PROJECT_ID`, `PLATFORM_DATASET`, `SANITY_API_VERSION`, `SanityError`
- `src/favicon.ts` — `fetchFavicon(site)`: the icon of a publisher's website, found from its page and downloaded (below), `iconLinks(html, base)` (the icons a page names) and `rank(link)` (which one is best)
- `scripts/list.ts` — `pnpm catalog:list`; `src/testing.ts` — the fixtures of the tests (a game as Sanity answers, a fake Sanity, fake picture hosts and publishers' websites), not exported
- Order of the list: the live games, then the planned ones, each group by the `order` of the Studio (the games' hotness, below), a game with none after the games that have one, then by name for the planned ones (`compareGames`) and in registry order for the live ones. This is the order of the catalog and the one the lists start on: `/games` calls it Trending, and the home's Popular games are its first 15
- `pickLocalized` gives a text for a visitor: their language, else English, else French, else any other; it says which one it took, so a page can mark a text that is not in the visitor's language. Every description is English today, so it always takes that one

## The Sanity read (`src/sanity.ts`)
- One `GET` of the project's public API through its CDN, `https://mhgqs6fe.apicdn.sanity.io/v2025-02-19/data/query/production?perspective=published&query=…` (one query, two lists: the games and the expansions): a plain `fetch`, no SDK, no framework, and **no token**. The dataset is public: its published documents can be read by anyone, so there is nothing to configure, not even in a fresh clone. The caller hands in the cache options (`server.ts` gives Next's) and may hand in its own `fetch`, a project and a dataset (a test does). It answers `{ games, skipped, expansions, warnings }`; a failure is a `SanityError` (`status`, 0 when Sanity could not be reached; the message never holds an address)
- The query (`CATALOG_QUERY`, GROQ) takes the published `game`s that have a slug, oldest first (`_createdAt`: two games with one slug are settled the same way every time), and follows each reference to the document it points at in the same call, so one request is the whole catalog: the names of the categories, the creators with their roles, the publishers with their websites, the slugs of the related games and of the base game, the address of the file of each picture. A reference to a document that is not published comes back `null`, which the reader drops
- The translated fields (PLT-104): a text and a picture that a language can change (`description`, a game's `logo` and `cover`, and the `cover` and `boxFront` of an expansion) are arrays of rows `{ language, value }` in the project, and the query picks one with `$language` (a parameter, `&$language="en"` in the address: `HUB_LANGUAGE`, or the `language` option of `readSanityGames`): `coalesce(description[language == $language][0].value, description[language == "en"][0].value, string(description))`, the picture the same through `value.asset->url`. The last term is the plain value of the project before its fields were translated (`string(description)` gives nothing for an array, `logo.asset->url` nothing for an array), so one query reads a project whose games are partly converted, and the hub is the same before and after the migration (checked on the 92 real documents of the catalog, first with the migration applied to them offline, in English and in French, then for real on 2026-11-02: `pnpm catalog:list` gave the same list). Nothing in the project has the old shape any more: the last terms and the four old fields stay for a restore from the backup, and can go once that is not needed. The links to the rules are `rules[]{ language, "link": value }` and the four old fields (`rulesFr`…), a row over the field of its language. `coalesce` skips only a `null`, so a row of the language whose value is an empty text would hide the English one; the Studio unsets a field that is emptied, so none is written, but the language pass should keep that in mind. The rows of the other languages are in the answer only for the rules; the texts and pictures come back in one language, so the answer does not grow with the languages the Studio holds
- Read of a game: `name`, `slug`, `kind`, `order`, `bggId`, `buyUrl`, `releaseDate`, `playersMin`, `playersMax`, `duration`, `minAge`, `complexity`, `description`, `rules` (and `rulesFr|En|Es|De` until they are gone), `categories`, `creators`, `publishers`, `related`, `baseGame`, `logo`, `cover`, `icon`, `background`, `gallery` (each item's caption and the address of its picture, of its clip and of its clip's poster), `helpers` (the key and the title of each aid that the game's lobby offers), the document's last edit (`updatedAt`) and the day it was created (`_createdAt`, read as `addedAt`: the day the game was added, which the Newest sort reads). Not read: `names` (the name in the other languages), `tagline`, `boxFront` of a game, the hotspot and the crop that the Studio keeps beside a picture (the CDN is asked for the whole picture, below), a creator's photo, website and BGG id, a publisher's logo and BGG id, a category's icon, color and description, and the editorial documents: nothing on the hub shows them yet
- A game needs a name (one line of text that passes `nameProblem` of `@pbgo/games/slug`) and a slug that passes `slugProblem` (lower-case, 40 characters at most, not a route of the site). One that has not is reported in `skipped` with its reason, never guessed at, and the others are read; two games with one slug: the older one wins and the other is reported. A text is trimmed and its control characters removed (it goes to a terminal and to the logs), the names of people and publishers included
- An expansion needs a name and a slug as a game does, but its slug may be 48 characters long (`slugProblem(slug, [], "expansion")`, `MAX_EXPANSION_SLUG_LENGTH`: it names no package, token or Studio host, and starts with its base game's slug, as `the-werewolves-of-millers-hollow-the-village` does), a base game that the hub lists, and a slug that no older expansion has. One that lacks any of them is left out of `expansions` and reported in `warnings` with its reason: the Studio is where it is put right
- A value the Studio lets through and the hub cannot use leaves its field empty, a game is never refused for it: a `playersMax` under the `playersMin` (empty means "N or more"), a `complexity` outside 1 to 5, a `releaseDate` that is no day, a rulebook or a website that is not an http(s) link, a picture that is not on the image CDN of the project that was read (the hub points a visitor nowhere else)
- The people credited: `creators` is one line per person with all they did on that game (`{ name, roles }`); the roles are BoardGameGeek's, `CREATOR_ROLES` of `@pbgo/studio-kit/constants`, the list the Studio's form shares, read in the order of that list. A line with no role of the list, or with no name (its person is not published), is dropped
- The links between games: `related` holds the slugs of the games its `related` list names, then its base game, each once, never its own slug and only games the reader kept (an unpublished game or a skipped one is not a link). It is one side of a link as the Studio has it; `buildCatalog` makes it go both ways (below)
- The descriptions: `descriptions` is `{ en }` (or empty): the Studio can hold the other languages, and the hub shows English until the language pass (`docs/platform-sanity.md`, PLT-32). Giving the read a language is changing `HUB_LANGUAGE`, and `descriptions` would then hold the language that was asked for
- The project having no published game at all is not a failure: the hub then lists the live games of the registry alone, and says so (`warnings`)

## The order of the games (the hotness)
- The `order` field of the game in the Studio, lowest first, a game with none after those that have one, then the name for the games to come (case-insensitive, accents aside, numbers in order, so `6 nimmt!`, `7 Wonders`, `10 Minutes`, `Bang`): `compareGames`. It is what the owner calls the games' hotness: the first games are the ones the hub puts forward. The seed numbered the games in the order the hub listed them when it was seeded, which was the one of the Games Development database of Notion (Priority, then Status, then Effort, then the name), and the numbers have been edited in the Studio since (two games may share one: the name then orders them). Nothing else orders the list: no priority and no status, and no card shows `order`
- The live games come first and are ordered by it too (2026-11-08: the owner asked for the games already live to come first, "by hotness as well"), the registry's order only breaking a tie between two of them; a live game with no game in the Studio (`registryRow`) has no `order`, so it comes after the live games that have one. Before that a live game was never ordered by it, it was the registry's, wherever its `order` would have put it
- `buildCatalog` is the one place that orders the games, and the lists only follow it: the home's Popular games are the first 15 entries, `/games` starts on them (Trending) and a sort of the visitor's keeps the catalog's order for the games it leaves tied (below)

## The hub (`apps/web/src/app/(hub)/page.tsx`, and `games/page.tsx` for `/games`)
- Two pages read `getCatalog()` and give every entry, in the order the catalog gives (the live games, then the games to come), to `GameSearch`, which holds the search and the filters (below): the home (`(hub)/page.tsx`) and the list of games (`(hub)/games/page.tsx`, `/games`: what the home used to be, a title, the search bar and `GameList`, which draws the games that match in one grid; indexable, in the sitemap, `canonical` `/games`). The search bar of the header (`HeroSearch`) types and picks into it; its field says "Search games, tables & tournaments...", but only the games can be searched today. The home lays the glass bar over the foot of its title and draws the sections of the platform under it until a search is started (`HomeBody`). None has a visible title (what it shows says what it is; each has an `sr-only` heading). *Popular games* (`PopularGames`) is the grid of `/games` cut to two rows at every width, whose bottom fades out, with "See all games" over the fade, centred, to `/games` (`SectionPreview`, `SectionAction`); there is no count of plays to rank them by yet, so they are the first games of the catalog in its order (the live games first, then the games to come, each group by the `order` of the Studio, the games' hotness), and `PopularGames` is the place that ranks them by plays the day there is a count. Then *Tables in progress*, *Tournaments in progress* and *What's new* (`EmptySection`: an empty state each and its button, "See all tables", "See all tournaments", "See what's new", to the page of its tab, until the list of open tables PLT-21, the tournaments PLT-31 and the release notes PLT-20 exist; the rows of tables will take the place of the empty state, with the same fade and button as the games; their words are `COMING_SOON`, `apps/web/src/lib/coming-soon.ts`, shared with the pages of the tabs). The page never sorts or splits the games again, and `order` only sorts, no card shows it. With the Studio's project unavailable the list is the live games alone, each one a `registryRow`: its name and its facts under a plain frame.
- Every card is the same tile, `GameCard` (`@pbgo/ui/platform/game-card`, drawn in `docs/design/03-components/04-surfaces/02-game-card.md`): one picture on a grey 4:3 frame (`bg-muted`, a platform token), with no layer over the art (no logo, scrim or tint), then its name, on one line and cut with an ellipsis when it does not fit, and two facts, its players and its duration (`UserMultipleIcon` and `HourglassIcon`), and nothing else: no tagline, no placeholder. The picture is the game's cover (PLT-114), which fills the frame; a game with no cover shows its background, alone, filling it the same way; a game with neither has its logo, else its icon, contained and not cropped, on the plain frame; with none of them the frame is a plain grey and the name sits under it. Never two pictures: the logo is not drawn over a cover or a background
- A live game is `variant="play"`, a game to come `variant="soon"` with a small "Coming soon" badge at the top right of the card. `catalogCardProps(entry)` (`apps/web/src/lib/game-card-props.ts`) is the one place that makes a card's props, and the only thing it reads of the registry is `entry.live`, for that variant. Every card takes the same values from the game's game of the Studio: its picture is `cardPicture(game)` (below), an address in Sanity's image CDN, and its facts are `playersLabel` and `durationLabel`. So Courtisans' card shows the pictures of its game in the platform's Studio, not the ones of its own project: a change in the platform's Studio reaches the hub once the catalog has read it again (below), a change in the game's own Studio does not
- Every card is a plain `<a>` to the game's page on the hub, `/game/<slug>` (below), the games to come as much as the live ones. `GameCard` requires an `href`, so a card that goes nowhere cannot be drawn; `catalogCardProps` holds that one rule
- Only the card of a live game carries `data-game`: analytics counts the games opened from the hub (`game_opened_from_hub`), and a game to come is not one. The click on a live card now leads to the game's page on the hub rather than into the game (`docs/analytics.md`)
- The picture of a card is `GameCardVisual` (`@pbgo/ui/platform/game-card`), a frame that chooses nothing: a `picture` fills it, else a `logo` sits on it, else it stays plain. `cardPicture(game)` (`src/catalog.ts`, pure and tested) chooses what a game's card draws, the first it has of its cover (fills), its background (fills, alone), its logo, its icon (both on the plain frame), and `gamePicture(game)` (`apps/web/src/lib/game-card-props.ts`) hands that to the card as a `picture` or a `logo`. The head of a game's page does neither: it draws the game's background across the page and its logo in place of the name by itself (`heroPicture`, larger). `catalogCardProps(entry)` makes the props of the cards of the home, of `/games`, of the search and of the related cards of a game's page. Those related cards carry no `data-game` either: the listener counts `/` and `/games` only

## Search and filters (`GameSearch`, `HeroSearch`, `SearchCategory`, `SearchMoreFilters`, `HomeBody`, `GameList`)
- The home and `/games` search in client components of `apps/web/src/components/`, with one state between them. `GameSearch` is the provider that holds the search, the picks, the order (`sort`) and the categories the games have. `HeroSearch` is the search bar of the header (`SearchBar` of `@pbgo/ui`, drawn in `docs/design/03-components/02-navigation/03-search-bar.md`): one pill with the magnifier at its start, which sends the search and scrolls to `#results` like Enter, the field (with a clear button while there is a text) and, at its end, the category (`SearchCategory`), then, under it, centred on a line of their own and each in a container of its own, the other filters (`SearchMoreFilters`). The category is a segment that opens a `Popover` with a title, a Clear button and a list with a search field (`Combobox`: several at once, so the panel stays open; the segment is always drawn, and with no category yet its panel says so). The number of players is a stepper (`NumberStepper`: a minus button, the number with its icon just after it and a plus button, no panel and no label) that starts on no number and says "Any": the first press, either way, picks a table of four (`FIRST_PLAYERS`), the buttons then move it one place along its options, and the minus button goes back to "Any" from 1; the duration the hourglass, the limit written next to it (its minutes and the minute mark, "30′", or "1h+" for no limit), then a slider with one thumb on twelve steps (`DurationFilter`: from 5′ to 55′, five minutes at a time, and "1h+", the last being no limit, where it starts; the fill runs from the first step to the thumb; a dot marks each quarter hour), the complexity its icon and bars that fill up to the level pressed, with nothing written beside them (`ComplexityFilter`: a `Meter` that is not `clearable`: it starts all filled, the last level being no limit, `ANY_COMPLEXITY`, and pressing the picked level keeps it, so there is always a level, from 1 to 5), the age a menu of "6+" to "14+" and "All ages" (`AgeFilter`: the last age, 18, is no limit, `ANY_AGE`, and starts the menu), as wide as its button. The rules are `@pbgo/catalog/filter` (`src/filter.ts`, pure and tested); the components only draw them. Their texts are English constants: the platform speaks English
- It all happens in the browser. The page stays static and hands `GameSearch` every game as `{ ...indexEntry(entry), props: catalogCardProps(entry) }`: what the filter and the sort read of the game (`GameIndex`: slug, name, `live`, the day it was added, the normalised text to search, players, duration, complexity, minimum age, categories; no description, no picture) beside the props of its card. The HTML of the page lists every game whatever the link holds, so a crawler or a visitor without JavaScript gets the whole list. Nothing is asked of the server when a visitor types
- Filters only remove, and the order is a pick of its own (`sortGames`, `@pbgo/catalog/filter`, pure and tested): it orders what the filters leave, as a new list, starting from the order of the catalog, which every sort keeps for the games it cannot tell apart. **Trending**, where the list starts, is the catalog's order itself: the live games first, then the games to come, each group by the `order` of the Studio (the hotness above). **A–Z** is alphabetical by name, case and accents aside, numbers in their order (`6 nimmt!`, `7 Wonders`, `10 Minutes`, `Azul`), and does not put the live games first. **Newest** puts the game added last first (`addedAt`, the day its `game` was created in the Studio), a game that says no day after the others, and compares moments, not spellings. The games of the first seed were all created at one moment (2026-10-30), so Newest keeps the catalog's order until a game is added after them. The menu is `SortGames` (`apps/web/src/components/sort-games.tsx`, "Sort by" and a `Select` of `@pbgo/ui`), at the right over the cards of `/games`: the home has no menu, and its Popular games are Trending
- The search: every game, a live one included, is searched by its name, the people credited on it (whatever they did: designers, artists, developers…) and its publishers, never by its descriptions. Case, accents and apostrophes do not count (`normalize`: "herve" finds "Hervé", "millers" finds "Miller's"; œ æ ß ø ł are spelled out). Every word of the query must be somewhere in the text of the game, a part of a word is enough, in any order. 60 characters at most (`MAX_QUERY_LENGTH`)
- The filters, all of which must hold: categories (any of the ones picked, spelled as the Studio has them: they are the names of the `category` documents a game points to, the panel offers the ones the games have, in alphabetical order, each with the icon that `apps/web/src/lib/category-icons.ts` gives its name (a placeholder: a `category` document has an icon, a color and a description, which the catalog does not read yet, and the name of a category will find them there), and a game with no category is left out as soon as one is picked; "Play now" and "Coming soon" are not categories and no longer a filter, the card says "Coming soon" itself); players (1 to 7, 8+, none where the bar starts: a game stays when its range holds the number, a game with no upper limit ("3+") seats any number from its lower limit up, and "8+" keeps the games that seat 8 or more); duration (up to 5, 10 … 55 minutes, five at a time, or no limit, the slider's twelfth step "1h+", where the bar starts; a game counts by the one figure of its game in the Studio, a live game with none by the registry's when that is a single figure, not a range); complexity (a level from 1 to 4, or 5, which is no limit and where the bar starts: a game stays when its level, the weight of its game rounded to the nearest whole number, is at most the one picked, so 2.49 is level 2 and 2.5 level 3; the weight is BoardGameGeek's, from the `complexity` field of the game); age (6, 8, 10, 12 or 14, or 18, which is "All ages", no limit and where the menu starts: the age of the youngest player, so a game stays when its minimum age is at most that, and the menu reads "8+"). A pick that is not set asks for nothing, so with none every game stays; one that is set leaves out a game that does not say its players, its duration, its complexity or its minimum age, since it cannot be said to fit. The data is thin for now (on 2026-11-08, 31 of the 71 games say their players, 32 their duration and their minimum age, and none its weight), so a first pick narrows the list a lot and a level of complexity empties it until the weights are in the Studio. `isFiltered` is false where the bar starts, nothing typed and nothing picked: the home keeps its sections until the visitor types or picks, and "Reset filters" puts the picks back there
- The address: the picks are written into it in place (`history.replaceState`: the list as the visitor has it is not a page to come back to), as `/?category=Cards&category=Party&players=6&duration=30&complexity=2&age=10`, a `category` for each one picked, each pick left out when it is where the bar starts (none: "Any" players, no limit on the duration, all the bars, "All ages"), so the list as it opens is `/` (or `/games`). The order is in it too, `sort=name` or `sort=newest`, after the picks and left out for Trending (`sortToParams`): a link opens the list in the order it was left in, a sort that is not one is Trending (`sortFromParams`), and "Reset filters" puts the picks back and keeps the order. A link that holds picks opens the list cut. A value the filters do not offer (`players=04`, `age=7`, `duration=60`, a category no game has) is ignored, and the pick goes back to where the bar starts, and so is the `?show=` of the availability filter that was; so are the last bar and the last age (`complexity=5`, `age=18`) and the old `duration=any`, which the links written before the bar started on nothing hold: they are where it starts. The typed text is never in the address, neither written nor read: the address goes to analytics with every event, and what a visitor types is theirs while analytics events carry no personal data (`docs/analytics.md`). A search that can be shared (`?q=`) would first need a rule in `@pbgo/analytics` that scrubs it
- The home and `/games` are static, so the server cannot read the query string. On the server and on the first render of the browser `GameSearch` sees none (`useSyncExternalStore`: the same markup, no hydration mismatch), then the real one. A link that holds picks therefore shows the sections of the home (the whole list on `/games`) for a moment before the results appear. A typed text is lost on reload
- Analytics: no event for the search or the filters. The count of `game_opened_from_hub` is unchanged: it listens on the document for `a[data-game]` at the moment of the click, so the cards that a filter brings back count as before, only the live ones carry `data-game`, and `usePathname` ignores the query string, so `/?category=Cards` is still the hub
- A new criterion = a field of `GameFilter` and of `GameIndex`, its rule in `filterGames`, its parameter in `filterFromParams` and `filterToParams` (left out when it is the default), a test in `filter.test.ts`, and its segment in `SearchCategory`, `SearchMoreFilters`
- Tests: `filter.test.ts` runs the model, the sort and its address included (`pnpm --filter @pbgo/catalog test`). `apps/web` has no test suite, so `GameSearch`, `HeroSearch`, `SearchCategory`, `SearchMoreFilters`, `SortGames`, `HomeBody` and `GameList` are checked in the browser: the menu of the sort (each sort, the address, a shared link), typing, the panel of each filter (a pick, a second click on it, Clear, Escape, the keyboard), the empty state and its button, a shared link, a phone, a tablet and a desktop width

- `game` was already a reserved slug, being a segment of the table's address (`/<slug>/game/<code>`). `/game/<slug>` has two segments and a table three, and the static `game` wins over `[game]`, so the two never meet

## The SEO of the game pages (`packages/catalog/src/seo.ts`, `@pbgo/catalog/seo`)
- One rule, `isIndexable(entry)`, behind the three things below. A live game follows the registry's `indexable` flag, like its home did (`/<slug>`, which now shows this page): `/game/courtisans` may be indexed, the page of a live game whose flag is off may not, whatever its game in the Studio says. A game to come may be indexed once its game in the Studio has a description (English, for now): until then the page has nothing to say and stays out of the results (`noindex`, no JSON-LD, not in the sitemap). A game has no home of its own any more: `/<slug>` shows its page on the hub, whose canonical is `/game/<slug>`, the one address of the game that search engines index
- Pure functions, tested without Next (`seo.test.ts`); `apps/web` hands them what the page loaded. `getGamePage` makes the page's `seo` (`GameSeo`, by `gameSeo(entry, description)`: the description is the one the page shows, from the game's game of the Studio, live or not; a game with none has none in its metadata and its JSON-LD, nothing stands in for it), `generateMetadata` is `gameMetadata(game.seo, { url: SITE_URL, name: SITE_NAME })`, the page writes its JSON-LD `<script>` only when `seo.indexable`, and `sitemap.ts` is `sitemapItems(SITE_URL, entries)`
- The metadata: the title is the game's name (the layout's template adds the site's); the description is the text the page shows, on one line and cut at 160 characters between two words (`metaDescription`); `alternates.canonical` is the page's own absolute URL; `robots` is `index, follow` (with the `googleBot` large-image and snippet hints) or `noindex, follow`, a page that may not be indexed still letting its links be followed; Open Graph (`type: website`, `siteName`, `url`, `title` with the site's name, `description`, `locale` of the language the description was found in, the image) and a Twitter card (large with a wide picture, `summary` with a small one or none). Open Graph and Twitter are set on a `noindex` page too: a link to it still previews in a chat
- Next merges metadata key by key: a page's `openGraph` and `twitter` replace the layout's whole, so they repeat the type, the site name and the URL, and a key with nothing to say is left out, never set to `undefined` (Next reads a key that is present as an override, and `undefined` would wipe the layout's value: the tests walk the object for one)
- The picture a page shares, for every game: `sharePicture(game)`: its Background (wide) if the game has one, else its Logo or Icon (not wide, so the Twitter card is `summary`), else nothing. It is an absolute address in Sanity's image CDN already, which the page leaves as it is (`absoluteUrl` only completes a path). A live game's own share image, `/<slug>/opengraph-image/share`, stays the picture of its own home, not of its page on the hub. Before PLT-90 the share image was `/api/catalog/<slug>/background`, and Facebook, X and the like keep the links they have seen: `robots.txt` still opens `/api/catalog/` (`Allow` beats `Disallow: /api/`, the longest rule wins), and the route sends those links to the CDN
- The language: the description is the one the page shows (`pickLocalized`: the visitor's language, else English, French, any other). A crawler sends no language, so it reads the site's default, English (`getLocale` of core), and falls back the same way; the `og:locale` is the language the text was found in, English while every description is. No `hreflang`: a page has one URL, not one per language
- The JSON-LD (`gameJsonLd`, written by `serializeJsonLd`, which escapes `<` so that a name can never close the tag): a schema.org `Game` with `name`, `url`, `description` (on one line, not cut), `image`, `numberOfPlayers`, `timeRequired` (ISO 8601, from the duration, one figure), `typicalAgeRange` (`8-`), `author` (the designers and the solo designers), `contributor` (everyone else credited on the game, whatever they did: a Game has no `illustrator`) and `publisher` (with its website as the `url`). A field with no value is absent, not empty. No `inLanguage`: the text is not always in the visitor's language
- The sitemap: the hub, its list of games, then the hub page of every game of the catalog for which `isIndexable` is true, so it lists exactly the pages that do not say `noindex`. A page is dated by its game's last edit in the Studio (`lastModified`, from `updatedAt`; none when the date does not read, so none for a live game that has no game in the Studio); a live game's page is `weekly` with priority 0.8, one to come `monthly` with 0.6. It is rebuilt every ten minutes (`revalidate = 600`, like the catalog), not once per build, so a game that gets a description is listed within twenty minutes at worst. When the catalog is the live games alone (the Studio's project unavailable) the sitemap lists those alone until the next rebuild
- To look at it: `pnpm dev`, then view-source on `/game/<slug>` of a game with a description and of one without, `/sitemap.xml` and `/robots.txt`

## Cache and failure
- `getCatalog` is wrapped in React's `cache` (one read per request); the Sanity call itself is cached by Next for ten minutes (`next: { revalidate: 600, tags: ["catalog"] }` on the `fetch`; the stale answer is served while a fresh one is fetched). `revalidateTag(CATALOG_TAG, { expire: 0 })` makes the next read ask Sanity again; no webhook of the project calls it yet, so a published change shows on the hub within about eleven minutes (Sanity's CDN keeps an answer for a minute, then Next's copy for ten). Next does not cache an answer over 2 MB: the catalog is about 65 KB for 71 games
- The Studio's project is the one optional part. When it does not answer (an outage, a timeout of 5 s, a bad query), the catalog is the live games alone, each one a `registryRow` (its name, its players and its duration, no picture, no text), `source` is `"unavailable"`, and a Studio-only slug has no page (`/game/<slug>` answers 404). In development (`NODE_ENV=development`) the catalog also lists the other games of the registry, each a `registryRow` that says "Coming soon" (`buildCatalog`'s `registryGames` option, after the live games and in registry order), so that a hub that cannot read the project can be seen with all its grid, names and figures but no picture; a deployment never does, since a game that the Studio does not announce is not announced
- What is wrong is logged once per distinct line and per server instance, as `[catalog] …` on `console.warn`: the project unavailable, no published game, a game left out and why. Nothing logged holds an address of a request

## The pictures, and the route of the old addresses (`GET /api/catalog/<slug>/<logo|icon|background>`)
- A game's pictures are files of its game in the platform's Sanity project (`logo`, `icon`, `background` and, since PLT-114, `cover`; the logo and the cover are translated fields, the row of the language of the read is taken, else the English one, else the plain image the field held before). The reader hands out the address of each file in the project's image CDN (`https://cdn.sanity.io/images/mhgqs6fe/production/…`: only that CDN, a picture anywhere else is dropped), and a page draws `pictureUrl(game, slot)`, which `sizedPictureUrl` answers: that address with `?w=<width>&fit=max&auto=format&q=85`, 800 px for a logo, 512 for an icon and 1200 for a background and for a cover (never more than the file holds; the head of a game's page asks 2400 for its background), `auto=format` giving WebP or AVIF to a browser that takes it and `q=85` encoding it above the CDN's default of 75. Two kinds of file keep their address as it is: an SVG, and a WebP, JPEG or AVIF file whose name says it is not wider than the width asked for (`…-<w>x<h>.<ext>`, read the way `pictureRatio` does), which goes out with no query at all. A PNG or a GIF is always asked for, so that a large one is never sent whole. `pictureRatio(url)` gives the shape of a picture, its width over its height, from the size that the CDN puts in the name of the file (`…-650x590.webp`), so that a frame can keep it before the picture arrives: the tile of an expansion in a lobby has the shape of its cover, or of the front of its box. The visitor's browser loads the picture from `cdn.sanity.io` itself: nothing runs on this site's servers for it, and Sanity's CDN keeps it. `img-src` is not restricted by this site; if the pictures ever have to go through this site's own domain, `/_next/image` already accepts `cdn.sanity.io` (`images.remotePatterns` in `next.config.ts`)
- A picture is not encoded twice unless it has to be (PLT-114). Every picture of the platform's project is a WebP already, and asking the CDN for one with `auto=format` usually encoded it a second time, to AVIF or WebP at its default quality, even when nothing was resized; the small ones showed it first, the covers, which were 640 × 480 then. So a file that is not wider than the page draws it goes out as it is, and a wider one is shrunk once, at `q=85`. The price is weight, not requests: on 2026-11-06 the pictures that the cards and the heads of the 71 game pages load weighed about a third more (6.6 to 8.8 MiB for the 129 raster ones; the heaviest after the change is one 1602 × 2400 background, 1.3 MiB in the head of its page). The widths did not change, and a small or soft file stays so: the files are the owner's to replace. Checking an address with `curl` needs the browser's `Accept` header (`image/avif,image/webp,*/*`): the CDN varies its answer by it, and `*/*` gets a JPEG or a PNG made from the WebP, as any client that does not list WebP does
- No picture is no error page: a game that does not have one leaves a plain grey frame (`bg-muted`, a platform token: no initials, no placeholder art). The cards of the hub and the pages of the games (`/game/<slug>`) draw it (above)
- The cover (PLT-114) is the card's picture and the card's alone: the head of a game's page and the picture a page shares do not use it, so a game that has a cover and nothing else (`castle-combo` and `dnup` on 2026-11-06) shares no picture, `sharePicture` being the background, else the logo or the icon. The CDN is asked for the whole picture (`fit=max`, never a crop) and the card's frame crops it with `object-cover`, from its middle. The hotspot and the crop that the Studio keeps beside a cover (`hotspot: true`) are not read: the 15 covers of the Studio on 2026-11-06 are all 1600 × 1200 (they were 640 × 480 until that afternoon), the frame's own 4:3 shape, and none has either. A cover of another shape is cropped around its centre; reading the hotspot is the day one comes (`fit=crop&crop=focalpoint` from the CDN, or an `object-position`)
- The route is what is left of the one that served the pictures of the Notion rows (Notion's links expired after about an hour, so the server downloaded each picture from a fresh link). Links to it were shared and cached before PLT-90, a page's share image among them, and a consumer that knows a game's slug only (the icon of a game in the friends' panel, in the list of a visitor's games) can still ask for `/api/catalog/<slug>/icon`. Its order, so that nothing costs more than it has to: 1) the slot is one of the three, or `publisher-<n>` (next section), else 404 (the cover of a game came after those links, nothing points at it by address and a page draws it from `pictureUrl(game, "cover")`, so `/api/catalog/<slug>/cover` is a 404: adding it is one word in `ADDRESSED_SLOTS` of `route.ts`, the day a consumer that knows a slug only needs it); 2) the catalog could not be read: 503, the game may well exist; 3) the slug is a game of the catalog, live or not, else 404; 4) a picture the game has is a 308 to its address in the CDN (`?v=` of an old link is ignored), a picture it does not have a 404

| Answer | `Cache-Control` |
| --- | --- |
| 308 to the picture in the image CDN | `public, max-age=300, s-maxage=3600` |
| 404 (not a game of the catalog, or a picture the game does not have) | `public, max-age=60, s-maxage=60` |
| 503, with `Retry-After` (the catalog cannot be read now) | `no-store` |

- What the server fetches (`picture.ts`, the one place that does it, for the icon of a publisher's website and for the seed): the visitor gives a slug and a slot, never a URL. A link must be https, with no credentials and the default port; an IP address, a name without a dot, `localhost` and the names a network keeps for itself (`.localhost`, `.local`, `.internal`, `.localdomain`, `.home.arpa`) are refused. A redirect is followed by hand, three at most, each one checked again. One 8 s limit covers the download, the size is capped at 4 MiB while the body streams (a function answers 4.5 MB at most), and the file must be a picture by its bytes (PNG, JPEG, GIF, WebP, AVIF, SVG, and ICO, which only an icon is), never by what the host said. The logs name the host, never a link
- Limits, on purpose: the server does not resolve names, so a public name that points at a private address (`127.0.0.1.nip.io`) passes: the websites come from the Studio, trusted as far as whoever can edit it

## The icon of a publisher (`GET /api/catalog/<slug>/publisher-<n>`)
- Why it exists: a game's page shows each publisher with the icon of its website at the left of its name (`CreditLink`). The visitor's browser must not ask the publisher's website for it (this site keeps its visitors' data on its own domain, as the media proxy and the `/ingest` rewrites do), so the server looks the icon up and the CDN keeps it. The page draws it from `publisherIconUrl(game, index)`: `/api/catalog/<slug>/publisher-<index>?v=<iconVersion(website)>`, `index` being the place of the publisher in the game's list, from 0, as `creditLines` lists them, and `v` a short hash of the website's address, so that a publisher whose website changes gets a new address for its icon
- It is the picture route (`pictureRoute()`) with another kind of slot. `publisher-<n>` has no leading zero and at most two digits, so one icon has one address. The first steps are the picture's (the slug is a game of the catalog), then the game must have an n-th publisher with a website (the `website` of its `publisher` document), else 404, and `v` must be the version of that website, else a 307 to the right URL, before anything is fetched, so nobody can make the server look for an icon under a `v` of their own. Sanity is not read again: the website is the catalog's. The visitor gives a slug and a place and never an address: a `url=`, `site=` or `host=` in the query is not read, and a test sends them to prove it
- What the server does (`favicon.ts`, `fetchFavicon(site)`): it reads the page of the website as far as its first 256 KiB for the links `rel="icon"`, `shortcut icon` and `apple-touch-icon` (`iconLinks`; `data:` icons, comments and anything `allowedUrl` refuses are left out), ranks them (`rank`, the lowest first: 32 to 128 px, the nearest to 64 first; then a scalable one, an SVG or `sizes="any"`; then an apple-touch-icon; then a bigger one; then one that says no size, usually an ICO; the smallest, under 32 px, last), tries four at most (the best three, then `/favicon.ico`, once), and serves the first that is a picture by its bytes (PNG, JPEG, GIF, WebP, AVIF, SVG or ICO) and at most 512 KiB. A page that cannot be had (down, 4xx, a bad certificate) still leaves `/favicon.ico`. An `http` address in the Studio is asked for over https. One 8 s limit covers the page and the icons together. It sends `Accept` and a `User-Agent` that names the site (`PlayBoardGamesOnline-icons/1.0 (+https://playboardgamesonline.app)`) and nothing else
- What it may fetch is what a picture may (`picture.ts`, `allowedUrl`): https only, no credentials, no port, no address, no `localhost`, no name of a local network, for the website's own address and for every link its page gives and every redirect it makes (three at most, by hand, each checked again)
- The answers: 200, `public, max-age=86400, s-maxage=86400` (a day: a favicon changes once in years); 404, `public, max-age=3600, s-maxage=3600` when the website has no icon the server can use, `public, max-age=60, s-maxage=60` when the game has no such publisher or no website; 307 to the current `v` (`public, max-age=0, s-maxage=10`); 503, `no-store`, when the website cannot be reached now (`Retry-After` 300: it is then left alone for five minutes, per server instance, so that a website that is down or has a broken certificate is not asked again by every visit to its game's page, and nobody waits for its 8 s) or the catalog cannot be read. Every 200 has the headers of a picture (`X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, like the media route) and its type comes from its bytes. A website that fails is logged once per instance, as `The icon of the publisher <n> of "<slug>" cannot be served: <host> …`, the host and never an address
- The page: `CreditLink` (`@pbgo/ui/platform/credit-link`) keeps the 16 px place of the icon from the first paint and asks for the picture once the page is interactive, so that a 404 or a 503 is always heard and the place is then given up: a publisher with no icon is its name alone, with no broken picture and nothing that moves but that name, once. The icon is decorative (`alt=""`): the link says the publisher's name. `robots.txt` already opens `/api/catalog/`: a crawler that renders the page may fetch an icon, which is a small cached image
- BoardGameGeek's icon is the same route with the slot `bgg`: `/api/catalog/<slug>/bgg?v=<iconVersion(BGG_SITE)>` (`bggIconUrl(game)`), which the head of a game's page draws on its link to the game there (`BggButton`). The game must have a BGG id, else 404 (there is no link to draw it on); the website is the constant `BGG_SITE` (`https://boardgamegeek.com`) and never the request's, and `v` is the version of that address, else a 307 before anything is fetched. The server looks it up as for a publisher. BoardGameGeek turns a client that is not a browser away from its pages (a 403, on 2026-11-02), so the page names no icon and what is left is `/favicon.ico` (an ICO of 16 and 32 px, about 5 KiB), which is all the button needs, and the CDN keeps it a day. One website, one wait: when BoardGameGeek cannot be reached it is left alone for five minutes whichever game asks, and a failure is logged once as `The icon of BoardGameGeek, for "<slug>" cannot be served: <host> …`
- Limits, on purpose: names are not resolved (as for a picture); only the first 256 KiB of a page are read, so an icon named after that is not seen; the icon is the website's favicon, as asked, and the `logo` of a `publisher` document, which the Studio has, is not read (it could stand in where a website has no icon); the icon is only as good as the `website` of the publisher (on 2026-10-30, of the 18 websites of the publishers, 16 give an icon; `https://www.catchupgames.com` has an invalid certificate for `www`, while `https://catchupgames.com` works, so its `publisher` should say that, and the link a visitor follows would be refused by their browser otherwise; the Magilano website has no icon at all, so its name stands alone); a publisher's new favicon shows within a day

## Working on the package
- `pnpm --filter @pbgo/catalog test` and `pnpm --filter @pbgo/catalog typecheck`. The tests run the reader against a fake Sanity built from the shape the project answers (`src/testing.ts`: `sanityGame(slug, overrides)` is one document as the query returns it, `fakeSanity(answer)` the fetch that answers with a list or with a failure, `sanityFailure`); a new field = its line in `CATALOG_QUERY`, the field of `CatalogGame`, its line in `readSanityGames`, `registryRow`, `catalogGame` and `sanityGame` of `testing.ts`, a test. `sanity.test.ts` does not run the query: `sanity-query.test.ts` does, with a GROQ engine (groq-js) over small datasets in either shape of the translated fields, and `groqSanity` of `testing.ts` is the project's API behind that engine (the picture route is tested through it too). A change to `CATALOG_QUERY` is also proved against the real project with `pnpm catalog:list`, which must give the same list
- The picture route is tested against a fake Sanity and fake picture hosts and websites of publishers (`fakeWeb`), never the network: the answers, the headers, the memo and the refused links. A change to `route.ts` or `picture.ts` is checked by breaking it on purpose and seeing a test fail
- The SEO is tested without Next or the network (`seo.test.ts`, on the entries that `catalogEntry` of `testing.ts` builds from `registryGame` and `catalogGame`): the rule, the cut of the description, the metadata (and that no key of it is `undefined`), the JSON-LD and the lines of the sitemap
- The source is run as it is by Node (`pnpm catalog:list`, type stripping) and bundled by Next (`transpilePackages`): in `src/`, a value import from a sibling file has no extension that both accept, so a file imports only types from its siblings (`import type`) and the pieces that need each other meet in `server.ts`, `route.ts` and `scripts/list.ts`; `scripts/` import with `.ts` extensions. `seo.ts` is the exception, since Node never loads it (Next bundles it and Vitest runs it): it imports values from `./catalog` and from core (`lib/i18n`, `lib/site-url`). `picture.ts` imports nothing at all, and `favicon.ts` is another exception like `seo.ts`: it imports values from `./picture`, and Node never loads it (`route.ts` does, in Next and in Vitest). `server-only` throws under plain Node, so only `src/server.ts` imports it (the tests of `server.ts` and `route.ts` mock it). `list-script.test.ts` runs the script under plain Node to keep this true
