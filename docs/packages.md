# Games registry and shared packages

The root `CLAUDE.md` names the shared packages in a few lines; this file holds the detail: the registry, a game's binding package and every package of `packages/`. What `@pbgo/core` draws inside a game (HUD, announcements, seat label, game over, skin) is in `docs/game-ui.md`.

## Games registry (`packages/games`, `@pbgo/games`)
- `src/registry.ts` — `GAMES`, pure data read by the hub, the sitemap, the router, `next.config.ts` and the scripts: `slug`, `name`, `tagline`, `players`, `duration` (minutes), `sanityProjectId`, `live` (playable in production; every game stays playable outside production), `indexable` (sitemap, no `noindex`). The art of the hub card is not in the registry: its logo is the `logo` of the game's published Sanity `settings` and its background the `background` of its `interface` (`gameCardArt()` of `packages/core/sanity/cover.ts`), and a picture the game does not have leaves the card's frame plain; the game's page on the hub draws the same two pictures, larger (`gameCover()` of the same file, the `hero` of the `interface`, is no longer read by the hub's cards and pages: `/design` borrows it as a stand-in background)
- `src/index.ts` (server) — `LOADERS`: slug → `() => import("@pbgo-game/<slug>/server")`; `getGame`, `getPlayableGame`, `getPreviewableGame`, `gameRoute`, `gamemasterRoute`
- `src/runtime.tsx` (client) — `RUNTIMES`: slug → `dynamic(() => import("@pbgo-game/<slug>/runtime"))`, mounted by the `[game]` layout
- Code splitting: a page loads only its game's code; the hub loads none (no three.js). Never import a game package statically from shared code.
- Adding a game = one `@pbgo-game/<slug>` package + one entry in `GAMES`, `LOADERS` and `RUNTIMES` + the dependency in `packages/games/package.json` (`pnpm new-game` does all of it)

## A game's binding package (`@pbgo-game/<slug>`)
Contract types in `@pbgo/core/lib/binding` (`GameBinding`, `UiBinding`, `ServerBinding`):
- `.` (`src/index.ts`, isomorphic) — `SLUG`, `NAME`, `KEYWORDS`, `AUTHOR`, `CONTACT`… (from `src/lib/site.ts`), the engine `GAME` (absent: not playable yet); optional `SOUNDS`, `DEFAULT_SKIN`, `UI_THEME`, `SETTINGS_DEFAULTS`, `ERROR_CODES`, `REACTIONS`, `STUDIO_URL`. No text of the game is in it: its tagline, description, translations and error messages live in its Sanity project (see `docs/sanity-and-languages.md`)
- `./ui` (`src/ui.tsx`, client) — `Logo`, `Game` (the board, loaded lazily so the home page does not pull in three.js)
- `./server` (`src/server.ts`, server only) — everything of `.` plus optional `loadSetupData` (data for `GAME.setup`), `loadGameData` (`data` prop of the board), `ROUTES` (the game's own routes, `/api/<slug>/games/<code>/<route>`), `SEO` (`(ctx) => { genres?, platform?, heading? }`: the search-engine texts, read from the game's Sanity project in the visitor's language)
- `./runtime` (`src/runtime.tsx`, client) — the game's styles and fonts and `BindingProvider`
- `./styles.css` — the game's Tailwind entry: imports `@pbgo/core/styles/game.css` (theme tokens, `@source` to `packages/core` and `packages/ui`), then `@source "."` and the game's own tokens and fonts
- Core never imports a game: pages and API handlers receive the `GameModule`, client components read it with `useBinding()`

## Shared packages (`packages/`)
A change here reaches every game on the next deployment.
- `@pbgo/core` — the shared base: server (`server/*`: Supabase games with a version lock, players, admin, stats, tasks, rate limiting), `lib/*` (binding contract, api, realtime, settings, i18n, skin, sound, site URLs), components (home, lobby, game context, HUD, chat, game over, sharing, admin, toolbar), pages (`pages/home|game|admin|preview`), route handlers (`routes/api/**/route.ts` for the games, `routes/gamemaster/**/route.ts` for the gamemaster), metadata images
  - The standard screens, the HUD, the in-game UI, the skin and the accent font of core: `docs/game-ui.md`
  - Who the game waits for (engine contract v2): `GAME.waitingFor(state)` = the players the game waits for (several on a simultaneous step), `GAME.autoPlayFor(state, playerId)` = plays the current step for one of them. Core reads them only through the `@pbgo/engine-kit` helpers `waitingPlayers`, `canPlayFor`, `playFor`; the legacy `activePlayer` / `autoPlay` still work (`@deprecated`). `waitingFor` is public: `PublicGame.waitingFor`, next to `present` (members seen in the last 75 s) and `takeovers` (per waiting player: required voters and votes so far)
  - Absent player: after `settings.turnTimeout` (60 s by default, Gamemaster › Mechanics) without a write, `StalledTurn` offers the present players to vote, per absent player (`/takeover`, which plays with `playFor`); the opening of Courtisans (missions to read) is an ordinary takeover too. Rules in `server/takeover.ts` (pure, tested): a player is played for once every member seen in the last 75 s, other than them, has voted for them; an absent player never blocks
  - Concurrent writes: `updateGame` retries up to 8 times with a growing random wait
- `@pbgo/games` — the registry (above)
- `@pbgo/analytics` — PostHog for the hub and every game: typed events (`ServerEvents`, `ClientEvents`), `track()` of the server (`./server`), the consent-aware browser provider, the banner, `ConsentLink` and `useIdentifyPlayer` (`./client`), the consent store and rules, the table-code scrubber and the banner texts (`.`), the settings (`./config`). It may depend on `@pbgo/ui` and `@pbgo/studio-kit/constants`, never on core or a game. See `docs/analytics.md`
- `@pbgo/catalog` — the games the hub can list (PLT-56): `buildCatalog` joins the live games of the registry with the planned games of the Notion Games database and lists with each entry the games related to it (`related`, from the `Related Games` and `Parent item` links of the rows, whichever row holds the link), `pickLocalized` picks a text in the visitor's language, `pictureUrl` is the address of a planned game's picture and `cardPictureUrl` the one its hub card draws (`.`, pure); `getCatalog()` reads Notion with a plain `fetch`, cached ten minutes under the tag `catalog`, and falls back on the live games alone without `NOTION_API_KEY` or when Notion fails (`./server`, server only); `pictureRoute()` is the handler of `/api/catalog/<slug>/<logo|icon|background>`: it asks Notion for a fresh link, downloads the picture and serves it (`./route`, server only). It may depend on `@pbgo/games` (`./registry`, `./slug`), `@pbgo/studio-kit/constants` and the types of core, never on a game. Source run by Node itself for `pnpm catalog:list`, so a file imports only types from its siblings. See `docs/catalog.md`
- `@pbgo/engine-kit` — engine ↔ web contract (`GameDefinition` with `waitingFor` / `autoPlayFor`, `Results`…), turn helpers (`waitingPlayers`, `currentPlayer`, `canPlayFor`, `playFor`, `playOn`), game options (`defaultOptions`, `normalizeOptions`), `EngineError`. A game's engine re-exports it: `export * from "@pbgo/engine-kit"`
  - Building blocks of the card games, pure, seeded and tested, each documented in `packages/engine-kit/README.md`: `rng` (`createSaveableRng` / `restoreRng` carry a stream from one action to the next, `shuffle`, `sideSeed`), `ids` (numeric opaque card ids, `reissueId` when a card goes back into hiding), `deck` (`draw`, `peek`, `insertAt`, `reshuffleDiscard`, `drawWithReshuffle`, `deal`), `log` (`viewLog`: entries filtered per viewer), `rounds` (`roundsOutcome`, `sumRounds`, `ranks`: scores until a target), `simultaneous` (`Submissions<T>`, `openSubmissions`, `submit`, `pendingSubmissions(submissions, seatIds)`, `allSubmitted`, `submittedFlags`, `revealSubmissions`)
  - Lean state, for every game (PLT-45): the state holds ids and numbers only, no display data, no derived values, no log
  - The state is stored as `jsonb`, which does not keep the order of the keys: an order (seats, turns) always comes from an array of the state, never from `Object.keys`
- `@pbgo/table` — the shared table tools of the boards (react-three-fiber), written once so every game's table behaves the same (PLT-62). It depends on `@pbgo/core` (the easing curves of `components/game/easing`, the share photo of `lib/photo`, the motion preference of `lib/use-motion`); core never imports it. A game imports it from its board, the chunk loaded lazily with the game, so the hub and the game home load no three.js; it is listed in `transpilePackages`
  - `Card`: a rounded plane with a front and a back. It glides to `target`, flies in from `from`, bends in flight, hovers, glows, shines and casts a shadow. Props: `id` (the game's own name for the card: it feeds the pose memory below), `target` / `from` (a `Pose`), `front` / `back` (textures), `size` (`CardSize`: `width`, `height`, optional `radius`; the same for every card of a game, which then share one geometry), `glow`, `gloss`, `shadow`, `above`, `speed`, `onClick` / `onHover` / `onArrive`, and `children` for the overlays (a value, a suit: the origin is the middle of the face). `draggable` / `onDrop` are reserved (PLT-69)
  - The pictures: `paintFace(key, size, draw)` paints a face or a back on a canvas, once per key and size; `standIn(key, size, { color, label })` is what a card shows while its picture is missing (label it `[missing: key]`): still a texture on the card, never a DOM card
  - The glows: `defineGlows({ name: { halo?, outline?, frame?, sparkle? } })` names what a game's cards light up with; a card wears one `Glow` at a time, and a part a glow leaves out is not drawn
  - The poses: `Pose`, `onTable(x, z, { y, face, yaw, lean, scale, delay })`, `FACE_UP` / `FACE_DOWN`, `RESTING_HEIGHT`, `lean(key)` and `hashRandom(key)` (a pose never calls `Math.random`: the same key leans the same way on every client)
  - `CARD_SETTINGS`: the defaults of the card's knobs (flight, bend, gloss, shadow) for the game's leva panel
  - `Table`: the canvas every game plays on, with the camera, the room and the lights around what lies on it. It owns the `Canvas` (a game never writes one) and one `Suspense`. Props: `camera` (`CameraSettings`: `tilt` in degrees from the vertical, `yaw`, `distance`, `fov`, `targetX`, `targetZ`; a plain object read on every frame, so a game's debug panel edits it live), `intro` / `playIntro` (the camera's entrance), `floor`, `lights`, `photo`, `id` (DOM id of the canvas's wrapper, `TABLE_CANVAS_ID` by default), `near` / `far` (read once, when the canvas is created) and `children` (surfaces, cards, seats)
  - The camera: one pure, tested function, `placeCamera` (`table/camera.ts`), puts it where the settings say, for the live camera and for the share photo's. A screen narrower than 1.6:1 backs it off so the table keeps fitting, and it never sinks under 0.5 above the table. The entrance (`CAMERA_INTRO`: it starts 1.45 times farther, turned by 22° and tilted by 12°, and settles over 2.6 s) plays when the table mounts; `playIntro={false}` holds the camera on its settings, and a visitor who asks for reduced motion never sees it
  - `Floor` (the `floor` prop: `{ color, size }`): the room around the table, one colour on a plane of 400 × 400 by default, so it seems endless. `Surface`: what the cards lie on, an ellipse or a rectangle in world units (`size`, `shape`) with a picture (`map`) or a `color` and an optional wooden `rim: { width, color }`; it never catches a click or a hover. A game's own mat (a shader, a roller) stays in the game
  - `Lights` (the `lights` prop: `true` or `{ ambient, sun, sunPosition }`, defaults in `DEFAULT_LIGHTS`): a table of flat materials, like the template's, needs none
  - The share photo: with `photo` (a `CameraSettings`), `Table` registers the game over's capture (`setPhotoCapture` of core) with a camera of its own, placed by `placeCamera`, so the photo does not depend on where the live camera stands. An object with `userData.hiddenInPhoto` is left out of it. Without `photo` the share image is the pixels of the canvas
  - The pose memory: give a `Card` an `id` (stable for that card) and a card that leaves the table and appears again within a second, in another place, starts from where the old one was, so the card a player plays flies from their hand to the trick instead of appearing there. A given `from` wins. From a remembered pose a card flies only when it is more than 4 units from its target; nearer, it glides there like any other move. It needs a `Table` around it, and a card with no `id` is not remembered
  - Zones, seats and the debug panel are the next steps of PLT-62 and are not in the package yet
- `@pbgo/ui` — shadcn components + `cn`: `@pbgo/ui/game/<comp>` (game theme), `@pbgo/ui/platform/<comp>` (platform theme: hub, account, legal, admin, 404), `@pbgo/ui/styles/platform.css` (platform tokens), `@pbgo/ui/theme` (`PLATFORM_THEME_COLOR`), `@pbgo/ui/utils`. See `docs/design-system.md`
- `@pbgo/studio-kit` — shared Sanity schemas (`settings`, `interface`, `audio`, `texts` via `createTexts(extraFields, extraGroups)`, `localeString`…; no `rules` document, see `docs/sanity-and-languages.md`) and `createStudioConfig({ title, projectId, gameTypes })` (a game type with the same name replaces the shared one); `@pbgo/studio-kit/constants` (languages, `FONT_CHOICES`) importable on the web side
- `@pbgo/content-kit` — the seed pipeline of a game's Sanity content, shared by every game: options and token, plan, art (scan, WebP, upload, place), drafts-only writes, report, plus the test helpers (in-memory dataset, Studio-schema checker). A game keeps only its data and its config in `games/<slug>/content` and calls `runSeedCli`. Four entry points: `.` (what the data files import: `localeString`, `localeText`, `setField`, `setItemField`, `ArtSlot`, `SeedDoc`), `./seed` (the runner), `./testing` and `./form-rules` (the rules of the Studio forms, for a Studio's own test: no Sanity client, no `sharp`). Consumed as source and run by Node (type stripping): relative imports carry `.ts`, type imports are `import type`, erasable syntax only, and the kit declares its own dependencies. Documented in `packages/content-kit/README.md`; `apps/web` does not use it
- `@pbgo/tsconfig`, `@pbgo/eslint-config` — shared TypeScript and ESLint configs
- Every external dependency comes from the pnpm catalog (`catalog:` in `package.json`, versions in `pnpm-workspace.yaml`); `pnpm check:catalog` enforces it
- A new workspace package used by apps/web goes into `transpilePackages` (`apps/web/next.config.ts`; game packages are added from the registry)
