# Games registry and shared packages

The root `CLAUDE.md` names the shared packages in a few lines; this file holds the detail: the registry, a game's binding package and every package of `packages/`. What `@pbgo/core` draws inside a game (HUD, announcements, seat label, game over, skin) is in `docs/design/04-in-game/`.

## Games registry (`packages/games`, `@pbgo/games`)
- `src/registry.ts` — `GAMES`, pure data read by the hub, the sitemap, the router, `next.config.ts` and the scripts: `slug`, `name`, `tagline`, `players`, `duration` (minutes), `sanityProjectId`, `live` (playable in production; every game stays playable outside production), `indexable` (sitemap, no `noindex`). What the hub shows of a game is neither in the registry nor in the game's own Sanity project: its card and its page are its `game` in the platform's own Sanity project, pictures included, Courtisans as any other (`@pbgo/catalog`, `docs/catalog.md`, `docs/platform-sanity.md`). The registry decides only `live`, `indexable`, the slug and the order of the live games; its `name`, `players` and `duration` reach the hub only as the minimal row (`registryRow`) of a live game that has no game there, or when the platform's project cannot be read. A game's own Sanity project is read once one enters the game
- `src/index.ts` (server) — `LOADERS`: slug → `() => import("@pbgo-game/<slug>/server")`; `getGame`, `getPlayableGame`, `getPreviewableGame`, `gameRoute`, `gamemasterRoute`
- `src/runtime.tsx` (client) — `RUNTIMES`: slug → `dynamic(() => import("@pbgo-game/<slug>/runtime"))`, mounted by the `[game]` layout
- Code splitting: a page loads only its game's code; the hub loads none (no three.js). Never import a game package statically from shared code.
- Adding a game = one `@pbgo-game/<slug>` package + one entry in `GAMES`, `LOADERS` and `RUNTIMES` + the dependency in `packages/games/package.json` (`pnpm new-game` does all of it)

## A game's binding package (`@pbgo-game/<slug>`)
Contract types in `@pbgo/core/lib/binding` (`GameBinding`, `UiBinding`, `ServerBinding`):
- `.` (`src/index.ts`, isomorphic) — `SLUG`, `NAME`, `KEYWORDS`, `AUTHOR`, `CONTACT`… (from `src/lib/site.ts`), the engine `GAME` (absent: not playable yet); optional `SOUNDS`, `DEFAULT_SKIN`, `UI_THEME`, `SETTINGS_DEFAULTS`, `ERROR_CODES`, `REACTIONS`, `STUDIO_URL`. No text of the game is in it: its tagline, description, translations and error messages live in its Sanity project (see `docs/sanity-and-languages.md`)
- `./ui` (`src/ui.tsx`, client) — `Logo`, `Game` (the board, loaded lazily so the screens around it do not pull in three.js)
- `./server` (`src/server.ts`, server only) — everything of `.` plus optional `loadSetupData` (data for `GAME.setup`), `loadGameData` (`data` prop of the board), `ROUTES` (the game's own routes, `/api/<slug>/games/<code>/<route>`)
- `./runtime` (`src/runtime.tsx`, client) — the game's styles and fonts and `BindingProvider`
- `./styles.css` — the game's Tailwind entry: imports `@pbgo/core/styles/game.css` (theme tokens, `@source` to `packages/core` and `packages/ui`), then `@source "."` and the game's own tokens and fonts
- Core never imports a game: pages and API handlers receive the `GameModule`, client components read it with `useBinding()`

## Shared packages (`packages/`)
A change here reaches every game on the next deployment.
- `@pbgo/core` — the shared base: server (`server/*`: Supabase games with a version lock, players, admin, stats, tasks, rate limiting, the results of the finished games and what the pages read of them: `results.ts`, `standings.ts`, with the member's games across every game and their totals, and `lib/member-games.ts`, which puts them in the shape of the member's pages), `lib/*` (binding contract, api, realtime, settings, i18n, skin, sound, site URLs), components (the screens around the board, game context, HUD, chat, game over, sharing, admin, toolbar), pages (`pages/game|admin|preview`), route handlers (`routes/api/**/route.ts` for the games, `routes/gamemaster/**/route.ts` for the gamemaster), metadata images
  - The standard screens, the HUD, the in-game UI, the skin and the accent font of core: `docs/design/04-in-game/`
  - Who the game waits for (engine contract v2): `GAME.waitingFor(state)` = the players the game waits for (several on a simultaneous step), `GAME.autoPlayFor(state, playerId)` = plays the current step for one of them. Core reads them only through the `@pbgo/engine-kit` helpers `waitingPlayers`, `canPlayFor`, `playFor`; the legacy `activePlayer` / `autoPlay` still work (`@deprecated`). `waitingFor` is public: `PublicGame.waitingFor`, next to `present` (members seen in the last 75 s) and `takeovers` (per waiting player: required voters and votes so far)
  - Absent player: after `settings.turnTimeout` (60 s by default, Gamemaster › Mechanics) without a write, `StalledTurn` offers the present players to vote, per absent player (`/takeover`, which plays with `playFor`); the opening of Courtisans (missions to read) is an ordinary takeover too. Rules in `server/takeover.ts` (pure, tested): a player is played for once every member seen in the last 75 s, other than them, has voted for them; an absent player never blocks
  - Concurrent writes: `updateGame` retries up to 8 times with a growing random wait
- `@pbgo/games` — the registry (above)
- `@pbgo/analytics` — PostHog for the hub and every game: typed events (`ServerEvents`, `ClientEvents`), `track()` of the server (`./server`), the consent-aware browser provider, the banner, `ConsentLink` and `useIdentifyPlayer` (`./client`), the consent store and rules, the table-code scrubber and the banner texts (`.`), the settings (`./config`). It may depend on `@pbgo/ui` and `@pbgo/studio-kit/constants`, never on core or a game. See `docs/analytics.md`
- `@pbgo/accounts` — the accounts of the hub: Supabase Auth with Google and Discord, the hub's own sign-in with Steam (the OpenID part, `steam.ts`, and the member of an external provider, `external.ts`: signing in, linking and unlinking; Twitch is a connection, linked and never a way in) (`./client` for the browser, `./server` for Server Components and route handlers, `./proxy` for the session refresh, `./config` for the project's two public variables), the pure part (`.`: `Account`, `accountOf`, `safeNext`, the figures of a profile, and the age of a member against the age a game or an expansion asks: `ageInYears`, `ageRefusal`, `restrictedAge`, `birthdateProblem`, PLT-125), the demo account of development (`./demo`), the site's motion and transparency as the member chose them (`./display`: the cookies, the script of the head of every page, the sync; PLT-111) and the visitor's language (PLT-103): `./language` (the twelve languages, the matching of a browser's languages, the key of the account that keeps the choice, the cookie, what to write where) and `./set-language` (the one setter, light because the games' pages load it: core's language pickers import it, so `@pbgo/core` depends on `@pbgo/accounts`, and `@pbgo/accounts` depends on `@pbgo/studio-kit` for the list of languages). See `docs/accounts.md`. It depends on `@supabase/ssr` and `@supabase/supabase-js`, never on core or a game. See `docs/accounts.md`
- `@pbgo/docs` — the `docs/` folder of the repo as pages of the site, `/docs` (PLT-87, PLT-88). `.` (`src/docs.ts`, pure) is the model: a section is a folder of `docs/`, a page a markdown file in it and a group a folder of a section, with its own landing page and its own pages; `index.md` is the landing page of a folder, the title of a page is its first `# ` heading (a file with none is named after its file), the landing page of a section opens with a front matter block (`---` lines of `key: value`: `icon`, a name the app registers in `apps/web/src/lib/doc-icons.ts`, and `description`, plain words) that says what its card shows on the docs hub, `frontMatterOf` takes it off the text of the page and a key it does not know stops the build, the menu is the landing page first and then what is in the folder in the order of the names, and a number in front of a name (`03-components/`, `01-button.md`) puts it in its place and is not part of its address (`/docs/design/components/controls`). A folder, a file or a link is read only if its name is a word of lowercase letters and digits joined by dashes (`isDocName`: the name is the address, so nothing else is read from the disk). `buildSections` stops on a folder with no `index.md`, on two entries with the same address and on a page called `index`; a section carries its `description` and its `icon`. `neighboursOf` gives the page before and the page after one in the order of the menu, which the foot of every page links to. `filterPages` and `matchesQuery` are the search of the side menu of a doc: a page whose title holds every word, whatever the case and the accents, with its group, and a group with the pages of it that do. `resolveLink` leads a relative link of a page to another page of the docs to that page, read the way the disk has the names (so that a link works on GitHub too: `../02-foundations/03-radius.md`), shows a link to a file of the repo that has no page as a name, and refuses an unsafe link. `./server` reads the folder when the pages are built (`findDocsDir` finds `docs/` next to the nearest `pnpm-workspace.yaml`; a page is looked up among the files found by its address and no path is made from an address; a link to somewhere else is not followed), and a test reads the real `docs/` of the repo and checks that every relative link and every `#anchor` of every page exists. The pages are those of the build (`dynamicParams` is off in `apps/web/src/app/(hub)/docs/[section]/[[...page]]/page.tsx`, so no function reads `docs/` once the site is up, and any other address is a plain 404): in development a file that is added needs a restart of `pnpm dev` to have its page, though the menu shows it at once. `./markdown` is `Markdown`, GitHub's flavour (`react-markdown`, `remark-gfm`, `rehype-slug`): an `id` and a link on each heading, a rule above each `##`, a code block as text with no highlighter, a table in `@pbgo/ui/platform/table`, a text that can be selected, and raw HTML shown as the text it is; the text keeps a readable measure (`max-w-reading`) while the tables, the code and the specimens take the width of the page. A fenced block of the language `specimen` is a live piece of the site: its first line is the name of a component that the app registers (`specimens`, here `apps/web/src/app/(hub)/docs/_specimens/`, one module for each group of pages of the design docs), the lines after the name are given to it as `body`, and a name that is not registered stops the build, as does a registered name that no page shows (`generateStaticParams` of the docs route). The files of `docs/` that are not in a section folder are not rendered yet. The site draws them in two looks: `/docs`, the way into the docs, in the look of the hub's pages (`apps/web/src/app/(hub)/docs/page.tsx`: `ListPageHeader` with a description, a card for each section), and a doc's pages, the same for every doc (`[section]/layout.tsx` and `apps/web/src/components/docs-sidebar.tsx`: the doc's name, a search of its pages and its pages in sections that fold, next to the page).
- `@pbgo/catalog` — the games the hub lists (PLT-56, PLT-83, PLT-90), each one as its `game` of the platform's own Sanity project, live games included, the registry deciding only `live` and `indexable`: `buildCatalog` puts the live games of the registry first, each with its game or, when it has none, the minimal `registryRow` (name and players from the registry, nothing else), then the other games of the project, each group in the Studio's `order` (lowest first, the games' hotness: `compareGames` for the games to come, the registry's order breaking a tie between live games), and lists with each entry the games related to it (`related`, from the `related` and `baseGame` links of the games, whichever game holds the link); `pickLocalized` picks a text in the visitor's language, `pictureUrl` is the address of a game's picture in the project's image CDN, `cardPicture` what its hub card draws (its cover, else its background, else its logo or its icon), `cardPictureUrl` its logo else its icon, `sharePicture` the one its page shares and `creditLines` the credits of its page (`.`, pure); `readSanityGames()` (`src/sanity.ts`) reads the project with a plain `fetch` of its public API, no SDK and no token, in a language (`language`, English: `HUB_LANGUAGE`) with English as the fallback, and reads the project before and after its fields are translated (PLT-104); `getCatalog()` is the cached read, ten minutes under the tag `catalog`, which falls back on the `registryRow` of each live game when the project cannot be read (`./server`, server only); `pictureRoute()` is the handler of `/api/catalog/<slug>/<slot>`: it finds the icon of a publisher's website and serves it, and sends the old addresses of the pictures to the CDN (`./route`, server only); `isIndexable`, `gameSeo`, `gameMetadata`, `gameJsonLd` and `sitemapItems` make the SEO of the game pages, their metadata, JSON-LD and lines of the sitemap (`./seo`, pure, tested without Next); `fetchPicture` downloads a picture, for the platform's seed (`./picture`). It may depend on `@pbgo/games` (`./registry`, `./slug`), `@pbgo/studio-kit/constants` and the types of core (`./seo` also reads its `lib/i18n` and `lib/site-url`), never on a game. Source run by Node itself for `pnpm catalog:list`, so a file imports only types from its siblings (`seo.ts` apart: Node never loads it). See `docs/catalog.md`
- `@pbgo/engine-kit` — engine ↔ web contract (`GameDefinition` with `waitingFor` / `autoPlayFor`, `Results` and `outcomesOf`, which reads them as the win, loss or draw of each player for the history…), turn helpers (`waitingPlayers`, `currentPlayer`, `canPlayFor`, `playFor`, `playOn`), game options (`defaultOptions`, `normalizeOptions`) and the keys of their words (`engineTextKeys`), `EngineError` with the vocabulary of the refusals every game shares (`SHARED_ERROR_CODES`, worded by core) and, for the tests of a binding, `@pbgo/engine-kit/testing` (`conformanceProblems`, the contract played the way the server plays it, and `errorVocabularyProblems`). A game's engine re-exports it: `export * from "@pbgo/engine-kit"`
  - Building blocks of the card games, pure, seeded and tested, each documented in `packages/engine-kit/README.md`: `rng` (`createSaveableRng` / `restoreRng` carry a stream from one action to the next, `shuffle`, `sideSeed`), `ids` (numeric opaque card ids, `reissueId` when a card goes back into hiding), `deck` (`draw`, `peek`, `insertAt`, `reshuffleDiscard`, `drawWithReshuffle`, `deal`), `log` (`viewLog`: entries filtered per viewer), `rounds` (`roundsOutcome`, `sumRounds`, `ranks`: scores until a target), `simultaneous` (`Submissions<T>`, `openSubmissions`, `submit`, `pendingSubmissions(submissions, seatIds)`, `allSubmitted`, `submittedFlags`, `revealSubmissions`)
  - Lean state, for every game (PLT-45): the state holds ids and numbers only, no display data, no derived values, no log
  - The state is stored as `jsonb`, which does not keep the order of the keys: an order (seats, turns) always comes from an array of the state, never from `Object.keys`
- `@pbgo/table` — the shared table tools of the boards (react-three-fiber), written once so every game's table behaves the same (PLT-62). It depends on `@pbgo/core` (the easing curves of `components/game/easing`, the share photo of `lib/photo`, the motion preference of `lib/use-motion`); core never imports it. A game imports it from its board, the chunk loaded lazily with the game, so the hub and the screens around the board load no three.js; it is listed in `transpilePackages`; its `Seat` draws the plate of a player (name, avatar, turn crown, aura, score line and status) and `PlayerSeat` fills it from the platform's table
  - `Card`: a rounded plane with a front and a back. It glides to `target`, flies in from `from`, bends in flight, hovers, glows, shines and casts a shadow. Props: `id` (the game's own name for the card: it feeds the pose memory below), `target` / `from` (a `Pose`), `front` / `back` (textures), `size` (`CardSize`: `width`, `height`, optional `radius`; the same for every card of a game, which then share one geometry), `glow`, `gloss`, `shadow`, `above`, `speed`, `onClick` / `onHover` / `onArrive`, and `children` for the overlays (a value, a suit: the origin is the middle of the face). `draggable` / `onDrop` are reserved (PLT-69)
  - The pictures: `paintFace(key, size, draw)` paints a face or a back on a canvas, once per key and size; `standIn(key, size, { color, label })` is what a card shows while its picture is missing (label it `[missing: key]`): still a texture on the card, never a DOM card
  - The glows: `defineGlows({ name: { halo?, outline?, frame?, sparkle? } })` names what a game's cards light up with; a card wears one `Glow` at a time, and a part a glow leaves out is not drawn
  - The poses: `Pose`, `onTable(x, z, { y, face, yaw, lean, scale, delay })`, `FACE_UP` / `FACE_DOWN`, `RESTING_HEIGHT`, `lean(key)` and `hashRandom(key)` (a pose never calls `Math.random`: the same key leans the same way on every client)
  - `CARD_SETTINGS`: the defaults of the card's knobs (flight, bend, gloss, shadow), with `CARD_FIELDS`, the knobs the debug panel offers for them
  - `Table`: the canvas every game plays on, with the camera, the endless table and the lights around what lies on it. It owns the `Canvas` (a game never writes one) and one `Suspense`. Props: `camera` (`CameraSettings`: `tilt` in degrees from the vertical, `yaw`, `distance`, `fov`, `targetX`, `targetZ`; a plain object read on every frame, so a game's debug panel edits it live), `intro` / `playIntro` (the camera's entrance), `held` (the entrance waits at its first frame until this turns false) and `onLoaded` (called once when what the children suspend on is in): both are the start screen's, below, `surface`, `lights`, `photo`, `id` (DOM id of the canvas's wrapper, `TABLE_CANVAS_ID` by default), `near` / `far` (read once, when the canvas is created) and `children` (cards, seats)
  - The camera: one pure, tested function, `placeCamera` (`table/camera.ts`), puts it where the settings say, for the live camera and for the share photo's. A screen narrower than 1.6:1 backs it off so the table keeps fitting, and it never sinks under 0.5 above the table. The entrance (`CAMERA_INTRO`: it starts 1.45 times farther, turned by 22° and tilted by 12°, and settles over 2.6 s) plays when the table mounts; `playIntro={false}` holds the camera on its settings, and a visitor who asks for reduced motion never sees it. A board drawn behind the platform's start screen (PLT-107) passes `held`: the camera stands at the first frame of the entrance and plays it from there when the screen goes (`introRest` takes `held`); and `onLoaded`, which the board hands to its own `onLoaded` (a game loading its pictures without suspending reports itself)
  - `Surface` (the `surface` prop, required: `{ color, map, tile }`): the table the cards lie on, endless: its `color` is the one the canvas is cleared to, and a `map` that repeats over it fades into that colour with distance, so it has no edge and no camera sees an end of it; it never catches a click or a hover. A game's own mat (a shader, a roller) is a plane it draws on the table and stays in the game
  - `Lights` (the `lights` prop: `true` or `{ ambient, sun, sunPosition }`, defaults in `DEFAULT_LIGHTS`): a table of flat materials, like the template's, needs none
  - The share photo: with `photo` (a `CameraSettings`), `Table` registers the game over's capture (`setPhotoCapture` of core) with a camera of its own, placed by `placeCamera`, so the photo does not depend on where the live camera stands. An object with `userData.hiddenInPhoto` is left out of it. Without `photo` the share image is the pixels of the canvas
  - The pose memory: give a `Card` an `id` (stable for that card) and a card that leaves the table and appears again within a second, in another place, starts from where the old one was, so the card a player plays flies from their hand to the trick instead of appearing there. A given `from` wins. From a remembered pose a card flies only when it is more than 4 units from its target; nearer, it glides there like any other move. It needs a `Table` around it, and a card with no `id` is not remembered
  - The layout helpers (`layout.ts`, pure and tested): each returns the `Pose[]` of a zone, and every number is an argument (no setting is read inside the package, so a game's debug panel keeps editing its own). A layout is drawn in the frame of a `Spot` (`{ x, z, yaw }`: +x to the right, −z is where the top edge of a face-up card points, away from the viewer at yaw 0); `inFrame(spot, pose)` puts a pose of that frame on the table, `shifted(pose, { x, y, z })` moves a pose without touching the original
    - `fan(n, { gap, y, rise, z, curve, tilt, roll, face, scale })`: a hand, centred on x = 0, first card on the left, each one a little higher than the one before; `curve` lowers the ends toward the player, `tilt` bends the cards back, `roll` turns them about their own axis. `row(n, { gap, y, rise, z, face, turn, scale })`: a flat line along x. `pile(n, { y, step, face, topFace, lean, leanAmplitude, scale })`: a stack at the origin, bottom card first, each leaning its own way when `lean` names it (the same on every client). `grid(n, { columns, gapX, gapZ, rows, y, face, turn, scale })`: lines in reading order, the first one farthest from the viewer, the last short line left-aligned; `rows` fixes the number of lines the grid is centred on
    - `seats(count, { radiusX, radiusZ, me, margin })`: the ring of seats, indexed like the players, as `Spot`s (not poses). The viewer (`me`, the index of their seat) sits in front at `{ x: 0, z: radiusZ, yaw: 0 }`, the others share the far half of the ellipse in turn order from the player after the viewer, each turned to face the middle; a lone opponent sits straight across. Without a valid `me` (a spectator) everyone is on the far half
  - `Zone` and `Pile`: the cards of a zone placed by a layout. `<Zone frame layout size enter stagger cards />`: card `i` of `cards` (a `ZoneCard`: the props of a `Card` but `target` and `size`, plus a React `key`) takes slot `i` of `layout`, put in the `frame`; a card with no slot is not drawn. A card with no `from` of its own enters from `enter` (world space, not in the frame), each one `stagger` seconds (0.08 by default) after the one before it, counted from the zone's first card; a card's own `from` wins and `from: null` turns its entry flight off. A zone owns no state: the game gives it the cards, with their keys, and the pose memory of `Card` does the rest. `<Pile frame count size back top limit enter stagger />` is a zone of `count` face-down cards over `pile(...)` (at most `limit`, 24 by default), whose top card shows its face when `top.front` is given; its cards are keyed by height, so a pile of named cards, where the card below must stay face up, is a `Zone` over `pile(n, { face: "up" })`. Both are a toolbox the game composes, not a declarative board: a zone anchored to the camera (Courtisans' hand) arrives with the Courtisans migration
  - The seat (`seat/`): `TableText`, `SeatAvatarMesh`, `Aura` and `TurnCrown`, put together by `Seat` and filled from the platform's table by `PlayerSeat` (nickname, seat colour, account picture, crown icon, font, and the state of the player that `seatStateOf` reads from `waitingFor`, `present`, `status` and `results`). The plate shows the turn with the crown on the avatar, the players expected together with a soft aura, a winner with the full aura and a player who is away or out faded; with `onSelect` it can be picked. `SEAT_SETTINGS` holds its numbers. The debug panel is the next step of PLT-62 and is not in the package yet
  - The debug tools (`debug/`): `useSettings(folder, object, fields, options)` binds a settings object to a folder of the debug panel (it writes the folder down with `useDebugFolder` of core, which loads nothing: the panel draws it when it is there, so a board never remounts for leva), with `useSettingsVersion` and `notifySettings` for what a `useMemo` computes from the object. While the panel is open `Table` mounts `TableDebug` (a chunk of its own): the Camera, Entrance, Card, Seat, Lights, Floor, Glow · name and Share Photo folders, helpers drawn over the table (axes, the frame and slots of every `Zone`, the spot and plate of every `Seat`), an inspector for the card under the pointer and a slow motion (the clock of the canvas). Core holds the rule that none of it runs on the production deployment (`debugAllowed`, `components/game/debug-rule.ts`) and the registry of folders (`debug-folders.ts`). `docs/engine/04-build-a-game/07-tuning.md`
- `@pbgo/ui` — shadcn components + `cn`: `@pbgo/ui/game/<comp>` (game theme), `@pbgo/ui/platform/<comp>` (platform theme: hub, account, legal, docs, gamemaster, 404), `@pbgo/ui/styles/platform.css` (platform tokens), `@pbgo/ui/theme` (`PLATFORM_THEME_COLOR`), `@pbgo/ui/utils` (`cn`), `@pbgo/ui/motion` (the durations and the easing of the tokens, in the units `motion/react` takes), `@pbgo/ui/reduced-motion` (whether the motion is reduced: the member's choice, then the device's; the hook and `MotionPreference` that every platform component that moves uses) and `@pbgo/ui/brands` (the marks of the sign-in providers). A component that shows data is given it already made, and what that data is made of is in modules with no React, tested as they are: `friends` and `social` (the friends, their conversations and their requests), `queue` (a visitor who looks for a table), `tables` (the seats of a table and the words said of it), `results` (how a game ended for a player, their figures), `ranks` (the tiers and divisions: a rank, never the rating) and `leaderboard` (a row and which rows the board draws). See `docs/design/` (the guidelines are in `01-guidelines/`)
- `@pbgo/studio-kit` — shared Sanity schemas (`settings`, `interface`, `audio`, `texts` via `createTexts(extraFields, extraGroups)`, `localeString`…; no `rules` document, see `docs/sanity-and-languages.md`) and `createStudioConfig({ title, projectId, gameTypes })` (a game type with the same name replaces the shared one); `@pbgo/studio-kit/constants` (languages, `FONT_CHOICES`, `PLATFORM_LANGUAGES` and `DEFAULT_PLATFORM_LANGUAGE`, `translatedType`) importable on the web side; `@pbgo/studio-kit/field-translations` (`fieldTranslations`: `sanity-plugin-internationalized-array` set up for translating a Studio's fields row by row, PLT-104; its own entry point, the plugin and its peers `@sanity/language-filter` and `@sanity/assist` are optional peers of the kit, so a Studio that does not use it installs nothing; `createStandaloneStudioConfig` takes it in `plugins`)
- `@pbgo/content-kit` — the seed pipeline of a game's Sanity content, shared by every game: options and token, plan, art (scan, WebP, upload, place), drafts-only writes, report, plus the test helpers (in-memory dataset, Studio-schema checker). A game keeps only its data and its config in `games/<slug>/content` and calls `runSeedCli`. Four entry points: `.` (what the data files import: `localeString`, `localeText`, `setField`, `setItemField`, `setRow` (an image in the row of a language of a translated field), `ArtSlot`, `SeedDoc`), `./seed` (the runner), `./testing` and `./form-rules` (the rules of the Studio forms, for a Studio's own test: no Sanity client, no `sharp`; `pluginTypes` gives the types a Studio's plugins register). The merge finds the rows of a translated field by their language, not their key, since the Studio makes up the key of a row it adds. Consumed as source and run by Node (type stripping): relative imports carry `.ts`, type imports are `import type`, erasable syntax only, and the kit declares its own dependencies.
