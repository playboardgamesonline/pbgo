# Play Board Games Online · monorepo

oré's online board games in one repository (`playboardgamesonline/pbgo`), a pnpm workspace served by **one Next.js app** on `playboardgamesonline.app`: the hub at `/`, each game at `/<slug>`, and the back office of all of them (the gamemaster) at `/gamemaster`.

Moving the project to another account: see `MIGRATION.md`.

## Structure
- `apps/web/` — `web`, the only Next.js app (hub, every game and the gamemaster). Vercel project `pbgo`, root directory `apps/web`
- `games/<slug>/` — one game = packages only, no app of its own:
  - `src/` — the binding package `@pbgo-game/<slug>`: site constants, engine binding, board, server loaders, sounds, defaults, i18n, skin
  - `packages/engine` — `@<slug>/engine`, the pure TypeScript engine (no UI), tested with Vitest
  - `apps/studio` — `<slug>-studio`, the game's Sanity Studio
  - `content/` — the game's Sanity content as versioned code (its data and its config) and a seed script that writes drafts, run by the shared `@pbgo/content-kit` (Hanabi and Exploding Kittens, see `docs/content-pipeline.md`)
  - `assets/` — sources (PDF, PSD, HD visuals), git-ignored. The seed's art folder is outside the repo (Hanabi: `~/Companies/PBGO/assets/hanabi`) and is passed with an absolute `--art-dir`
- `template/` — the game template, itself a game (`@pbgo-game/template`, demo "La Plus Haute", served at `/template`). See `template/CLAUDE.md` and `template/docs/GAME_GUIDE.md`
- `packages/` — shared code (below)
- `docs/` — guides: `content-pipeline.md` (seeding a game's Sanity content)
- `supabase/migrations/` — schema of the single Supabase project
- `scripts/` — `new-game.sh`, `go-live.sh`, `add-game.sh`, `setup-env.sh` (helpers in `lib.sh`), `run.sh`, `check-catalog.mjs`

## Routes (`apps/web/src/app`)
| URL | File | |
| --- | --- | --- |
| `/` | `(hub)/page.tsx` | hub: the live games of the registry |
| `/legal` | `(hub)/legal/page.tsx` | legal notice |
| `/design` | `(hub)/design/page.tsx` | design system reference: every token and component of the platform, then the shared in-game UI drawn in the look of two games side by side (noindex, not in the sitemap) |
| `/<slug>` | `[game]/page.tsx` | game home ("coming soon" when the game is not playable here) |
| `/<slug>/game/<code>` | `[game]/game/[code]/page.tsx` | table (lobby, board, game over) |
| `/<slug>/preview/home\|game` | `[game]/preview/[kind]/page.tsx` | admin previews (iframe): the game's own page, served to the signed-in gamemaster only (404 otherwise), see Gamemaster |
| `/gamemaster` | `gamemaster/page.tsx` | the gamemaster's overview: every game of the registry |
| `/gamemaster/login` | `gamemaster/login/page.tsx` | sign-in, one session for every game |
| `/gamemaster/<slug>/<section>...` | `gamemaster/[game]/[[...section]]/page.tsx` | a game's admin (Setup, Tasks, Monitoring); `/gamemaster/<slug>/preview/home\|game` is rewritten to `/<slug>/preview/...` |
| `/<slug>/admin/...` | `next.config.ts` | permanent redirect to `/gamemaster/<slug>/...` (the former per-game admin) |
| `/<slug>/icons/favicon\|apple`, `/<slug>/manifest.webmanifest`, `/<slug>/opengraph-image/share` | `[game]/...` | the game's metadata files |
| `/api/<slug>/games/...`, `/api/<slug>/feedback` | `api/[game]/...` | the game's public API |
| `/gamemaster/api/login\|logout`, `/gamemaster/api/<slug>/settings\|upload/<slot>\|tasks\|feedback` | `gamemaster/api/...` | the gamemaster's API: sign-in and sign-out, then everything that needs the session |
| `/api/media` | `api/media/route.ts` | Sanity media proxy, shared by every game |
| `/ingest/*` | `next.config.ts` (`beforeFiles` rewrites) | PostHog behind the site's own domain: `/ingest/static/*` and `/ingest/array/*` to its assets host, the rest to its ingest host (EU). Only with a PostHog key and host, see Analytics |
| `/robots.txt`, `/sitemap.xml` | `robots.ts`, `sitemap.ts` | site-wide |
| `/favicon.ico` | `public/favicon.ico` | the hub's icon: a static file answers before `[game]`, so `favicon.ico` is never read as a slug. Not `app/favicon.ico`: Next adds that one to the head of every page, game pages included, next to their own `/<slug>/icons/*` |

- The hub (`(hub)/layout.tsx`), the games (`[game]/layout.tsx`) and the gamemaster (`gamemaster/layout.tsx`: platform look, no game runtime, noindex) have separate root layouts; `global-not-found.tsx` answers any URL that matches no route. Links from the hub to a game are plain `<a>` (full page load).
- Route files are thin wrappers: pages call `@pbgo/core/pages/*` with the game (`gameOf` / `playableGameOf` / `previewableGameOf` from `apps/web/src/lib/game.ts`; the gamemaster pages take any game of the registry through `getGame`), API routes wrap the `@pbgo/core/routes/api/**` handler with `gameRoute()` from `@pbgo/games` and the `@pbgo/core/routes/gamemaster/**` ones with `gamemasterRoute()`. Segment configs (`dynamic`, `revalidate`) stay written out in the app (Next does not read them through a re-export).
- 404: a URL that matches no route (`/x/a/b/c`, `/<slug>/not-a-page`) gets `global-not-found.tsx`, rendered on the server. A page that calls `notFound()` (`gameOf` / `playableGameOf` / `previewableGameOf`: unknown slug, missing table or preview) gets `[game]/not-found.tsx` (`GameNotFound`): the game's own 404 for a slug of the registry, the site's 404 for any other slug. The gamemaster has its own `gamemaster/not-found.tsx` (unknown game or section). Next 16.4 answers a page's `notFound()` with status 404 and `noindex` but renders the not-found UI on the client (the server HTML has an empty body).
- The `[game]` layout is a root layout, so it must not call `notFound()` itself: nothing sits above it to catch the error and Next answers with its own default 404 page. For an unknown slug it renders a bare `<html>` shell and each page's `gameOf` answers 404. `dynamicParams = false` is not enforced on these dynamic pages.
- A game that is not playable here (no engine, or not live in production) keeps its home page ("coming soon"); its table and API answer 404 (`GAME_NOT_FOUND`). The gamemaster ignores that rule: it manages every game of the registry, live or not, in production too, and its previews render any game with an engine (`hasEngine`, `getPreviewableGame`), for the signed-in gamemaster only.
- A game's public files live in `apps/web/public/<slug>/` (URL `/<slug>/...`); build their URLs with `asset()` of the game's `src/lib/site.ts`. Paths derive from the slug: no base path, no `withBase()`.
- `api`, `legal`, `design`, `ingest` and `gamemaster` are routes of `apps/web`, and `login` / `logout` are reserved with them (`/gamemaster/login` sits next to `/gamemaster/<slug>`), so none of them can be a game slug (`registry.test.ts`, `pnpm new-game`)

## Games registry (`packages/games`, `@pbgo/games`)
- `src/registry.ts` — `GAMES`, pure data read by the hub, the sitemap, the router, `next.config.ts` and the scripts: `slug`, `name`, `tagline`, `players`, `duration` (minutes), `visual` (cover art of the hub card, a public path under `/<slug>/`), `sanityProjectId`, `live` (playable in production; every game stays playable outside production), `indexable` (sitemap, no `noindex`)
- `src/index.ts` (server) — `LOADERS`: slug → `() => import("@pbgo-game/<slug>/server")`; `getGame`, `getPlayableGame`, `getPreviewableGame`, `gameRoute`, `gamemasterRoute`
- `src/runtime.tsx` (client) — `RUNTIMES`: slug → `dynamic(() => import("@pbgo-game/<slug>/runtime"))`, mounted by the `[game]` layout
- Code splitting: a page loads only its game's code; the hub loads none (no three.js). Never import a game package statically from shared code.
- Adding a game = one `@pbgo-game/<slug>` package + one entry in `GAMES`, `LOADERS` and `RUNTIMES` + the dependency in `packages/games/package.json` (`pnpm new-game` does all of it)

## A game's binding package (`@pbgo-game/<slug>`)
Contract types in `@pbgo/core/lib/binding` (`GameBinding`, `UiBinding`, `ServerBinding`):
- `.` (`src/index.ts`, isomorphic) — `SLUG`, `NAME`, `TAGLINE`, `DESCRIPTION`, `AUTHOR`, `CONTACT`… (from `src/lib/site.ts`), the engine `GAME` (absent: not playable yet); optional `SOUNDS`, `I18N`, `DEFAULT_SKIN`, `UI_THEME`, `SETTINGS_DEFAULTS`, `ERROR_MESSAGES`, `REACTIONS`, `STUDIO_URL`
- `./ui` (`src/ui.tsx`, client) — `Logo`, `Game` (the board, loaded lazily so the home page does not pull in three.js)
- `./server` (`src/server.ts`, server only) — everything of `.` plus optional `loadSetupData` (data for `GAME.setup`), `loadGameData` (`data` prop of the board), `ROUTES` (the game's own routes, `/api/<slug>/games/<code>/<route>`), `SEO`
- `./runtime` (`src/runtime.tsx`, client) — the game's styles and fonts and `BindingProvider`
- `./styles.css` — the game's Tailwind entry: imports `@pbgo/core/styles/game.css` (theme tokens, `@source` to `packages/core` and `packages/ui`), then `@source "."` and the game's own tokens and fonts
- Core never imports a game: pages and API handlers receive the `GameModule`, client components read it with `useBinding()`

## Shared packages (`packages/`)
A change here reaches every game on the next deployment.
- `@pbgo/core` — the shared base: server (`server/*`: Supabase games with a version lock, players, admin, stats, tasks, rate limiting), `lib/*` (binding contract, api, realtime, settings, i18n, skin, sound, site URLs), components (home, lobby, game context, HUD, chat, game over, sharing, admin, toolbar), pages (`pages/home|game|admin|preview`), route handlers (`routes/api/**/route.ts` for the games, `routes/gamemaster/**/route.ts` for the gamemaster), metadata images
  - Standard screens and game flow (from Courtisans): `Screen` (home, invitation, lobby), `GameHud` + `Ticker` + `groupTurns` + `useAnnouncements`, `GameOver` (`renderDetail` for the score detail), sound (`lib/sound.ts`, `SoundButton`, `SoundEngine`), `DesktopOnly`, leva debug panel, all mounted by `AppShell` in the `[game]` layout
  - In-game UI (ticker, announcements, takeover pill, chat, game over, `PlayersStrip`, seat label): written once, drawn in the game's own look, never the platform's. The ticker, the takeover pill, the chat and the toolbar have no setting, they take the game's skin as they are. Three parts are tuned by `UI_THEME` of the binding (`UiTheme` in `lib/binding.ts`; `lib/ui-theme.ts` holds the defaults and `announcementTheme|seatTheme|gameOverTheme`): the announcements, the seat label and the game over. A game never restyles a component
  - Pure view + connected wrapper: the announcements (`announcement-view.tsx`, `AnnouncementPresence` wraps it in `AnimatePresence`; `announcement.tsx` adds the sound, leva and the game), the game over (`game-over-panel.tsx`; `game-over.tsx` reads the game, shares the result and replays) and the strip (`players-strip-view.tsx`; `players-strip.tsx`) take props only, so `/design` draws the very same markup as the games. A change goes into the view; the specimens follow by themselves
  - Seat label (`seat-label.tsx`, fed by `player-seat.tsx`): avatar + nickname + seat colour, the one way a player is named in the DOM (lobby, strip, announcements, game over). The 3D tables paint the same avatar (`lib/seat-avatar-canvas.ts`, `SeatAvatarMesh` of each game). The avatar is generated (initial on the seat colour); an account picture (`imageUrl`, PLT-13) replaces it and nothing else changes. `UI_THEME.seat`: `shape`, `ring`, `font`, `name` (`"seat"` colour or `"ink"`)
  - Announcements: four kinds (`start`, `round`, `turn`, `victory`), presets and timeline in `lib/announcement-settings.ts` (pure and tested; `announcementSettings(preset, UI_THEME.announcement)` seeds them). Sizes go through `vh()`, `calc(var(--vh, 1vh) * n)`: a screen reads the viewport, a stage that sets `--vh` (the `/design` specimens, scaled down) sizes like a screen of its own height. `UI_THEME.announcement`: `font`, `color`, `outline`, `shadow`, `veil`, `rule`, `confetti`
  - Game over: the panel (winner, ranking, score chips from `renderDetail`, share thumbnail as a polaroid) in the game's surface. `UI_THEME.gameOver`: `surface` (any CSS background), `border`, `radius`, `ink`, `accent`, `frame`
  - `DesktopOnly`: full-screen wall under 900 px on game pages only (`/<slug>/game/…`, the gamemaster's game preview included); the home and public pages stay readable on mobile (SEO), with `DesktopNotice` and no table creation from a narrow screen. The wall (`z-[100]`) sits above the cookie bar (`z-50`) like it does above the rest of the game page, so nothing is asked on that screen: the bar shows on the game home and the hub
  - Skin (`lib/skin.ts`, `loadSkin`, `useSkin`, `useText`): Sanity `interface` (top/bottom art, character, pattern, host icon, player colors, desktop only) + `texts` (home intro, victory lines, `UI_TEXTS` labels of `@pbgo/studio-kit/constants`); a game's defaults in `DEFAULT_SKIN`
  - Who the game waits for (engine contract v2): `GAME.waitingFor(state)` = the players the game waits for (several on a simultaneous step), `GAME.autoPlayFor(state, playerId)` = plays the current step for one of them. Core reads them only through the `@pbgo/engine-kit` helpers `waitingPlayers`, `canPlayFor`, `playFor`; the legacy `activePlayer` / `autoPlay` still work (`@deprecated`). `waitingFor` is public: `PublicGame.waitingFor`, next to `present` (members seen in the last 75 s) and `takeovers` (per waiting player: required voters and votes so far)
  - Absent player: after `settings.turnTimeout` (60 s by default, Gamemaster › Mechanics) without a write, `StalledTurn` offers the present players to vote, per absent player (`/takeover`, which plays with `playFor`); the opening of Courtisans (missions to read) is an ordinary takeover too. Rules in `server/takeover.ts` (pure, tested): a player is played for once every member seen in the last 75 s, other than them, has voted for them; an absent player never blocks
  - Concurrent writes: `updateGame` retries up to 8 times with a growing random wait
  - Accent font (announcements, intro): CSS variable `--font-accent`
- `@pbgo/games` — the registry (above)
- `@pbgo/analytics` — PostHog for the hub and every game: typed events (`ServerEvents`, `ClientEvents`), `track()` of the server (`./server`), the consent-aware browser provider, the banner, `ConsentLink` and `useIdentifyPlayer` (`./client`), the consent store and rules, the table-code scrubber and the banner texts (`.`), the settings (`./config`). It may depend on `@pbgo/ui` and `@pbgo/studio-kit/constants`, never on core or a game. See Analytics
- `@pbgo/engine-kit` — engine ↔ web contract (`GameDefinition` with `waitingFor` / `autoPlayFor`, `Results`…), turn helpers (`waitingPlayers`, `currentPlayer`, `canPlayFor`, `playFor`, `playOn`), game options (`defaultOptions`, `normalizeOptions`), `EngineError`. A game's engine re-exports it: `export * from "@pbgo/engine-kit"`
  - Building blocks of the card games, pure, seeded and tested, each documented in `packages/engine-kit/README.md`: `rng` (`createSaveableRng` / `restoreRng` carry a stream from one action to the next, `shuffle`, `sideSeed`), `ids` (numeric opaque card ids, `reissueId` when a card goes back into hiding), `deck` (`draw`, `peek`, `insertAt`, `reshuffleDiscard`, `drawWithReshuffle`, `deal`), `log` (`viewLog`: entries filtered per viewer), `rounds` (`roundsOutcome`, `sumRounds`, `ranks`: scores until a target), `simultaneous` (`Submissions<T>`, `openSubmissions`, `submit`, `pendingSubmissions(submissions, seatIds)`, `allSubmitted`, `submittedFlags`, `revealSubmissions`)
  - Lean state, for every game (PLT-45): the state holds ids and numbers only, no display data, no derived values, no log
  - The state is stored as `jsonb`, which does not keep the order of the keys: an order (seats, turns) always comes from an array of the state, never from `Object.keys`
- `@pbgo/ui` — shadcn components + `cn`: `@pbgo/ui/game/<comp>` (game theme), `@pbgo/ui/platform/<comp>` (platform theme: hub, account, legal, admin, 404), `@pbgo/ui/styles/platform.css` (platform tokens), `@pbgo/ui/theme` (`PLATFORM_THEME_COLOR`), `@pbgo/ui/utils`. See Design system
- `@pbgo/studio-kit` — shared Sanity schemas (`settings`, `interface`, `audio`, `texts` via `createTexts(extra)`, `localeString`…; no `rules` document, see Languages) and `createStudioConfig({ title, projectId, gameTypes })` (a game type with the same name replaces the shared one); `@pbgo/studio-kit/constants` (languages, `FONT_CHOICES`) importable on the web side
- `@pbgo/content-kit` — the seed pipeline of a game's Sanity content, shared by every game: options and token, plan, art (scan, WebP, upload, place), drafts-only writes, report, plus the test helpers (in-memory dataset, Studio-schema checker). A game keeps only its data and its config in `games/<slug>/content` and calls `runSeedCli`. Three entry points: `.` (what the data files import: `localeString`, `localeText`, `setField`, `setItemField`, `ArtSlot`, `SeedDoc`), `./seed` (the runner) and `./testing`. Consumed as source and run by Node (type stripping): relative imports carry `.ts`, type imports are `import type`, erasable syntax only, and the kit declares its own dependencies. Documented in `packages/content-kit/README.md`; `apps/web` does not use it
- `@pbgo/tsconfig`, `@pbgo/eslint-config` — shared TypeScript and ESLint configs
- Every external dependency comes from the pnpm catalog (`catalog:` in `package.json`, versions in `pnpm-workspace.yaml`); `pnpm check:catalog` enforces it
- A new workspace package used by apps/web goes into `transpilePackages` (`apps/web/next.config.ts`; game packages are added from the registry)

## Design system (`@pbgo/ui`)
Black and white, dark theme only, Geist Sans in semibold with tight line-height and letter-spacing. No accent colour, no gradient: game art is the only colour on the platform. Every token and component is shown on the internal page `/design` (`(hub)/design/page.tsx`, noindex, not in the sitemap): it is the reference, check it before building a screen.
- Two layers share the token names (`--background`, `--foreground`, `--primary`, `--muted`, `--border`, `--radius`, `--font-body`…):
  - Platform layer (hub, account, legal, admin, 404): values in `packages/ui/src/styles/platform.css`, scoped to the class `.platform`. The class sits on `<html>` (hub and 404, through `PlatformDocument`), on the admin wrapper and on the root of every portal (select, dropdown, dialog, sheet, tooltip, toast), which React renders outside the wrapper. Components: `@pbgo/ui/platform/*`
  - Game layer: the `:root` values of `packages/core/styles/game.css`, overridden at runtime by the game's Sanity skin (inline style on `<html>`, `themeStyle()`). Components: `@pbgo/ui/game/*`. A game changes its look by changing token values, never a component
- Boundary: the platform never sets a value on `:root` and a game never sets one on `.platform`. In `platform.css`, `@theme` only defines new names (`shadow-surface|float|overlay`, `duration-fast|base|slow`, `ease-standard`, `bg-scrim`, `max-w-page|reading`, `px-gutter`, `py-section`); a name Tailwind already has (type-scale line-heights, `--tracking-tight`, `--default-transition-*`, `--font-weight-*`) gets its platform value inside `.platform`, or every game would inherit it
- In-game UI: not part of the platform layer. It is drawn in the game's own look (its skin tokens `--foreground`, `--surface`, `--accent-game`, `--font-title`, `--font-accent`, set by `themeStyle()`), tuned by `UI_THEME` (see Game UI); never `@pbgo/ui/platform`, Geist or the `.platform` class. `/design › In-game UI` is the one place where the hub shows it: two games (Courtisans and the template) side by side, each inside a `GameScope` (`_components/game-scope.tsx`) that resets the platform's values (Geist, weight, line-heights, tracking, radius) and sets the game's tokens and font stacks on its own wrapper, never on `:root`. The hub does not load `game.css`: `globals.css` points `@source` at the four pure components (`seat-label`, `players-strip-view`, `announcement-view`, `game-over-panel`) and maps the utilities only games have (`font-display`, `bg-surface`, `bg-surface-dark`, `text-accent-game`) with `@theme inline`, which emits no variable. A new pure component drawn on `/design` needs its `@source` there. The font files of a game are not loaded on the hub, so its families fall to the next of the stack (Georgia); the colours, layout and motion are the real ones. Use `data-look`, never `data-game` (analytics counts the hub links that carry it)
- Palette: Tailwind's `neutral` scale (chroma 0) and `destructive`, nothing else. One font weight (600): `font-medium`, `font-bold`… resolve to it, so don't write them. Depth: `shadow-surface|float|overlay` and `ring-1 ring-foreground/10`. Motion: `duration-fast|base|slow`, `ease-standard`. Shapes: `rounded-*`, scaled from `--radius`
- Popovers with a list (select, dropdown menu) are translucent (`bg-popover/70`) and carry their blur on the popover element itself (`backdrop-blur-2xl backdrop-saturate-150`), never on a `::before`. A descendant with a blend mode (the `Avatar` ring is `mix-blend-lighten`) makes the popover an isolated group in Chromium, and a pseudo-element backdrop then blurs nothing: the page shows through the list, sharp. The game switcher (an `Avatar` in each of its rows) is the live check of this rule
- `PLATFORM_THEME_COLOR` (`@pbgo/ui/theme`) is the browser colour of platform pages; `theme.test.ts` keeps it equal to `--background`. `platform.test.ts` rejects `dark:`, palette and hard-coded colours, arbitrary sizes and the old `admin` names in `packages/ui/src/platform/*`
- A new component: `pnpm dlx shadcn@latest add <comp>` (preset `beEgoY8u`), move it to `packages/ui/src/platform`, import `cn` from `../utils`, make it dark-only and token-only, show it on `/design`, then use it

## Commands (from the root)
- `pnpm install` — once for the whole monorepo
- `pnpm dev` — apps/web on http://localhost:3100 (hub + every game; `pnpm dev <slug>` prints its URL)
- `pnpm dev:studio <slug>` — the game's Sanity Studio
- `pnpm build` (= `pnpm --filter web build`) · `pnpm typecheck` · `pnpm test` · `pnpm lint` · `pnpm check:catalog`
- `pnpm --filter @<slug>/engine test` · `pnpm --filter @pbgo/core test`
- `pnpm new-game <slug>` — `games/<slug>` from `template/`, registered in `packages/games` (not live)
- `pnpm go-live <slug>` — Sanity side: project, public dataset, CORS, studio deployed, project id written in the registry, write token in `apps/web/.env.local`
- `pnpm add-game <slug> [--push]` — `setup-env --check` first (nothing is created when it fails), then new-game + go-live + setup-env; `--push` commits and pushes a branch for a pull request
- `pnpm setup-env [--no-push | --check]` — applies the pending Supabase migrations (see Supabase), fills `apps/web/.env.local` (generating `ADMIN_SESSION_SECRET` once and appending it to the secrets file) and pushes the variables to the Vercel project `pbgo`, looked up by its id (`VERCEL_PROJECT_ID` of the secrets file, else `prj_bsk7OjC3wkJrI6ElHFa8bfD71xfs`), never by its name, through the API alone (no `.vercel/project.json`, no Vercel CLI, no CLI login: any worktree will do); aborts, touching neither `.env.local` nor Vercel, when a Supabase value is missing, a project can't be used or a migration fails (see Environment). `--no-push` writes nothing to Vercel and neither reads nor migrates the production project. `NEXT_PUBLIC_POSTHOG_KEY` and `NEXT_PUBLIC_POSTHOG_HOST` (optional, both or neither) go to `.env.local` and to every Vercel target once `@pbgo/analytics` accepts the pair (a pair it refuses prints ✗ and is neither written nor pushed, the exit code does not change). A Supabase variable already on the Production target (the Supabase ↔ Vercel integration manages them) is skipped, not overwritten, and the run still exits 0; it exits 1 only when the Vercel project can't be reached or a Vercel call really fails

## Package names
`@pbgo-game/<slug>` (binding), `@<slug>/engine`, `<slug>-studio` (template: `@pbgo-game/template`, `@template/engine`, `template-studio`). Always target a package with `--filter`.

## Deployment
- One Vercel project, `pbgo` (root directory `apps/web`), owns the domain `playboardgamesonline.app`. Push to `main` = production; every pull request gets a preview
- A game reaches production when `live: true` in the registry; `indexable: true` lets search engines in. Only Courtisans is live and indexable
- `robots.txt` disallows `/api/`, `/ingest/`, `/gamemaster`, `/*/preview`, `/*/game/`; the sitemap lists the hub and the indexable games (never the gamemaster); non-indexable game pages carry `noindex`. Every `/gamemaster/**` response also has `X-Robots-Tag: noindex, nofollow` (`next.config.ts`) and the `noindex, nofollow` meta

## Environment (`apps/web/.env.example`)
- Local values in `apps/web/.env.local`, never committed; on Vercel, on the project `pbgo`. `pnpm setup-env` fills both from `~/.config/pbgo/secrets.env` (outside the repo, `chmod 600`)
- The secrets file holds `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF` (production) and `SUPABASE_PREVIEW_PROJECT_REF` (`pbgo-preview`), all three required: `pnpm setup-env` refuses to run without them. The production project's keys go to the Vercel Production target only; `apps/web/.env.local` and the Vercel Preview and Development targets get the preview project's keys, never production ones. ## Sanity
- One Sanity project per game (`sanityProjectId` in the registry), dataset `production`, studio `<slug>-studio` deployed to `<host>.sanity.studio`
- The studio reads its project id from `apps/studio/.env` (`SANITY_STUDIO_PROJECT_ID`, see `.env.example`) or from `sanity.cli.ts`
- A game's own content types: schemas in `apps/studio/schemaTypes`, queries in the binding's `src/sanity/`, then `pnpm --filter <slug>-studio typegen`
- Studio forms (the cards, colors and tiles a game's owner fills in one by one, in every game and in the template; the shared singletons `settings`, `interface`, `audio`, `texts` and a game's `game` keep their descriptions). A form is short and in the same order everywhere:
  - One document type, hence one list of the Studio (`collections` of `sanity.config.ts`), per kind of card (Number, Action, Modifier), never one type with a `kind` field. A game whose cards are the faces of one deck (Hanabi) has one `card` list, next to the list of its colors
  - No `Effect` or `Rule` field on a card: the rules reach players as the publisher's PDF links in `settings`, and what a card does is the engine's
  - No `description` (the grey sub-label under a field) on a card, a color or a tile: the `title` says it, and a format hint goes into the validation message (`.error("One letter")`). The subtitle of the list preview stays (`× 3`)
  - The identity of the card comes first (game key, name, or value and color), then the quantity (`quantity` or `copies`), and the visual (image) is always the last field of the form
  - A `name` may be multilingual (`localeString`), but the document always has an English game key (`key`, titled "Game key", a dropdown of the keys the engine knows): the engine, the seed and the board read the key, the name is only shown. A card with no name (Hanabi) is identified by its English keys, value and color
  - A game with a seed keeps these rules in its `schema.test.ts` (Hanabi: "the forms of the cards"). Courtisans predates them (its board reads `role.rule`): it follows in a later change
- Seeding: a game's content (cards, credits, rulebook links, art) is described in `games/<slug>/content/` (data and config) and written by the shared `@pbgo/content-kit` with `pnpm --filter @pbgo-game/<slug> content:seed --dry-run` then `--apply`. Drafts only (publishing stays in the Studio), idempotent, never overwrites what was edited in the Studio. Token `SANITY_API_WRITE_TOKEN_<SLUG>`, never printed. Process, options, art naming: `docs/content-pipeline.md`
- Media proxy `GET /api/media?url=` (shared by every game; fonts, sounds, SVG) only serves `https://cdn.sanity.io/(images|files)/<projectId>/…` where `<projectId>` is the `sanityProjectId` of a game of the registry (`sanityAssetUrl` in `packages/core/sanity/media.ts`, which also refuses `%` in the path and fetches the normalized URL). Core never imports the games: `apps/web/src/app/api/media/route.ts` passes the ids to `mediaRoute()`

## Supabase
- One project for every game (production), plus `pbgo-preview` for local development and Vercel previews. Schema: `supabase/migrations` (`games`, `tasks`, `feedback`, each with a `game` column = the slug; RLS on without policies, only the server reads and writes)
- Migrations: `supabase/migrations/<number>_<name>.sql`, applied by `pnpm setup-env` to `pbgo-preview`, then to production, in file order, each one recorded in `supabase_migrations.schema_migrations` (the Supabase CLI's table: `version` = the number, `name` = the rest). One line per project: up to date, applied …, or failed with the error; a recorded migration never runs again. A migration and its tracking row are one `BEGIN … COMMIT`: a failure leaves neither, stops the run, and production is left alone when preview fails. So a file holds no `BEGIN` / `COMMIT` / `ROLLBACK` and no statement that can't run in a transaction (`CREATE INDEX CONCURRENTLY`, `VACUUM`): apply those by hand and insert their row. `0001` and `0002` are recorded without being run on a project that already holds their effects (baseline; `pbgo-preview` predates the tracking table)
- Setup-env applies the files of the checkout it runs in, production included: run it from an up-to-date `main`, never from a branch with an unmerged migration (`--no-push` stays on preview, which is how to try a migration). A merge and its deployment apply nothing
- Realtime is broadcast only: after each write the server sends `update` on `game:<slug>:<code>`, clients refetch their view (`GET /api/<slug>/games/<code>`)
- Player identity: httpOnly cookie `<slug>_player`
- Presence: `games.seen` (jsonb, player id → last time the server saw them), written by the RPC `touch_game_player` (migration `0002_presence.sql`) on reads and writes of a table, at most every 15 s per player (`server/presence.ts`, after the response); it touches neither `version` nor `updated_at`. The takeover only counts the members seen in the last 75 s

## Rate limiting
- Every mutating game route (create, join, leave, options, start, action, replay, takeover) and `POST /api/<slug>/feedback` start with `await rateLimit(game.slug, request, "<rule>")` (`server/rate-limit.ts`). Limits live in `RATE_LIMITS` (`server/rate-limiter.ts`): per player cookie when present, else per IP (create: always per IP), never per table, plus a per-IP ceiling across routes. Over the limit: 429 `RATE_LIMITED` + `Retry-After`. The chat route has its own per-player token bucket
- `POST /gamemaster/api/login` belongs to no game: it starts with `await rateLimit(null, request, "adminLogin")`, 5 attempts per 10 minutes per IP, counted before the credentials are checked (the right password is refused too once the limit is reached)
- Counters are in memory, per function instance; to share them, implement `RateLimitStore` and call `setRateLimitStore()`. A new mutating route of a game (`ROUTES`) must call `rateLimit` too

## Analytics (PostHog, `@pbgo/analytics`)
Optional: without `NEXT_PUBLIC_POSTHOG_KEY` and `NEXT_PUBLIC_POSTHOG_HOST` nothing runs (no request, no banner, no "Cookies" link). Vercel's `<Analytics />` is a separate, cookie-free measure and is unchanged. Every event carries `env` (`production`, `preview` or `development`: `VERCEL_ENV`, copied to `NEXT_PUBLIC_APP_ENV` by `next.config.ts`), the property that tells a real player from a test
- Events are typed in `packages/analytics/src/events.ts` (snake_case, `game` = the slug on every game event) and hold no personal data: never a nickname, chat text or table code. A new event = one entry there, then one line at the call site
- Server events (counted whatever the visitor answered): `trackAfter(event, playerId, properties)` of `@pbgo/core/server/analytics`, in `packages/core/routes/api/games/**`, after `updateGame` returns and never inside its modifier (that runs again when it loses a race). The id is the random value of the game's `<slug>_player` cookie, so nothing more is stored on the device; `identity_stable: false` until accounts exist (PLT-13), no person profile, no geolocation. `game_finished` is sent when the returned row is `over`; its `duration_s` and `moves_count` are approximations (`updated_at − created_at`, `version`) flagged `approximate: true`. Not tracked yet: `game_abandoned` (needs a sweeper)
- Browser: `AnalyticsProvider` is mounted by the hub, `[game]` and `global-not-found` root layouts, never by the gamemaster. The SDK talks to `/ingest` (rewritten to PostHog's EU hosts, `next.config.ts`; `skipTrailingSlashRedirect` is global because PostHog's endpoints end with a slash, and every canonical URL and the sitemap are explicit strings without one). Before the visitor answers it runs with `persistence: 'memory'` (nothing stored: each page load is a new anonymous visitor, so unique-visitor counts before consent are inflated). "Accept" switches to `localStorage+cookie`, calls `identify(<player id>)` at a table (`useIdentifyPlayer`) and starts session recording; "Refuse" or a withdrawal goes back to memory and sweeps the SDK's keys (`keys.ts`). `game_opened_from_hub` is counted from the hub's links that carry `data-game="<slug>"` (the hero button and the game cards: a new link from the hub to a game needs the attribute)
- The answer is `pbgo-consent` in `localStorage` (choice and date), asked again after 13 months (`consent.ts`). The banner (`CookieBanner` of `@pbgo/ui/platform`) is a single line docked to the bottom of the screen, never a card over the page: one sentence that ends with a "Details" link to `/legal#cookies`, then Refuse and Accept as the same button (FR/EN/ES/DE in `texts.ts`; `texts.test.ts` caps the sentence: one line on a desktop, 6.6% of a 1280×800 screen; on a phone it wraps to 3–4 lines beside the two stacked buttons, 9.4% of a 390×844 screen and 11.9% of a 375×667 one, and more below that (12.4% in English and 14.8% in German at 360×640), so a shorter sentence is the lever). The full disclosure (what is counted either way, what a refusal stores) lives in `/legal#cookies`, not in the bar. The banner and the "Cookies" links that reopen it (`ConsentLink`: hub footer, game home footer; the settings menu row) are hidden on pages that do not report: `/gamemaster`, `/design` and `/<slug>/preview/*` (`isExcludedPath`). The banner is `ph-no-capture` (its clicks are reported once, by `cookie_consent`, never by autocapture under the identity being given up; `banner.test.ts` keeps the class). What the visitor is told lives in `texts.ts` and in `/legal#cookies` (`(hub)/legal/page.tsx`): change them together with the behaviour
- The bar keeps its room free (`reserve.ts`, `reserveSpace`): the banner measures itself (a `ResizeObserver`) and publishes its height as `--consent-h` on `<body>`, with an inline `padding-bottom` of the same height, and removes both when it goes away (0px without a banner). Never on `:root`: the platform sets no value there, or every game would inherit it. A page that scrolls simply ends above the bar; a screen as tall as the viewport and an element fixed to the bottom do the arithmetic themselves (see Game UI). The 3D canvas and the board area resize when the banner appears, is reopened from a "Cookies" link or closes
- Recordings mask every input; the chat is `ph-no-capture`, nicknames printed by core are `ph-mask` (the 3D scenes draw theirs in a canvas, which is not recorded). A game that prints a nickname in its own DOM adds `ph-mask` there, and `ph-no-capture` as well when it sits inside a button or a link: autocapture sends the text of a clicked `a` / `button` (`$el_text`), nested text included. Never set `maskTextFn` in `options.ts`: it replaces the stars of every masked node and would show the nicknames
- Table codes (`/<slug>/game/<CODE>`, `/api/<slug>/games/<CODE>/…`, and `Table #XXX-XXX` of the tab title) are scrubbed by `scrub.ts`: from every property of an event (`before_send`), from the page address, the links and the network timings of a replay (`maskCapturedNetworkRequestFn`, `maskAttributeFn`), and the `<title>` is masked in the replay (`maskTextSelector: "title"`). The code field is `ph-mask` too. A new place that prints the code needs the same care. The client's masking options win over the project's "Privacy and masking" settings: leave the project's text and block selectors empty. The recorder compresses its larger chunks (gzip), so check a replay after gunzipping it, never by searching the raw upload
- Not in the repo, set in the PostHog project `pbgo` (EU cloud): recording enabled for the domain, exception autocapture, web vitals, IP anonymisation, the internal/test-account filter, authorised URLs
